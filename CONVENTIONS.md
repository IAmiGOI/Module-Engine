# ST Module Engine — Beta: конвенции именования и структуры

Черновой шаблон. Цель — чтобы КАЖДЫЙ контракт, Блок, файл и манифест
выглядели предсказуемо, без разнобоя, который был в Alpha (там разные
модули изобретали свой стиль ключей независимо: `tracker:field:<id>:<name>`,
`lorebook:entry:<book>:<uid>`, `status:<id>` — три разных подхода к одному
и тому же).

## 1. Имена контрактов — `<домен>.<способность>[.<уточнение>]`

- Строчными буквами, через точку, camelCase внутри сегмента для составных
  слов: `model.generate`, `model.embed`, `tts.synthesize`, `image.generate`,
  `storage.settings`, `storage.chatMemory`, `worldInfo.entries`,
  `characterCard.field`, `tracking.value`, `pipeline.run`.
- **Домен = область СПОСОБНОСТИ, не имя конкретного поставщика.** Контракт
  `model.generate` может реализовывать и Ядро внутренних моделей, и Ядро
  локал-хост моделей, и Ядро основной модели ST — заказчик просит
  способность, а не конкретное Ядро (иначе теряется весь смысл Директора).
- **Правило №1 — контракт ВСЕГДА конечен и не меняется в рантайме.**
  Никогда не зашивать динамический ID прямо в имя контракта (в отличие от
  Alpha's `tracker:field:<blockId>:<name>`). Вместо этого — фиксированное имя
  контракта (`tracking.value`) + динамический параметр внутри самого запроса
  (`{ blockId, fieldName }`). Discovery динамических инстансов — через Блоки
  (см. ниже), не через раздувание списка контрактов.

## 2. Имена Блоков — та же схема, свой неймспейс на шину

`<домен>.<категория>` — например `picker.insertableValues`,
`tracking.blocks`, `worldInfo.publishedEntries`. Официальная таксономия
категорий Блоков (см. ARCHITECTURE.md) публикуется движком централизованно
— автор нового Ядра/Модуля не изобретает своё имя категории, а берёт из
таксономии.

## 3. Имена динамических событий — `<домен>.<категория>.changed`

Когда Блок пополняется/меняется, событие на Шине событий называется
`<то же имя Блока>.changed` — например `tracking.blocks.changed`,
`worldInfo.publishedEntries.changed`. Единообразно с именем самого Блока —
подписчику не нужно запоминать отдельное соглашение для события.

## 4. Единый конверт ответа — везде одинаковый

Любая доставка через `subscribe()` (и, соответственно, через библиотечный
`request()`) — всегда одна и та же форма:

```
{ ok: true, value: <результат> }
{ ok: false, error: { message, code? } }
```

Никогда не бросает исключение через границу Директора (см. "Контракт на
ошибки" в ARCHITECTURE.md) — эта форма и есть механизм, которым это
гарантируется. Один конверт на все 4 шины, без исключений по типу контракта.

## 5. Манифест — одна форма для Ядра, Модуля и Сервиса

```
{
  id: '<домен>.<имя>',           // тот же стиль, что контракты
  version: '<semver>',
  layer: 'core' | 'module' | 'service',
  dependencies: [
    { contract: '<имя контракта>', versionRange: '<semver-range>' }
  ],
  rights: { tier: 'official' | 'community' | 'scanned-safe' | 'scanned-unsafe', key?: '<зашифрованный ключ>' }
}
```

Раннер читает это при загрузке для: semver-gate (см. ARCHITECTURE.md),
привязки прав к ID (см. систему прав), построения живого графа зависимостей
(Ядро логирования/Dev-panel).

## 6. Файлы и папки — по лагерю

```
cores/<домен>/index.js          // например cores/tracking/index.js
modules/<имя>/index.js          // например modules/dice/index.js
services/<имя>.js               // например services/http.js
libraries/core/<имя>.js
libraries/module/<имя>.js
libraries/shared/<имя>.js
```

`id` из манифеста соответствует пути (`cores/tracking` → `id: 'tracking'`
или `'engine.tracking'`, если нужен более явный неймспейс верхнего уровня —
открытый вопрос ниже).

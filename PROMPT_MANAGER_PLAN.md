# План: собственный Prompt Manager движка (PM)

Статус: **обсуждение и подготовка, кода нет.** Документ живой: ответы владельца — в разделе 0, открытые вопросы — в разделе 2. Ничего из раздела 3 («Набросок архитектуры») не решено окончательно, это рабочий черновик под правку.

Правила репозитория действуют полностью: комментарии и документы на русском, интерфейс на английском, файлы ≤ 300 строк (никаких файлов-«божков»), решения — в ROADMAP.md, полные названия тестов, работа маленькими шагами.

## 0. Решения владельца (не менять без согласования)

### Цель
- Свой менеджер промптов поверх ST: **лучше, быстрее, полностью совместимый с любым модулем движка**, работает с промптами и пресетами самого ST, умеет экспорт и импорт.
- Что не устраивает в менеджере ST: статичное дерево промптов; нет групп; **нет интеграции с ME** — размещение текущих инжектов модулей непрозрачно и не редактируется; старый интерфейс; мало функций; нет динамических промптов; нет промптов по триггеру; расположение через `@x` неинтуитивно визуально.
- «Быстрее» — и скорость редактора, и скорость сборки промпта.

### Границы первой итерации
- **Только Chat Completion.** Text Completion (Kobold, textgen, NovelAI) — позже.
- **Групповые чаты не поддерживаются:** при открытом групповом чате PM показывает предупреждение и выключается (работает штатная сборка ST). «Потом допишем».
- Если API переключён на Text Completion — тоже предупреждение и выключение.
- Ориентир по версии ST — **1.18+**. Образцов внешнего вида нет («нет» на вопрос об ориентирах).

### Включение и подмена ST
- PM **заменяет** сборку ST, когда включён; **по умолчанию включён**. Пассивного режима «только смотреть» нет.
- Штатный менеджер ST подавляется, пока включён наш; кнопка открытия штатного окна заменена на открытие нашего. **Открывается только с кнопки Prompt Manager ST** (других пунктов не нужно).
- Расхождение нашей сборки с ST на тех же входных данных **допустимо** там, где мы улучшаем.
- **Без запасного варианта при подавлении окна ST:** если не удалось подавить штатный менеджер, это **явная ошибка** (видимая пользователю), а не молчаливое сосуществование двух окон.
- **Ошибка плагина:** плагин **выключается**, пользователь предупреждён, сборка идёт дальше без него.
- **Не удалось подавить окно ST → PM выключается, пользователь предупреждён** (штатная сборка ST продолжает работать; чат не блокируется).

### Данные для сборки
- Всё берётся **через наши Ядра, с их доработкой по ходу** (не напрямую из `context` ST).
- Лорбук: **наше Ядро лорбука со СВОИМ движком активации** — пишется постепенно, **результат активации ST не используется** (решение владельца: «сами всё делаем, ST читать не надо»); **либо граф** (граф — замена WI, стоит рядом, основной, но не единственный вариант). *(Формулировка владельца была «наше ядро плача» — прочитано как «ядро лорбука».)*
- **Подстановка макросов — свой сервис** (наши макросы + макросы ST по синтаксису ST; вызова ST-ной подстановки не будет). **Счётчик токенов — свой, быстрый, приближённый.**
- Макросы — **и наши, и макросы ST**.
- Подключения (профили ST: модель, ключ, эндпоинт) PM **не трогает**.

### Модель промптов
- **Группы промптов** — с общей логикой или просто по смыслу.
- **Динамические промпты и триггеры:** «если X → вставить A, если Y → вставить B» и «если X → вставить». Условия: по **трекеру**, по **классификатору** (добавим позже), по **кулдауну**, по **ключевым словам**, по **длине сообщения** и т. д. — набор наращивается плагинами.
- **Интерфейс логики — визуальный конструктор, ноль кода, очень наглядно.**
- **Расположение:** `@x` остаётся для чата; **историю чата делим на начало и конец, блоки размещаются внутри неё визуально, с иерархией относительно друг друга.** Деление истории — **всеми способами на выбор** (по числу сообщений, по токенам, ручной границей); блок можно привязать к началу, к концу или относительно конкретного сообщения.
- **Группы промптов — дерево** (вложенные), общее условие / общий приоритет обрезки / общий бюджет токенов группы — **всё это на выбор** (включается по необходимости).
- **Кулдаун и «время жизни» срабатывания — «дать на выбор»:** в ходах, в сообщениях или по времени; блок остаётся до конца сцены или живёт N ходов (sticky) — выбирается в настройках триггера.
- **Инжекты модулей:** старый путь (`chat.unshift` из модулей) убирается; вводится **новый контракт публикации чат-инжекта**; размещение инжектов модулей видно и редактируется в PM как обычные блоки.
  - **Размещение решает пользователь.** Положение, которое предложил модуль, — только **начальное** (по умолчанию); пользователь свободно меняет положение и включение блока, а к предложенному модулем положению **возвращает кнопкой** («вернуть положение по умолчанию»).

### Плагины
- **Максимум логики — плагины, с горячей заменой** (без перезагрузки страницы), чтобы менеджер легко наращивался.
- Плагины берутся из **каталога** (пока дефолтного, встроенного). Читать они могут **всё, что может читать сам PM**.

### Обрезка и токены
- **Приоритет обрезки:** PM **сам определяет приоритет блоков**; пользователь может переопределить.
- **Визуализация:** переключаемые UI-режимы, показывающие, что обрезано.
- **Сжатия моделью пока нет.**
- **Авто-режим не должен резать историю каждый ход** (это убивает префикс). Вместо этого: при упоре в лимит **немного поднять лимит** (запас), чтобы префикс не обрезался, а блок/пачку сообщений **убрать в подходящий момент одним куском** (пакетная обрезка с запасом — «гистерезис»). Автор идеи считает это дешевле.
- Токены — **быстрый счётчик** (приближённый, локальный).

### Кеш префикса (ОЧЕНЬ важен)
- Провайдеры по приоритету: **OpenRouter → DeepSeek → Gemini → Z.AI → Claude → OpenAI** (приоритет убывает).
- **Режим «что рушит префикс»:** сравнение последних запросов, первая точка расхождения и блок-виновник — «достаточно».
- **Сам PM не делает резких движений, если пользователь их не назначил; он прозрачен.** Внутренние процессы PM оптимизируются так, чтобы не портить префикс сами (модули не в счёт).

### Параметры генерации (расширение объёма)
- В PM входит **управление сэмплером, ризонингом, стримингом и «всем, что есть в ST»** для Chat Completion. **Хранятся в пресете.**
- **Переопределения** на персонажа / чат / модель — **да**, отдельная логика определения, **по умолчанию отключена**.
- **Стриминг нужно управлять**, а не только передавать флаг.
- **Все параметры ST для Chat Completion делаем** (сэмплер целиком, ризонинг, стриминг, провайдерные особенности) — без урезания первой версии.

### Формат, экспорт, синхронизация
- **Внутри ME и для синхронизации — свой формат.** **Экспорт — в формат ST** (с конвертерами в обе стороны). Данные ME при экспорте упаковываются **в файле пресета** так, что их достаёт другой клиент ME; чистый ST их игнорирует (ME → простой ST данные не переносятся, и так задумано).
- **Полный экспорт/импорт, обмен файлами.** В файл идёт **пресет + всё, что к нему относится (слоты модулей, плагины, настройки), но не старые версии.**
- **Авто-подготовка всех существующих пресетов ST** при первом запуске: внутренние копии, оригиналы в файлах ST не трогаются до экспорта.
- **Синхронизация** — уже решена существующим синхронизатором (категория как у библиотеки графов, конфликты — его политикой).
- **Откат и история версий — да; хранятся в БД (IndexedDB).**
- **Журнал отправленных запросов** (собранный промпт по блокам, токены, что обрезано; сравнение запросов) — да, «достаточно» в объёме режима префикса.

### Интерфейс
- **Своё окно, несколько окон** (редактор порядка, предпросмотр «что уйдёт модели» с токенами по блокам и источником каждого блока, кеш префикса, журнал…). **Основное окно — порядок промптов.**
- Предпросмотр «что уйдёт модели» в реальном времени — «да, со всем».

### Guided CoT (новое требование)
- **Скрытые «guided CoT» — полноценные, не как в ST** (штатный ST даёт лишь одноразовую вставку размышления). **С автосохранением ризонинга в рамках одного CoT.** **Включаемая функция** (по умолчанию выключена). Подробности и вопросы — раздел 7.

### Материалы
- Владелец пришлёт **WI** (лорбук) после завершения этой части и **свои пресеты и захваченные запросы** для тестов равенства с ST.
- Разведку кода перед этапом 1 разрешено делать «всё, что хочешь» (только чтение и запись в этот документ).

### Порядок работы
- **Постепенно, максимум распределения нагрузки, никаких файлов-«божков».**

### 1а. Разведка кода (что реально устроено сейчас)

- **Порядок генерации в движке:** ST открывает прогон (`GENERATION_STARTED`) → **перехватчик** `onIntercept({chat, contextSize, abort, type})` в [cores/generation/index.js](cores/generation/index.js): сначала пайплайн `generation.prepare` (свежее состояние, выходы отбрасываются), потом `generation.beforeSend` (вклады) → ST сам собирает промпт (лорбук, персонаж, история, штатный Prompt Manager) → **обёртка `fetch`** на пяти эндпоинтах: `onSend({endpoint, payload})` → пайплайн `generation.payload` (`fold` над телом) → отправка. Решение отправки возвращает `{payload}` / `{cancel, reason}` / `{replyWith}` ([services/st-generation.js](services/st-generation.js)); `replyWith` — ответить самим, к бэкенду не ходить.
- **Следствие для PM:** собирать финальные `messages` естественнее всего в `generation.payload` (тело уже содержит всё, что ST посчитал), либо раньше, в `beforeSend`, если PM хочет владеть и данными. Для Chat Completion в теле лежат и `messages`, и параметры (`temperature`, `stream`, …) — их PM тоже может переписать. Стриминг читает ST из ответа `fetch`; чтобы им управлять, ответ придётся оборачивать.
- **Как модули вкладываются сейчас (то, что PM должен заменить контрактом):** это сырые правки копии истории `chat`: [summary](cores/summary/index.js) (`unshift` + обрезка старых сообщений), [граф памяти](cores/memory-graph/index.js) (`unshift` сообщений `Memory` и `Plot core`), [map-narration](cores/map-narration/index.js) (`splice` на глубину `INJECTION_DEPTH`), модули [notebook](modules/notebook/index.js), [tools](modules/tools/notebook.js) и `secrets` (`splice` по вычисленной позиции), [time](modules/time/index.js) (`unshift` сообщения `System`). Все — `{ is_user: false, is_system: true, name: 'X', mes }`. Именно эти вызовы переезжают на новый контракт публикации чат-инжекта (у каждого есть имя, позиция и признак «стабилен ли для префикса»).
- **Лорбук:** [Ядро лорбука](cores/lorebook/index.js) сегодня **не активирует** записи само — оно читает то, что активировал ST (`st.worldInfoActivated` → `lorebook.lastActivated`), плюс `lorebook.find/get` для записей. **Решение владельца: пишем свой движок активации** (ключи и вторичные ключи, рекурсия, вероятности, sticky/cooldown/delay, порядок и бюджет, группы, глубина сканирования и т. д.), результат ST не используем. Это отдельная крупная работа внутри Ядра лорбука (свой подплан). Граф памяти — параллельный источник вместо лорбука (уже вкладывается сам).
- **Макросы:** [Ядро макросов](cores/macros/index.js) сегодня **регистрирует наши макросы В ST** (`stMacros.register`); подстановку `{{char}}`, `{{user}}` и остальных делает сам ST при своей сборке. **Решение: свой сервис подстановки** — наши макросы + набор макросов ST по их синтаксису (перечень и точное поведение сверяем с пресетами и запросами, которые пришлёт владелец), без вызова ST.
- **Токены:** в репозитории **нет** счётчика токенов (общего сервиса). **Пишем свой** быстрый локальный счётчик (приближённый).
- **Пресеты ST:** чтение/запись через [services/st-user-data.js](services/st-user-data.js) (`presets/openai/<имя>.json` — уже в синхронизации); `stPreset.current` отдаёт текущий выбор ([services/st-preset.js](services/st-preset.js)). Нужно подтвердить по реальным файлам (пришлёт владелец) форму `prompts` / `prompt_order` в 1.18+.
- **Пайплайны:** [Ядро пайплайнов](cores/pipeline/index.js) — DAG этапов с зависимостями (`needs`), таймаутом, `fallbacks`, `onExhausted` (`abort` / `flag`). Этап исполняется под личностью владельца. Реестр этапов и есть «Блок» (обнаружение участников без правок в PM) — совпадает с замыслом PM из CORES.md.

## 3. Набросок архитектуры (ЧЕРНОВИК, не решение)

Слои, каждый — свои маленькие файлы:

1. **Формат и конвертеры** (`libraries/core/pm-*.js`, чистые функции): внутренний формат пресета PM; конвертеры ST ↔ ME без потерь для блока ME; версии формата; квантование не нужно.
2. **Ядро сборки** (`cores/prompt-manager/`): принимает контекст (персонаж, персона, лорбук/граф, история, вклады модулей, макросы) и пресет → упорядоченный список блоков → сообщения. Чистая сборка отдельно от ввода-вывода.
3. **Слоты и вклады модулей:** реестр вкладов (контракт публикации чат-инжекта), размещение задаёт пользователь в PM.
4. **Условия и триггеры:** движок правил с точками расширения под плагины; чистые вычисления, состояние (кулдауны) хранится отдельно.
5. **Бюджет и обрезка:** счётчик токенов, приоритеты, пакетная обрезка с запасом (гистерезис), отчёт «что обрезано».
6. **Кеш-аналитика:** сравнение последовательных запросов, точка расхождения, блок-виновник, провайдерные подсказки.
7. **Параметры генерации:** профили сэмплера/ризонинга/стриминга, переопределения (по умолчанию выключены), запись в тело запроса.
8. **Хранение:** пресеты и версии в IndexedDB (по образцу `graph-library.js`), источник бэкапа и категория синхронизации.
9. **Плагины:** каталог, реестр, горячая замена.
10. **Интерфейс:** несколько окон; визуальный конструктор условий; основное окно — порядок.
11. **Подмена ST:** перехват кнопки/окна и сборки.

## 4. Риски

1. Сборка ST завязана на данные, которые считает ST (лорбук, формат сообщений); замена сборки требует доработки наших Ядер (решено: делаем постепенно).
2. Подавление окна ST зависит от разметки конкретной версии — нужен запасной вариант.
3. Блок ME внутри файла ST пропадает, если пользователь пересохранит пресет средствами ST (внутренний формат остаётся источником истины).
4. Кеш у провайдеров разный (у OpenAI автоматический по префиксу, у Claude — явные маркеры, у Gemini — неявный, у DeepSeek/OpenRouter/Z.AI — свои правила): «не ломать префикс» определяется отдельно для каждого.
5. Счётчик токенов приближённый — обрезка с запасом должна это учитывать.
6. Сторонние расширения, правящие промпт в ST, перестанут видеть прежний порядок (цена, принятая в PIPELINE.md).

## 7. Guided CoT (скрытая цепочка рассуждений)

**Решения владельца:**
- **Отдельный раздел «CoT» в PM, по функционалу такой же, как основной** (блоки, группы, условия, приоритеты, макросы). **Шаг = один промпт или одна группа** — на шаг отправляется только он.
- **Отправка шага:** промпт CoT находится **в основном разделе промпта** (после всей истории), то есть идёт **вместе с основным промптом** — так он работает у **всех** провайдеров (подтверждено владельцем). Отдельный раздел «только под CoT-промпт» (вне основного) работает не у всех провайдеров — такой режим объявляется как необязательный/недоступный там, где не работает (перечень уточняется на практике). Промпт шага **явно оформляется как сообщение USER**, ответу шага задаётся **лимит около 1500 токенов** (максимум).
- **Модель на шаг — выбирается** (можно разные модели/воркеры).
- **Вид в чате:** ответ шагов — **свёрнутый блок**.
- **Ризонинг сохраняется между шагами** одного CoT (и провайдерный, и текст шагов).
- **Перегенерация и свайп: режим выбирается; по умолчанию — весь CoT заново** (кнопка «только финал» — отдельно).
- **Отображение процесса при стриминге: режим «расширенный» или «малый»; по умолчанию — малый.** Малый — строка «думает: шаг 2 из 4»; расширенный — заголовки шагов и их текст по мере появления.
- **Свёрнутый блок CoT сохраняется в метаданные сообщения** (переживает перезагрузку страницы); **в историю следующих ходов по умолчанию не отправляется.**
- **Ошибка шага: повторить шаг; при повторной ошибке — абортить** всю генерацию.
- **Кеш префикса:** промпт CoT идёт после всей истории — префикс он не ломает (проверяется режимом «что рушит префикс»).
- **Запуск CoT:** **все варианты** — всегда, по триггеру (длина сообщения, ключевые слова, трекер, кулдаун и т. д.), вручную кнопкой на конкретное сообщение.
- **Включаемая функция**, по умолчанию выключена.

**Техника (наброски):** промежуточные шаги идут запросами через нашу отправку (`replyWith` для финала); результаты шагов и ризонинг провайдера подставляются в следующие шаги того же CoT и живут, пока идёт этот CoT. Шаблоны шагов — блоки/группы CoT-раздела (как в основном), тип шага — точка расширения плагинов. Провайдерные различия (`reasoning_content` DeepSeek, `thinking` Claude, `reasoning` OpenRouter/Z.AI) — провайдерный адаптер.

**Открыто по CoT:** у каких провайдеров не работает режим «отдельный раздел под CoT-промпт» (выяснится на практике, не блокирует).

## 9. Разбор образцов пресетов (получены от владельца; ST 1.18+)

Четыре файла: **AmiGO** (Module Engine, 43 промпта), **FaPuTa Test alpha** (43), **Marinara's Spaghetti Recipe v10** (80), **White Lotus 4.1.0** (91, 105 КБ). Ниже — что в них реально лежит. Это факты по файлам; выводы для дизайна отмечены «→».

### 9.1 Структура файла пресета
Один JSON из трёх частей:
1. **Параметры генерации** (плоские поля верхнего уровня): `temperature`, `top_p`, `top_k`, `top_a`, `min_p`, `frequency_penalty`, `presence_penalty`, `repetition_penalty`, `openai_max_context`, `openai_max_tokens`, `max_context_unlocked`, `seed`, `n`, `stream_openai`, `reasoning_effort` (значения в образцах: `min`, `high`), `show_thoughts`, `verbosity`, `function_calling`, `tool_call_recurse_limit`, `tool_reasoning_mode`, `enable_web_search`, `use_sysprompt`, `squash_system_messages`, `names_behavior` (`-1`/`0`/`2`), `assistant_prefill`, `assistant_impersonation`, `continue_prefill`, `continue_postfix`, `media_inlining`, `inline_image_quality`, `request_images`, `request_image_aspect_ratio`, `request_image_resolution`, `bias_preset_selected` (только имя пресета logit bias — сами смещения лежат отдельно).
2. **Служебные шаблоны-строки:** `impersonation_prompt`, `new_chat_prompt`, `new_group_chat_prompt`, `new_example_chat_prompt`, `continue_nudge_prompt`, `group_nudge_prompt`, `send_if_empty`, `wi_format` (`{0}` — место содержимого лорбука), `scenario_format`, `personality_format` (в них тоже макросы: `{{scenario}}`, `{{char}}'s personality: {{personality}}`, `{{trim}}`).
3. **Промпты:** массив `prompts` (библиотека) и массив `prompt_order` (порядок и включение).
Плюс `extensions` (у White Lotus и Marinara там `regex_scripts`).

### 9.2 Промпты (`prompts[]`)
- Поля: `identifier`, `name`, `role` (`system` / `user` / `assistant`), `content`, `system_prompt`, `marker`, `enabled`, `injection_position` (`0` / `1`), `injection_depth`, `injection_order`, `injection_trigger` (массив, во всех образцах пустой), `forbid_overrides`.
- **Маркеры (8 штук во всех файлах):** `dialogueExamples`, `chatHistory`, `worldInfoBefore`, `worldInfoAfter`, `charDescription`, `charPersonality`, `scenario`, `personaDescription` — без `content`, ST подставляет своё содержимое. У маркеров иногда бывают лишние поля (`role`, `content`, `injection_*`) — игнорируются.
- **Встроенные не-маркеры:** `main`, `nsfw`, `jailbreak`, `enhanceDefinitions` (`system_prompt: true`). **Пользователи переиспользуют их под свои цели** и переименовывают: `nsfw` = «====Character instructions====» (FaPuTa) или «| NSFW Prompt» (Marinara), `jailbreak` = «Post-History Instructions», `enhanceDefinitions` = «====Pre-Response Instructions====». → идентификатор значим для ST, имя — метка пользователя; конвертер обязан сохранять оба.
- **Собственные промпты** имеют UUID в `identifier`, `system_prompt: false`, `marker: false`.
- **`injection_position`:** `0` — «относительно»: место определяет порядок в `prompt_order`; `1` — «абсолютно»: вставка в историю чата на `injection_depth` от конца, порядок среди вставок одной глубины по `injection_order` (значения в образцах: 1, 5, 97–110, 5000). `injection_depth` у относительных бессмысленно (4 по умолчанию).
- **Роли в образцах:** есть `user` и `assistant` промпты (префиллы, «Group Nudge», «User Persona (first user message)»), а не только `system`.
- **Ключевая находка:** у собственных промптов в `prompts[]` `enabled` в образцах равен `false`, а в `prompt_order` те же промпты `enabled: true`. **Эффективное включение — в `prompt_order[].enabled`**, поле `enabled` внутри промпта — устаревший/справочный остаток. → внутренний формат хранит включение ТОЛЬКО в порядке; конвертер при импорте берёт его оттуда (проверить по реальному запросу).

### 9.3 Порядок (`prompt_order[]`)
- Два списка: `character_id: 100000` и `100001`. **`100000` — короткий стандартный порядок (11 идентификаторов: main, worldInfoBefore, charDescription, charPersonality, scenario, enhanceDefinitions, nsfw, worldInfoAfter, dialogueExamples, chatHistory, jailbreak); `100001` — полный рабочий порядок пользователя (43 / 79 / 91 идентификатора).** Вероятно, `100001` — «глобальный» порядок для всех персонажей (по памяти о ST: в режиме глобальной стратегии используется «пустышка»). **Проверить**, что ST 1.18 использует именно его.
- Каждая запись — `{ identifier, enabled }`; **один идентификатор может встречаться в порядке несколько раз** (в AmiGO `main`, `nsfw`, `jailbreak`, `enhanceDefinitions` есть как в начале блока, так и в конце) — нужно проверять, что ST делает с повтором; в образцах повтор идентификатора в одном списке не замечен, но `chatHistory`/маркеры встречаются по одному разу.
- Абсолютные (`injection_position: 1`) промпты тоже стоят в `prompt_order` и там же включаются/выключаются.

### 9.4 Что пользователи делают внутри пресетов (то, что PM должен делать штатно)
1. **XML-обёртки парными промптами:** отдельные промпты `<setting>` … `</setting>`, `<CoT>` … `</CoT>`, `<info>` … `</info>` и т. д. Их порядок держит структура вручную. → **группа с оберткой** (открывающий и закрывающий тег генерируются группой) — типовая функция.
2. **Разделители и комментарии:** пустые промпты «━+ Enable Only One Toggles», «‒+ Type», «====Main Prompt====», «✉ Read-Me» (README целиком лежит в `content` внутри `{{// ... }}`). → **разделитель / заметка** как отдельный тип блока (не уходит в промпт).
3. **Переключатели через переменные:** у Marinara и White Lotus десятки «тумблер-промптов» с `content` вида `{{setvar::tense::past tense}}{{trim}}`; другой промпт использует `{{getvar::tense}}`. Эти пресеты вручную строят **«выбери один из»**, причём взаимоисключение держит только подпись «Enable only one». → **группа «выбор одного» (radio)** с одной активной опцией и значением, которое доступно как переменная; условие и шаблон видят выбранное. Это прямой ответ на «динамические промпты» и «визуальный конструктор».
4. **«Тумблеры-стили» и порядок:** сотни строк текста в `content`, единицы `injection_order` для порядка внутри одной глубины.
5. **Префиллы и наджи:** роли `assistant` и `user` с текстом, включаемые вручную (в групповом чате и т. д.).
6. **Тонкая работа с концом чата:** `<last_message>` … `</last_message>` абсолютными промптами глубин 0/1 с `injection_order` 99/101 — оборачивание последнего сообщения. → PM должен уметь обернуть последнее сообщение / блок сообщений в парные теги (в модели «история = начало + конец» это одна из привязок).
7. **Наши макросы и инструменты уже используются:** AmiGO содержит `{{rp-time_year}}`, `{{rp-time_month}}`, `{{rp-time_day}}`, `{{rp-time_time}}`, `{{rp-time_period}}` (макросы Модуля «Время») и инструкции про Notebook и TunnelVision-инструменты.

### 9.5 Макросы, реально встреченные в промптах и служебных шаблонах
`{{user}}` (195), `{{char}}` (66), `{{trim}}` (94), `{{// … }}` многострочные комментарии (46, встречаются и в служебных шаблонах: `{{//This is prompt…}}`), `{{setvar::имя::значение}}` (46; значение может быть длинным текстом со знаками препинания), `{{getvar::имя}}` (13), `{{random::…}}` (10, White Lotus), `{{scenario}}`, `{{personality}}`, `{{persona}}`, `{{group}}`, `{{summary}}`, `{{lastChatMessage}}` (не `lastMessage`!), `{{rp-time_*}}` (наши). **Устаревшие угловые:** `<USER>` и `<BOT>` (Marinara, внутри значений `setvar`, где ST подставит имена позже). Есть нестандартные написания вроде `{{//Toggle …}}` (комментарий без пробела после `//`). → перечень раздела 8 нужно дополнить: `lastChatMessage`, угловые `<USER>`/`<BOT>`; порядок раскрытия вложенных макросов внутри значений `setvar`.

### 9.6 Расширения и связанные данные
- **`extensions.regex_scripts`** (White Lotus: 4 скрипта; Marinara: пустой список): предустановленные regex-скрипты пресета. Поля: `scriptName`, `findRegex`, `replaceString`, `placement` (`[2]`), `disabled`, `markdownOnly`, `promptOnly` (`true` = менять только исходящий промпт), `runOnEdit`, `substituteRegex`, `trimStrings`, `minDepth`/`maxDepth`. → **если сборка наша, скрипты с `promptOnly` и нужным `placement` должны применяться нами**, иначе пресет поведёт себя иначе, чем в ST. Открытый вопрос, входит ли это в первую версию.
- **Настройки подключения внутри пресета** (White Lotus): `chat_completion_source` (`nanogpt`), модели всех провайдеров (`openai_model`, `claude_model`, `openrouter_model`, `deepseek_model`, `zai_model`, `custom_url`, `reverse_proxy`, `proxy_password` и др.), провайдерные параметры OpenRouter (`openrouter_providers`, `_allow_fallbacks`, `_middleout`). В остальных образцах их нет. Пароль в образце пуст. → **PM их не применяет (решение владельца), но при импорте/экспорте сохраняет как непрозрачные поля** и при экспорте чистит секретные (`proxy_password` и т. п.) — уточнить.
- **`bias_preset_selected`** — только ссылка по имени; сами смещения логитов в файле пресета не лежат (отдельный объект ST).

### 9.7 Выводы для плана
1. **Формат ST — плоский и хорошо определён**, конвертер ST ↔ ME без потерь реален; главная тонкость — «эффективное включение в порядке», повтор идентификаторов и переиспользование встроенных идентификаторов.
2. **Обязательно поддержать типы блоков:** маркер, текстовый (роль), разделитель/заметка, группа с обёрткой, «выбор одного» с переменной, абсолютная вставка на глубину относительно конца, обёртка последнего сообщения.

5. **Токенный бюджет:** максимальный контекст в образцах 25 000 – 1 000 000, `max_context_unlocked: false`. Нужны и «разблокированный контекст», и ограничение на ответ (`openai_max_tokens` 2000–8192).
6. **Тестовые данные:** файлы Marinara и White Lotus — чужие публичные пресеты; в репозиторий их целиком класть не стоит (авторские права) — **делаем синтетические фикстуры с той же структурой** (тексты сокращены до заглушек), плюс полные файлы владельца оставляем вне репозитория для ручной проверки. ## 10. Решения владельца по разбору образцов

1. **Regex:** свой простой язык-обёртка поверх regex (проще для пользователя, покрывает типовые задачи), плюс **импорт обычных regex-скриптов ST** как есть. Детали языка — отдельное обсуждение.
2. **`{{random}}`:** предупреждаем, что он ломает кеш префикса, и даём переключатель «заморозить» (значение фиксируется, недетерминизм отключается).
3. **Группа «выбор одного» (radio):** выбранное значение доступно как переменная для шаблонов и условий.
4. **Парные промпты-обёртки** (`<x>` … `</x>`) при импорте ST-пресета **склеиваются в группу с обёрткой** автоматически.
5. **Секреты** (`proxy_password` и подобные) **чистятся** при любом экспорте.
6. **Поля подключения** (модели, `custom_url`, `reverse_proxy`) хранятся непрозрачно и не применяются.
7. **Фикстуры:** чужие пресеты (Marinara, White Lotus, FaPuTa) в репозиторий и тесты **не используем**. Эталон — пресет владельца **AmiGO «Polished Version — Module Engine»**; остальные тестовые данные — синтетические.
8. **Логи запросов:** владелец предлагает логи OpenRouter вместо копий сетевых запросов (см. ответ в чате о том, что в них нужно).

## 11. Разбор реального запроса (лог OpenRouter, пресет AmiGO Polished, ST 1.18)

Получено от владельца: массив `messages` одного запроса (без параметров и `usage`). Персонаж — Владилена Милизе, персона «Sasha», рабочий Notebook и граф памяти. Что видно:

### 11.1 Как ST собрал сообщения (порядок = порядок в пресете)
1. **Каждый промпт пресета — отдельное `system`-сообщение**, без склейки (`squash_system_messages` выключен). Парные теги `<settings>` … `</settings>` — тоже отдельные сообщения.
2. **Пустые обёртки уходят в запрос.** `<char instructions>` и `</char instructions>` идут подряд без содержимого между ними. → группа с обёрткой **не должна отправляться, если внутри пусто** (экономия токенов и чище префикс). Это надо сделать настройкой группы, по умолчанию включённой.
3. **Блок `<info>`** содержит карточку персонажа (описание, личность в XML) и отдельным сообщением — личность и персону («18 yo Male»). Затем огромный `system`-блок лорбука (~ 50 КБ текста) одним сообщением.
4. **`[Start a new Chat]`** — `new_chat_prompt` пресета, стоит между промптами и историей.
5. **Историю ST отдаёт так:** `assistant` (приветствие, оно же первое сообщение), `user`, затем **`assistant` с `tool_calls` и два `tool`-сообщения**, потом промпты «после истории» (`<need guidelines>`, `<goal guidelines>`, `<logic>`, `<narration>`, `<CoT>`).
6. У assistant-сообщений есть **`"reasoning_content": ""`** — ST добавляет поле для провайдеров с ризонингом даже пустым.

### 11.2 Что вставили модули ME (сейчас это «сырые» вставки)
- **Граф памяти:** `assistant`-сообщение «Long-term memory — relevant connections: …» **в самом начале истории, до приветствия**. Текст включает рёбра (`A -[backbone]-> B (noise)`) и полные карточки узлов.
- **Notebook:** `assistant`-сообщение «[Private notebook — …]» сразу за ним, до приветствия.
- Оба модуля кладут вставки в начало `chat` через `chat.unshift` (так и описано в разделе 1а). В реальном запросе это единственное, что стоит между `[Start a new Chat]` и историей, и оно **меняется каждый ход** — ключевая причина, по которой кеш префикса не работает. См. п. 11.5.

### 11.3 Проблемы, видимые прямо в запросе (что PM должен сделать лучше)
1. **Макросы времени не подставлены.** В `<CoT>` осталась буква в букву строка `{{rp-time_year}} {{rp-time_month}} {{rp-time_day}} {{rp-time_time}} ({{rp-time_period}})`. В коде макросы регистрирует `cores/macros` через `stMacros.register` с закешированными значениями. Причина не определена (макрос не зарегистрирован в этом чате, гонка с кешем или иное имя). **Нужно отдельно проверить**; в PM собственный сервис макросов решает это структурно (см. раздел 2).
2. **Дублирование содержимого.** Один и тот же текст присутствует и в блоке `<info>` (лорбук), и во вставке графа: `<handler>`, `<legion_war>`, `<giadian_empire>`, `<wald>` (полностью). Нужен **дедуп идентичных блоков между источниками** с показом в превью: «блок X уже есть в Y, пропущен».
3. **Поломанный макрос в тексте карточки:** `</{{char}'s abilities>` (незакрытая `}`). Сервис макросов обязан терпеть невалидную запись и не ломаться.
4. **Служебная разметка модуля времени попала модели:** в приветствии стоят `[]('SY2148MAY22')` и `[]('PARAON')`. Похоже на скрытые маркеры, которые не должны уходить модели. → PM должен уметь **удалять маркеры** при сборке (правило по шаблону: «убрать из отправляемого промпта»). Нужно подтвердить, что это действительно случайно.
5. **Пометки `(noise)` в тексте графа** — служебные метки шумовых узлов, которые тоже уходят модели. Владелец решает, нужны ли они.
6. **Огромный статический блок в середине промпта.** Весь лорбук идёт одним сообщением до истории; всё, что после него, зависит от его неизменности. Если лорбук хоть немного меняется, префикс ломается, начиная отсюда.

### 11.4 Вызовы инструментов (tool calling) — новое требование
- В истории есть цепочка **`assistant` + `tool_calls` (2 вызова Notebook) → 2 сообщения `tool`**, привязанные по `tool_call_id`. ST хранит её как часть истории чата.
- Следствия для PM: (а) **пары «вызов + результат» неразделимы** — нельзя обрезать или разорвать их при обрезке по бюджету; (б) вставки «после истории» стоят **после** цепочки, значит «конец истории» считается с учётом этих элементов; (в) `reasoning_content` на assistant-сообщениях нужно сохранять как есть; (г) саму рекурсию инструментов ведёт ST, PM отдаёт только базовую сборку (**решение владельца нужно**: не ломает ли нам это Guided CoT, если шаг CoT сам делает вызовы).

### 11.5 Что это даёт для кеша префикса
Порядок сообщений по стабильности сейчас такой: стабильный текст пресета (сотни токенов) → **огромный лорбук** → **`[Start a new Chat]`** → **граф памяти + Notebook (меняются каждый ход)** → история → **длинные инструкции пресета после истории (снова стабильные)**. Всё после графа кеш не использует, а хвост с ~5000 токенов инструкций стабилен, но сидит **после** изменяющейся части. **Идеальный порядок для кеша:** весь стабильный текст, включая «guidelines/logic/narration/CoT», должен стоять **до** изменяющихся вставок, либо изменяющиеся вставки должны стоять в самом конце. Именно этот вывод PM должен показывать пользователю в режиме кеша префикса («если перенести блок X выше, кеш вырастет на N токенов»).

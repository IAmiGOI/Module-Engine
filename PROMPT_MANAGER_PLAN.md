# План: собственный Prompt Manager движка (PM)

Статус: **обсуждение и подготовка, кода нет.** Документ живой: ответы владельца — в разделе 0, открытые вопросы — в разделе 2. Ничего из раздела 3 («Набросок архитектуры») не решено окончательно, это рабочий черновик под правку.

Правила репозитория действуют полностью: комментарии и документы на русском, интерфейс на английском, файлы ≤ 300 строк (никаких файлов-«божков»), решения — в ROADMAP.md, полные названия тестов, работа маленькими шагами.

## 0. Решения владельца (не менять без согласования)

### Цель
- Свой менеджер промптов поверх ST: **лучше, быстрее, полностью совместимый с любым модулем движка**, работает с промптами и пресетами самого ST, умеет экспорт и импорт.
- Что не устраивает в менеджере ST: статичное дерево промптов; нет групп; **нет интеграции с ME** — размещение текущих инжектов модулей непрозрачно и не редактируется; старый интерфейс; мало функций; нет динамических промптов; нет промптов по триггеру; расположение через `@x` неинтуитивно визуально.
- «Быстрее» — и скорость редактора, и скорость сборки промпта.

### Границы первой итерации
- **Только Chat Completion.** Text Completion (Kobold, textgen, NovelAI) — позже.
- **Групповые чаты не поддерживаются:** при открытом групповом чате PM показывает предупреждение и выключается (работает штатная сборка ST). «Потом допишем».
- Если API переключён на Text Completion — тоже предупреждение и выключение.
- Ориентир по версии ST — **1.18+**. Образцов внешнего вида нет («нет» на вопрос об ориентирах).

### Включение и подмена ST
- PM **заменяет** сборку ST, когда включён; **по умолчанию включён**. Пассивного режима «только смотреть» нет.
- Штатный менеджер ST подавляется, пока включён наш; кнопка открытия штатного окна заменена на открытие нашего. **Открывается только с кнопки Prompt Manager ST** (других пунктов не нужно).
- Расхождение нашей сборки с ST на тех же входных данных **допустимо** там, где мы улучшаем.
- **Без запасного варианта при подавлении окна ST:** если не удалось подавить штатный менеджер, это **явная ошибка** (видимая пользователю), а не молчаливое сосуществование двух окон.
- **Ошибка плагина:** плагин **выключается**, пользователь предупреждён, сборка идёт дальше без него.
- **Не удалось подавить окно ST → PM выключается, пользователь предупреждён** (штатная сборка ST продолжает работать; чат не блокируется).

### Данные для сборки
- Всё берётся **через наши Ядра, с их доработкой по ходу** (не напрямую из `context` ST).
- Лорбук: **наше Ядро лорбука со СВОИМ движком активации** — пишется постепенно, **результат активации ST не используется** (решение владельца: «сами всё делаем, ST читать не надо»); **либо граф** (граф — замена WI, стоит рядом, основной, но не единственный вариант). *(Формулировка владельца была «наше ядро плача» — прочитано как «ядро лорбука».)*
- **Подстановка макросов — свой сервис** (наши макросы + макросы ST по синтаксису ST; вызова ST-ной подстановки не будет). **Счётчик токенов — свой, быстрый, приближённый.**
- Макросы — **и наши, и макросы ST**.
- Подключения (профили ST: модель, ключ, эндпоинт) PM **не трогает**.

### Модель промптов
- **Группы промптов** — с общей логикой или просто по смыслу.
- **Динамические промпты и триггеры:** «если X → вставить A, если Y → вставить B» и «если X → вставить». Условия: по **трекеру**, по **классификатору** (добавим позже), по **кулдауну**, по **ключевым словам**, по **длине сообщения** и т. д. — набор наращивается плагинами.
- **Интерфейс логики — визуальный конструктор, ноль кода, очень наглядно.**
- **Расположение:** `@x` остаётся для чата; **историю чата делим на начало и конец, блоки размещаются внутри неё визуально, с иерархией относительно друг друга.** Деление истории — **всеми способами на выбор** (по числу сообщений, по токенам, ручной границей); блок можно привязать к началу, к концу или относительно конкретного сообщения.
- **Группы промптов — дерево** (вложенные), общее условие / общий приоритет обрезки / общий бюджет токенов группы — **всё это на выбор** (включается по необходимости).
- **Кулдаун и «время жизни» срабатывания — «дать на выбор»:** в ходах, в сообщениях или по времени; блок остаётся до конца сцены или живёт N ходов (sticky) — выбирается в настройках триггера.
- **Инжекты модулей:** старый путь (`chat.unshift` из модулей) убирается; вводится **новый контракт публикации чат-инжекта**; размещение инжектов модулей видно и редактируется в PM как обычные блоки.

### Плагины
- **Максимум логики — плагины, с горячей заменой** (без перезагрузки страницы), чтобы менеджер легко наращивался.
- Плагины берутся из **каталога** (пока дефолтного, встроенного). Читать они могут **всё, что может читать сам PM**.

### Обрезка и токены
- **Приоритет обрезки:** PM **сам определяет приоритет блоков**; пользователь может переопределить.
- **Визуализация:** переключаемые UI-режимы, показывающие, что обрезано.
- **Сжатия моделью пока нет.**
- **Авто-режим не должен резать историю каждый ход** (это убивает префикс). Вместо этого: при упоре в лимит **немного поднять лимит** (запас), чтобы префикс не обрезался, а блок/пачку сообщений **убрать в подходящий момент одним куском** (пакетная обрезка с запасом — «гистерезис»). Автор идеи считает это дешевле.
- Токены — **быстрый счётчик** (приближённый, локальный).

### Кеш префикса (ОЧЕНЬ важен)
- Провайдеры по приоритету: **OpenRouter → DeepSeek → Gemini → Z.AI → Claude → OpenAI** (приоритет убывает).
- **Режим «что рушит префикс»:** сравнение последних запросов, первая точка расхождения и блок-виновник — «достаточно».
- **Сам PM не делает резких движений, если пользователь их не назначил; он прозрачен.** Внутренние процессы PM оптимизируются так, чтобы не портить префикс сами (модули не в счёт).

### Параметры генерации (расширение объёма)
- В PM входит **управление сэмплером, ризонингом, стримингом и «всем, что есть в ST»** для Chat Completion. **Хранятся в пресете.**
- **Переопределения** на персонажа / чат / модель — **да**, отдельная логика определения, **по умолчанию отключена**.
- **Стриминг нужно управлять**, а не только передавать флаг.
- **Все параметры ST для Chat Completion делаем** (сэмплер целиком, ризонинг, стриминг, провайдерные особенности) — без урезания первой версии.

### Формат, экспорт, синхронизация
- **Внутри ME и для синхронизации — свой формат.** **Экспорт — в формат ST** (с конвертерами в обе стороны). Данные ME при экспорте упаковываются **в файле пресета** так, что их достаёт другой клиент ME; чистый ST их игнорирует (ME → простой ST данные не переносятся, и так задумано).
- **Полный экспорт/импорт, обмен файлами.** В файл идёт **пресет + всё, что к нему относится (слоты модулей, плагины, настройки), но не старые версии.**
- **Авто-подготовка всех существующих пресетов ST** при первом запуске: внутренние копии, оригиналы в файлах ST не трогаются до экспорта.
- **Синхронизация** — уже решена существующим синхронизатором (категория как у библиотеки графов, конфликты — его политикой).
- **Откат и история версий — да; хранятся в БД (IndexedDB).**
- **Журнал отправленных запросов** (собранный промпт по блокам, токены, что обрезано; сравнение запросов) — да, «достаточно» в объёме режима префикса.

### Интерфейс
- **Своё окно, несколько окон** (редактор порядка, предпросмотр «что уйдёт модели» с токенами по блокам и источником каждого блока, кеш префикса, журнал…). **Основное окно — порядок промптов.**
- Предпросмотр «что уйдёт модели» в реальном времени — «да, со всем».

### Guided CoT (новое требование)
- **Скрытые «guided CoT» — полноценные, не как в ST** (штатный ST даёт лишь одноразовую вставку размышления). **С автосохранением ризонинга в рамках одного CoT.** **Включаемая функция** (по умолчанию выключена). Подробности и вопросы — раздел 7.

### Материалы
- Владелец пришлёт **WI** (лорбук) после завершения этой части и **свои пресеты и захваченные запросы** для тестов равенства с ST.
- Разведку кода перед этапом 1 разрешено делать «всё, что хочешь» (только чтение и запись в этот документ).

### Порядок работы
- **Постепенно, максимум распределения нагрузки, никаких файлов-«божков».**

### 1а. Разведка кода (что реально устроено сейчас)

- **Порядок генерации в движке:** ST открывает прогон (`GENERATION_STARTED`) → **перехватчик** `onIntercept({chat, contextSize, abort, type})` в [cores/generation/index.js](cores/generation/index.js): сначала пайплайн `generation.prepare` (свежее состояние, выходы отбрасываются), потом `generation.beforeSend` (вклады) → ST сам собирает промпт (лорбук, персонаж, история, штатный Prompt Manager) → **обёртка `fetch`** на пяти эндпоинтах: `onSend({endpoint, payload})` → пайплайн `generation.payload` (`fold` над телом) → отправка. Решение отправки возвращает `{payload}` / `{cancel, reason}` / `{replyWith}` ([services/st-generation.js](services/st-generation.js)); `replyWith` — ответить самим, к бэкенду не ходить.
- **Следствие для PM:** собирать финальные `messages` естественнее всего в `generation.payload` (тело уже содержит всё, что ST посчитал), либо раньше, в `beforeSend`, если PM хочет владеть и данными. Для Chat Completion в теле лежат и `messages`, и параметры (`temperature`, `stream`, …) — их PM тоже может переписать. Стриминг читает ST из ответа `fetch`; чтобы им управлять, ответ придётся оборачивать.
- **Как модули вкладываются сейчас (то, что PM должен заменить контрактом):** это сырые правки копии истории `chat`: [summary](cores/summary/index.js) (`unshift` + обрезка старых сообщений), [граф памяти](cores/memory-graph/index.js) (`unshift` сообщений `Memory` и `Plot core`), [map-narration](cores/map-narration/index.js) (`splice` на глубину `INJECTION_DEPTH`), модули [notebook](modules/notebook/index.js), [tools](modules/tools/notebook.js) и `secrets` (`splice` по вычисленной позиции), [time](modules/time/index.js) (`unshift` сообщения `System`). Все — `{ is_user: false, is_system: true, name: 'X', mes }`. Именно эти вызовы переезжают на новый контракт публикации чат-инжекта (у каждого есть имя, позиция и признак «стабилен ли для префикса»).
- **Лорбук:** [Ядро лорбука](cores/lorebook/index.js) сегодня **не активирует** записи само — оно читает то, что активировал ST (`st.worldInfoActivated` → `lorebook.lastActivated`), плюс `lorebook.find/get` для записей. **Решение владельца: пишем свой движок активации** (ключи и вторичные ключи, рекурсия, вероятности, sticky/cooldown/delay, порядок и бюджет, группы, глубина сканирования и т. д.), результат ST не используем. Это отдельная крупная работа внутри Ядра лорбука (свой подплан). Граф памяти — параллельный источник вместо лорбука (уже вкладывается сам).
- **Макросы:** [Ядро макросов](cores/macros/index.js) сегодня **регистрирует наши макросы В ST** (`stMacros.register`); подстановку `{{char}}`, `{{user}}` и остальных делает сам ST при своей сборке. **Решение: свой сервис подстановки** — наши макросы + набор макросов ST по их синтаксису (перечень и точное поведение сверяем с пресетами и запросами, которые пришлёт владелец), без вызова ST.
- **Токены:** в репозитории **нет** счётчика токенов (общего сервиса). **Пишем свой** быстрый локальный счётчик (приближённый).
- **Пресеты ST:** чтение/запись через [services/st-user-data.js](services/st-user-data.js) (`presets/openai/<имя>.json` — уже в синхронизации); `stPreset.current` отдаёт текущий выбор ([services/st-preset.js](services/st-preset.js)). Нужно подтвердить по реальным файлам (пришлёт владелец) форму `prompts` / `prompt_order` в 1.18+.
- **Пайплайны:** [Ядро пайплайнов](cores/pipeline/index.js) — DAG этапов с зависимостями (`needs`), таймаутом, `fallbacks`, `onExhausted` (`abort` / `flag`). Этап исполняется под личностью владельца. Реестр этапов и есть «Блок» (обнаружение участников без правок в PM) — совпадает с замыслом PM из CORES.md.

## 3. Набросок архитектуры (ЧЕРНОВИК, не решение)

Слои, каждый — свои маленькие файлы:

1. **Формат и конвертеры** (`libraries/core/pm-*.js`, чистые функции): внутренний формат пресета PM; конвертеры ST ↔ ME без потерь для блока ME; версии формата; квантование не нужно.
2. **Ядро сборки** (`cores/prompt-manager/`): принимает контекст (персонаж, персона, лорбук/граф, история, вклады модулей, макросы) и пресет → упорядоченный список блоков → сообщения. Чистая сборка отдельно от ввода-вывода.
3. **Слоты и вклады модулей:** реестр вкладов (контракт публикации чат-инжекта), размещение задаёт пользователь в PM.
4. **Условия и триггеры:** движок правил с точками расширения под плагины; чистые вычисления, состояние (кулдауны) хранится отдельно.
5. **Бюджет и обрезка:** счётчик токенов, приоритеты, пакетная обрезка с запасом (гистерезис), отчёт «что обрезано».
6. **Кеш-аналитика:** сравнение последовательных запросов, точка расхождения, блок-виновник, провайдерные подсказки.
7. **Параметры генерации:** профили сэмплера/ризонинга/стриминга, переопределения (по умолчанию выключены), запись в тело запроса.
8. **Хранение:** пресеты и версии в IndexedDB (по образцу `graph-library.js`), источник бэкапа и категория синхронизации.
9. **Плагины:** каталог, реестр, горячая замена.
10. **Интерфейс:** несколько окон; визуальный конструктор условий; основное окно — порядок.

## 4. Риски

1. Сборка ST завязана на данные, которые считает ST (лорбук, формат сообщений); замена сборки требует доработки наших Ядер (решено: делаем постепенно).

5. Счётчик токенов приближённый — обрезка с запасом должна это учитывать.
6. Сторонние расширения, правящие промпт в ST, перестанут видеть прежний порядок (цена, принятая в PIPELINE.md).

## 7. Guided CoT (скрытая цепочка рассуждений)

**Решения владельца:**
- **Отдельный раздел «CoT» в PM, по функционалу такой же, как основной** (блоки, группы, условия, приоритеты, макросы). **Шаг = один промпт или одна группа** — на шаг отправляется только он.
- **Отправка шага:** промпт CoT находится **в основном разделе промпта** (после всей истории), то есть идёт **вместе с основным промптом** — так он работает у **всех** провайдеров (подтверждено владельцем). Отдельный раздел «только под CoT-промпт» (вне основного) работает не у всех провайдеров — такой режим объявляется как необязательный/недоступный там, где не работает (перечень уточняется на практике). Промпт шага **явно оформляется как сообщение USER**, ответу шага задаётся **лимит около 1500 токенов** (максимум).
- **Модель на шаг — выбирается** (можно разные модели/воркеры).
- **Вид в чате:** ответ шагов — **свёрнутый блок**.
- **Ризонинг сохраняется между шагами** одного CoT (и провайдерный, и текст шагов).
- **Перегенерация и свайп: режим выбирается; по умолчанию — весь CoT заново** (кнопка «только финал» — отдельно).
- **Отображение процесса при стриминге: режим «расширенный» или «малый»; по умолчанию — малый.** Малый — строка «думает: шаг 2 из 4»; расширенный — заголовки шагов и их текст по мере появления.
- **Свёрнутый блок CoT сохраняется в метаданные сообщения** (переживает перезагрузку страницы); **в историю следующих ходов по умолчанию не отправляется.**
- **Ошибка шага: повторить шаг; при повторной ошибке — абортить** всю генерацию.
- **Кеш префикса:** промпт CoT идёт после всей истории — префикс он не ломает (проверяется режимом «что рушит префикс»).
- **Запуск CoT:** **все варианты** — всегда, по триггеру (длина сообщения, ключевые слова, трекер, кулдаун и т. д.), вручную кнопкой на конкретное сообщение.
- **Включаемая функция**, по умолчанию выключена.

**Техника (наброски):** промежуточные шаги идут запросами через нашу отправку (`replyWith` для финала); результаты шагов и ризонинг провайдера подставляются в следующие шаги того же CoT и живут, пока идёт этот CoT. Шаблоны шагов — блоки/группы CoT-раздела (как в основном), тип шага — точка расширения плагинов. Провайдерные различия (`reasoning_content` DeepSeek, `thinking` Claude, `reasoning` OpenRouter/Z.AI) — провайдерный адаптер.

**Открыто по CoT:** у каких провайдеров не работает режим «отдельный раздел под CoT-промпт» (выяснится на практике, не блокирует).

# Граф памяти (рабочее название) — проектирование

Новая система памяти, ПАРАЛЛЕЛЬНАЯ BasicSummary и Notebook, а не замена ни
одной из них. Идея — mind-map (как в Obsidian): узлы (ноды) с текстовым
содержимым, соединённые типизированными рёбрами, один центральный узел плюс
остальная сеть вокруг него.

Статус: **Phase 1 реализован и подключён к движку** (`cores/memory-graph/index.js`,
`libraries/core/embedding.js`, `services/embedding.js`, wiring в
`harness/engine-wiring.js`) — физика регионов, каскад размещения, decay,
локальный эмбединг, **включая импорт Lorebook при бутстрапе**
(`bootstrapFromLorebook()` — оказалось не отдельной "Phase 1b", а прямым
переиспользованием того же `placeNewNode()`, что и у нод от SideCar, см.
секцию ниже). Живьём проверено: движок собирается и все контракты
регистрируются (`memoryGraph.*`, `embedding.*`), модель реально грузится и
считает смысловые эмбединги на настоящем WI; сценарные тесты движка
(`tests/memory-graph-orchestration.test.js`) проверяют `checkAndPlace()` и
`bootstrapFromLorebook()` целиком, через реальный движок+Гейты. **Бутстрап
из живого Lorebook проверен в браузерном харнессе end-to-end** (реальная
книга харнесса → 2 ноды, первая — protected-центр региона, реальные
384-мерные эмбединги через настоящую загрузку модели).

**Переполнение региона — ВСЕ ТРИ механизма реализованы**
(`enforceRegionCapacity()` в `cores/memory-graph/index.js` — три рубежа по
порядку, каждый следующий срабатывает только если предыдущий не спас
место): **объединение дублей** (на каждой вставке, до переполнения вообще)
→ **реконсолидация кластера слабых** (при переполнении, ПРЕДПОЧИТАЕТСЯ —
решено с пользователем явно) → **decay-вытеснение** (последний рубеж, если
реконсолидировать нечего).

**Decay-вытеснение** (`pickEvictionCandidate()`/`removeNodeFromGraph()`):
- **Ёмкость закрыта**: 23 узла на регион (буквально по изначальной формуле
  1 центр + 2 под-центра + до 10 каждый — арифметика "12 vs 23" решена в
  пользу 23, `DEFAULT_SETTINGS.maxNodesPerRegion`).
- **Триггер**: СРАЗУ при вставке сверх лимита, внутри `attachToRegion()` —
  не отдельный периодический sweep.
- Узел с наименьшим весом (`computeNodeWeight()`) удаляется целиком (не
  переносится, не сжимается) — теперь ТОЛЬКО когда реконсолидировать
  нечего (см. ниже), в первом проходе это было единственным механизмом.
  Защищённые узлы (`protectedNode`, вес `Infinity`) никогда не вытесняются;
  если регион ЦЕЛИКОМ из защищённых — вытеснять нечего, лимит временно
  превышается, задокументированный крайний случай.
- Покрыто: 4 юнит-теста на `pickEvictionCandidate()` (вытеснение слабейшего,
  null когда все защищены, tie-break по возрасту, decay переворачивает
  порядок со временем) + 1 сценарный тест (маленький регион с потолком 2 и
  всего 2 незащищёнными кандидатами — ниже `reconsolidationMinCluster`,
  падает на обычное вытеснение) — все проверены bypass-then-restore. Живой
  смоук-тест в харнессе: движок грузится с `maxNodesPerRegion: 23` без
  ошибок.

**Объединение почти-дубликатов**
(`detectMergeCandidate()`/`findMergeCandidate()`/`sweepMergeQueue()`/
`foldNodesInGraph()` в `cores/memory-graph/index.js` — `mergeNodesInGraph`
обобщена до `foldNodesInGraph(nodeIds, ...)`, N>=2, общая теперь и для
слияния пары, и для реконсолидации кластера, см. ниже):
- **Отбор — двухступенчатый, на КАЖДОЙ вставке в регион** (решено с
  пользователем: "проверяем математикой, подозреваемых — на эмбединг"):
  дешёвый `jaccardOverlap()` по словам (порог 0.3, эвристика "на
  усмотрение") отсеивает явно непохожее, затем косинус эмбедингов
  (порог 0.92 — по живым числам из этого документа: связанные записи
  реального WI давали ~0.86, порог должен быть заметно выше) подтверждает
  реального "подозреваемого". Дороже, чем decay-вытеснение, но всё ещё без
  единого вызова модели на этом шаге — эмбединги уже посчитаны заранее.
- **Найденная пара НЕ сливается сразу** — уходит в СВОЮ очередь
  (`mergeQueue`, отдельно от накопителя `staging`). Пользователь явно
  отклонил переиспользование чисел накопителя (batch=5/+20 ходов) —
  своя, чисто временна́я логика: `mergeQueueMaxTurns` (по правке
  пользователя — "ходов 7-8" — взято 8) ходов с момента постановки в
  очередь, без гонки "батч ИЛИ таймаут".
- **Созревшая пара → один SideCar-вызов НА ПАРУ** (не групповой батч, как
  у `escalateToSideCar` — двум конкретным текстам нужен настоящий
  пересказ, не ярлык). Ответ `{label, content, importance}` — сливает;
  `{"distinct": true}` — SideCar не согласен, оба узла остаются как были,
  запись в очереди просто забывается (не повторяет попытку).
- **Слияние** (`foldNodesInGraph`): один новый узел с эмбедингом,
  пересчитанным по объединённому content; `protectedNode`/более старый
  `createdTurn` наследуются от ЛЮБОГО из оригиналов (слияние не может
  СНИЗИТЬ защиту или "омолодить" узел); рёбра ДРУГИХ узлов, указывавшие на
  любой из оригиналов, ПЕРЕАДРЕСУЮТСЯ на слитый узел (не обрываются — это
  объединение, не вытеснение), с дедупликацией параллельных рёбер после
  редиректа.
- Покрыто: 8 юнит-тестов (`jaccardOverlap`, `findMergeCandidate` — включая
  тест, где кандидат с БОЛЬШИМ косинусом отвергается словарным фильтром,
  доказывая, что фильтр реально что-то отсеивает, а не просто проигрывает
  по сходству) + 4 сценарных теста (очередь не сливает сразу; не трогает
  пару раньше срока; сливает после `mergeQueueMaxTurns`, сохраняя
  protected; "distinct" оставляет оба узла; ребро ТРЕТЬЕГО узла
  переадресуется на слитый, а не пропадает) — все проверены
  bypass-then-restore, включая один случай, где первая версия теста не
  реально пиновала поведение (кандидат "без общих слов" проигрывал по
  сходству и без фильтра — тест переписан с числами, где он выигрывал бы
  без фильтра). Живой смоук-тест в харнессе: движок грузится с новыми
  настройками (`mergeSimilarityThreshold: 0.92`, `mergeQueueMaxTurns: 8`)
  без ошибок, очередь пуста на несвязанных существующих узлах харнесса.

**Реконсолидация мелких записей — третий, последний механизм переполнения
реализован** (`tryQueueReconsolidation()`/`askSideCarForReconsolidation()`/
`sweepReconsolidationQueue()` в `cores/memory-graph/index.js`):
- **Предпочитается вытеснению** (решено с пользователем явно: "перед
  вытеснением, при переполнении") — сохраняет БОЛЬШЕ информации (сжимает
  кластер в один узел), чем вытеснение (теряет узел целиком). При
  переполнении `enforceRegionCapacity()` сначала пробует поставить кластер
  в очередь; удаётся — вытеснение в этот ход не происходит вовсе, регион
  временно превышает лимит (тот же принцип, что уже принят для "регион
  целиком из защищённых").
- **Кластер = 3 СЛАБЕЙШИХ незащищённых узла** региона по `computeNodeWeight()`
  (`reconsolidationMinCluster`, решено с пользователем: "3, как у batch
  накопителя" — то же число одновременно и порог "стоит ли вообще сжимать"
  1-2 узла ради вызова модели, и размер самого кластера). Уже стоящие в
  очереди узлы исключаются из отбора — не дублируем запись.
- **Через СВОЮ очередь, СВОИ числа** (решено явно, тот же принцип, что у
  объединения дублей): `reconsolidationQueueMaxTurns` (8) ходов с момента
  постановки, не блокирует текущую вставку.
- **Созревший кластер → один SideCar-вызов НА КЛАСТЕР** (сжатие уже само по
  себе батч-операция над N узлами разом, в духе фолда BasicSummary, но
  локально внутри региона). Ответ `{label, content, importance}` — сжимает
  через ОБЩУЮ с объединением дублей `foldNodesInGraph()` (обобщена с пары
  на произвольное N>=2 — рефакторинг проверен bypass-then-restore заново
  после обобщения, редирект рёбер третьего узла всё ещё ловится).
- Покрыто: 3 сценарных теста (переполнение ставит в очередь, а не вытесняет
  сразу — с точным набором из 3 ожидаемых id по стабильной сортировке при
  равных весах; sweep реально сжимает кластер в один узел, регион
  уменьшается на 2; при менее чем 3 подходящих кандидатах падает на
  обычное вытеснение, настройка `maxNodesPerRegion` установлена ДО
  `load()`/бутстрапа через `memoryGraph.configure`) — все проверены
  bypass-then-restore. Живой смоук-тест в харнессе: движок грузится с
  новыми настройками (`reconsolidationMinCluster: 3`,
  `reconsolidationQueueMaxTurns: 8`) без ошибок.

**Phase 2 — маяки+маршрут в промпт — первый проход реализован**
(`pickBeacons()`/`scoreBeaconCandidate()`/`buildBeaconRoute()`/
`findShortestPath()`/`renderMemoryPrompt()`/`injectIntoPrompt()` в
`cores/memory-graph/index.js`, этап `generation.beforeSend`):
- **Единый "центр графа"** (постоянный якорь ГГ, из раннего наброска
  дизайна) в реализации так и не появился — только 15 центров регионов и
  обычные рёбра `mentions`. Решено с пользователем: концептуально центр
  графа — ГГ (протагонист), но в ЭТОМ проходе маршрут строится ТОЛЬКО
  между маяками (беcз привязки к ГГ) — открытый пункт на будущее, не
  блокирует Phase 2.
- **3 маяка на ход** (`beaconCount`). Отбор — комбинированный счёт
  (`scoreBeaconCandidate`): релевантность (косинус к тексту последнего
  сообщения, сдвинутый в [0,1]) ПЛЮС `computeNodeWeight()` в лог-пространстве
  (`beaconWeightFactor`, тот же приём, что `keywordWeight` у логитов
  региона) — решено с пользователем явно: "маяки — не менее подцентра
  региона", слабый/забытый узел не должен побеждать чисто по тематической
  близости. Защищённые узлы (`Infinity` вес) выигрывают почти всегда.
- **Кандидаты — ТОЛЬКО размещённые узлы** (`regionId` не `null`): узел в
  накопителе невидим для ретрива (решено ещё в Phase 1, соблюдено здесь).
- **Маршрут — цепочка маяк0→маяк1→маяк2** по СУЩЕСТВУЮЩИМ рёбрам
  (`findShortestPath`, честный BFS — реально кратчайший, не первый
  найденный), БЕЗ Steiner-дерева. Недостижимый сосед по цепочке не
  пропадает — перечисляется отдельно (`standalone`, "(unconnected)" в
  промпте).
- **Шумные ответвления — реализованы** (`gaussianRandom()`/`pickNoiseNodes()`):
  узлы на ОДНО ребро от узла на маршруте, но не сам маршрут. НЕ фиксированный
  процент на ребро — решено с пользователем явно ("по Гаусу, либо другой
  вид шума"): каждому кандидату — гауссов счёт (Box-Muller через
  инжектированный `random()`, тот же приём, что `makeId()`), сортировка
  убывающе, ЖАДНЫЙ набор. Потолок — НЕ число узлов, а бюджет СИМВОЛОВ
  (`noiseCharBudget`, решено явно пользователем: "не более N символов, не
  узлов" — богатый регион не должен раздувать промпт количеством мелких
  узлов). `continue`, не `break`, на нехватке места — более короткий
  кандидат дальше по списку всё ещё может поместиться (реальный риск,
  пойман bypass-then-restore).
- **Формат в промпте — структурированный список рёбер** (решено): компактная
  цепочка "Label -[type]-> Label -[type]-> Label" для маршрута, плюс СВОЯ
  строка на каждое шумное ребро ("From -[type]-> Noise (noise)" — решено с
  пользователем: "шум идёт от маршрута, связь будет, её и покажем", не
  безадресный список), плюс content каждого ВОВЛЕЧЁННОГО узла (маршрут +
  шум + недостижимые) ровно один раз (не дублируется на стыке двух
  сегментов — реальный риск, пойман bypass-then-restore).
- Мягкая деградация на каждом шаге (пустой граф, пустой контекст,
  недоступный эмбединг, пустой маршрут) — `chat` просто не трогается,
  генерация никогда не блокируется этим этапом.
- Покрыто: 23 юнит-теста (`scoreBeaconCandidate`/`pickBeacons`/
  `findShortestPath` — включая тест, где честная BFS-очередь ДОЛЖНА
  победить более длинный "неправильный" путь, специально сконструированный
  так, чтобы стек-подобный обход провалился/`buildBeaconRoute`/
  `renderMemoryPrompt` — включая рендер шумных рёбер/`gaussianRandom`/
  `pickNoiseNodes` — включая тест на жадный набор по бюджету, где `break`
  вместо `continue` даёт неверный результат, пойман bypass-then-restore) +
  3 сценарных теста через РЕАЛЬНЫЙ `pipelineCore.run({pipelineId:
  'generation.beforeSend', ...})` (инъекция срабатывает и содержит content
  графа; пустой граф ничего не добавляет; узел вне маршрута, но на одно
  ребро от него, реально попадает как шум — с детерминированным seeded
  `random()` для воспроизводимости) — все проверены bypass-then-restore.
  **Живая проверка через настоящий перехватчик генерации в харнессе** (не
  прямой вызов контракта): Memory-сообщение реально появляется в массиве
  `chat` рядом с независимой инъекцией Notebook — обе сосуществуют на одном
  `generation.beforeSend` корректно.
- **Не сделано**: маршрут не учитывает ГГ/единый центр графа (см. выше);
  связь маяков ретрива обратно в приоритет размещения НОВЫХ нод
  (`decideFirstPlacement`'s `beaconRegion` остаётся всегда `null` —
  оригинальный дизайн предполагал маяки текущего хода как приоритет №1 при
  размещении, но `generation.prepare` (размещение) выполняется РАНЬШE
  `generation.beforeSend` (маяки этого хода), так что маяки на момент
  размещения ещё не посчитаны — реальная проблема очерёдности пайплайна,
  не просто недосуг; не решена, явно
  задокументирована, не скрыта).

**UI-редактор графа — реализован** (`cores/ui/memory-graph-panel.js`,
`libraries/core/graph-rendering.js`, новые контракты `memoryGraph.nodes.*`/
`memoryGraph.edges.*` + 5 дебаг-контрактов в `cores/memory-graph/index.js`).
Решено с пользователем явно (два раунда вопросов): "полноценный UI не хуже
obsidian" + вызов любой функции вручную + редактирование/создание/
перемещение нод и связей.

- **Рендеринг — Cytoscape.js** (CDN, `+esm` через jsdelivr, тот же приём
  лениво-кэширующей загрузки, что `embedding.js`) + `cytoscape-edgehandles`
  (плагин "тяни от узла к узлу — ребро"). Готовая библиотека, не свой
  force-движок с нуля — решено явно.
- **Перетаскивание = смена региона по-настоящему** (решено с пользователем
  явно, НЕ визуальный эффект): `regionLayoutPosition()`/`pixelToRegion()` —
  чистые взаимно-обратные функции (координата экрана ↔ sector/ring),
  `dragfree` на канвасе реально вызывает `memoryGraph.nodes.move`, которая
  убирает узел из старого региона (без авто-переназначения центра, если
  двигали именно центр — задокументированный крайний случай, тот же
  принцип, что у "регион целиком из защищённых") и заново прогоняет его
  через `attachToRegion()` в новый — то есть перемещение в переполненный
  регион МОЖЕТ спровоцировать ту же реконсолидацию/вытеснение, что и
  органическая вставка (проверено вживую).
- **CRUD нод** (`memoryGraph.nodes.create/update/delete/move`) — create/move
  переиспользуют `attachToRegion()` напрямую (без каскада — регион
  указывает сам пользователь), update пересчитывает эмбединг ТОЛЬКО при
  реальном изменении label/content, delete переиспользует
  `removeNodeFromGraph()`.
- **CRUD рёбер** (`memoryGraph.edges.create/delete`) — двусторонняя запись,
  как везде в файле; повторное создание одной и той же пары не дублирует.
- **"Вызов любой функции вручную"** — 5 дебаг-контрактов
  (`memoryGraph.checkAndPlace`/`sweepStaging`/`sweepMergeQueue`/
  `sweepReconsolidationQueue`/`bootstrapFromLorebook`) тонкими обёртками
  поверх уже существующих операций Ядра — `bootstrapFromLorebook` через
  контракт обходит guard "только если граф пуст" (это ЕГО единственный
  способ ре-импорта, задумано так).
- **Окно — большое FloatingPanel** (решено явно, не секция общей панели
  настроек), точная копия паттерна HUD Трекера (`modules/tracker/index.js`) —
  persisted position/size/collapsed через `storage.settings`. Своё
  `official`-Ядро (`core.ui.memoryGraph`), не Модуль — свой floating-корень
  через `uiEngine.mount()`, тем же способом, что notifications/updateOverlay.
  Маленькая карточка-вход (счётчик узлов + кнопка) в общей панели настроек
  (`engine-panel.js`'s `memoryGraphCard()`).
- **Побочная находка при переиспользовании персиста**: `checkAndPlace()`/
  `bootstrapFromLorebook()`/`sweepStaging()` вызывают `attachToRegion()`,
  которая может завести запись в `mergeQueue`/`reconsolidationQueue`
  (`detectMergeCandidate`/`tryQueueReconsolidation`), но персистили только
  `[nodes, regions, staging]` — реальный, ранее не найденный баг потери
  данных на перезагрузке. Исправлено (все три места теперь персистят все
  пять хранилищ), покрыто регрессионным тестом (реальная перезагрузка —
  второй экземпляр Ядра поверх той же Шины/хранилища) с bypass-then-restore.

8. **Бэкбон-связность между центрами/под-центрами** (решено с
   пользователем явно, числами, после обсуждения альтернатив — см. ниже):
   малая ("обычная") нода — не больше `ordinaryMaxDegree` (3) связей
   вообще; под-центр — от `subCenterMinDegree` (10) до `subCenterMaxDegree`
   (15) связей ЛЮБОГО типа; центр — минимум `centerMinBackboneDegree` (4,
   снижено с изначально предложенных 8 — с 15 регионами 8 из ≤14
   возможных пиров было бы избыточно плотно) связей, но ТОЛЬКО к другим
   центрам/под-центрам (peer-only, без верхнего предела и без ограничения
   на органические связи с обычными нодами).

   Изначальный запрос пользователя включал ЕЩЁ отдельную идею — одну
   ГЛОБАЛЬНУЮ "ноду персонажей", к которой цеплялись бы слабо связанные
   персонажи (закрывала бы жалобу "персонажи очень плохо привязаны").
   Явно обсуждено и решено с пользователем: НЕ строить отдельный механизм
   — бэкбон центров/под-центров закрывает ту же проблему органически
   (слабо связанный персонаж тянется к ближайшему под-центру/центру СВОЕГО
   региона), один механизм вместо двух конкурирующих.

   **Под-центр — теперь РЕАЛЬНО назначаемая роль**, не только заведённое
   пустое поле `subCenterIds` (как до этого раунда): первые
   `subCentersPerRegion` (2 по умолчанию) узла ПОСЛЕ центра региона —
   тот же принцип "первый(-ые) по прибытию", что и у самого центра, не
   отдельная оценка важности. Защищены, как и центр.

   **Потолок обычных нод** — проверка ВСТРОЕНА прямо в органическое
   связывание по имени (`attachToRegion()`): если любая из сторон
   потенциального `mentions`-ребра не защищена (`!protectedNode`) и уже на
   потолке, ребро просто не создаётся — обеим сторонам сразу, дёшево, без
   отдельного прохода.

   **Минимумы (10 у под-центра, 4 у центра) органическое связывание
   гарантировать физически не может** — на 15 регионов даже 4 связи у
   КАЖДОГО центра не появятся сами от случайных упоминаний в 1-2
   предложениях лорбука. `enforceBackboneConnectivity()` — АКТИВНОЕ
   досоздание рёбер нового типа `backbone` (отдельно от органических
   `mentions`), тот же принцип "математика, не LLM", что и у остального
   графа: кандидаты сортируются СНАЧАЛА по соседству регионов
   (`regionAdjacency()` — та же геометрия дартса, что уже используется
   для соседства регионов при переполнении), затем по убыванию косинуса
   эмбедингов среди оставшихся. Зовётся из `bootstrapFromLorebook()`
   (после размещения всех записей, ДО бонуса важности за связи — иначе
   досозданные рёбра не влияли бы на итоговую важность), плюс новый
   контракт `memoryGraph.sweepBackbone` для ручного перезапуска — ручное
   создание ноды через UI-редактор (`memoryGraph.nodes.create`) само по
   себе бэкбон НЕ довязывает, это отдельный, явный шаг (доказано тестом:
   "a manually-created node does NOT get backbone-filled automatically").

   Область действия — сознательно ТОЛЬКО бутстрап (решено с пользователем,
   тем же выбором, что и для авто-важности): активный проход считает
   косинус эмбедингов для потенциально многих пар, дёргать его на КАЖДОЙ
   органической вставке (`checkAndPlace`, за ход генерации) было бы
   расточительно. Роль под-центра и потолок обычных нод — наоборот,
   универсальны (внутри `attachToRegion()`, общий путь для бутстрапа И
   органического роста) — дёшевы, действуют всегда.

   6 новых сценарных тестов через реальный движок (роль под-центра,
   потолок обычных нод, минимум центра, минимум/максимум под-центра,
   не-автоматичность для ручного создания) — все доказаны
   bypass-then-restore, включая отдельную проверку, что "максимум не
   пробит" ловит именно снятие потолка, а не вырожденный случай "ничего
   не добавилось". Геометрический приоритет соседства НЕ покрыт отдельным
   тестом — честно отмечено как непроверенный край, сам `regionAdjacency()`
   уже протестирован в другом месте.

9. **Бутстрап больше НЕ блокирует весь движок** (решено с пользователем:
   "зависание при bootstrap... вынеси его отдельно"). `memoryGraphCore.load()`
   раньше делала `await bootstrapIfEmpty()` ПЕРЕД регистрацией этапов
   пайплайна, и сама была `await`-нута напрямую в `harness/engine-wiring.js`'s
   главной цепочке — весь движок (панель, докер запуска) висел за одним
   `await`, пока не отработает `bootstrapFromLorebook()` (реальный вызов
   эмбеддинга НА КАЖДУЮ запись лорбука, последовательно — при большом
   лорбуке реально долго). Исправлено переупорядочиванием: `load()` теперь
   СНАЧАЛА регистрирует этапы пайплайна (быстро), бутстрап уходит В ФОН
   ПОСЛЕДНИМ, не дожидаемый самой `load()`. Новый метод
   `waitForBootstrap()` на возвращаемом объекте Ядра — для кода (тестов,
   отладки), которому ДЕЙСТВИТЕЛЬНО нужно дождаться результата.
   `bootstrapFromLorebook()` заодно обёрнута в `enqueueWrite` (не была
   раньше) — иначе фоновый бутстрап и реальная генерация
   (`checkAndPlace()`, тоже через `enqueueWrite`) могли бы мутировать
   `nodes`/`regions` одновременно, гонка. `harness/engine-wiring.js` правок
   не потребовал вовсе — `await memoryGraphCore.load();` там и так
   становится быстрым автоматически, раз сама `load()` больше не ждёт
   медленную часть.

   Доказано НАПРЯМУЮ, не только механическим сохранением старых тестов:
   новый тест с управляемым `embeddingGate`-промисом (тестовый `buildEngine()`
   теперь умеет задерживать `embedding.compute` по требованию) показывает,
   что `await graphCore.load()` возвращается, пока эмбеддинг всё ещё
   висит — узел ещё НЕ размещён, `waitForBootstrap()` нужно ждать отдельно.
   Bypass-then-restore здесь получился ПОКАЗАТЕЛЬНЫМ: откат на "снова
   awaited" не просто уронил один тест — подвесил ВЕСЬ файл тестов до
   таймаута, живое доказательство, что это была настоящая причина
   зависания, не гипотетическая. Остальные ~25 существующих мест
   `await graphCore.load()` в тестах — механически дополнены
   `await graphCore.waitForBootstrap()` следом (не меняли ПОВЕДЕНИЕ, что
   тестируют, только сделали ожидание явным, раз оно перестало быть
   неявным побочным эффектом `load()`).

10. **Импорт главного персонажа из карточки** — решено с пользователем в
    два захода: сначала обсуждалась авто-эвристика по полям Lorebook, но
    пользователь явно предпочёл ЯВНЫЙ выбор в UI ("отмечает, есть ли инфа
    о главном персонаже в LB, или она в карточке"), не автоматическое
    угадывание. Живёт в панели графа памяти, доступен ВСЕГДА (не только
    при первом запуске): два варианта — "Character already in Lorebook"
    (ничего не создаёт — обычный бутстрап и так импортирует весь Lorebook,
    кнопка только подтверждает, что отдельная нода не нужна) и "Only in
    character card — import" (реальное действие).

    Новый Сервис `services/st-character.js` (`stCharacter.current`) —
    единственное место, трогающее сырую специфику карточки персонажа, тот
    же принцип, что у `services/st-lorebook.js`. Поля V2-карточки
    подтверждены по реальному исходнику ST (`public/script.js`, через
    `raw.githubusercontent.com`) — `data.creator_notes`/`data.extensions`
    читаются ВЛОЖЕННЫМИ в `character.data.*`; легаси V1 хранит поля плоско
    на самом объекте. Точный формат КОНКРЕТНОЙ карты заранее не известен —
    сервис читает ОБА варианта defensively (`character.X ?? character.data?.X`).

    `createNodeFromCharacterCard()` (`cores/memory-graph/index.js`) —
    контент ТОЛЬКО `description`+`personality` (решено с пользователем,
    выбрано из вариантов явно; `scenario` намеренно не берётся — не всегда
    про самого персонажа). Размещается ТЕМ ЖЕ каскадом, что бутстрап/
    SideCar-ноды (`placeNewNode()`), не ручным сектором/кольцом — у
    пользователя нет оснований выбирать регион вручную. Важность —
    `MAIN_CHARACTER_IMPORTANCE = 7` (не откалиброванный протокол, как и
    другие эвристики важности в файле — главный персонаж по определению не
    второстепенная деталь). Повторный импорт не блокируется отдельно —
    почти-дубликат естественно поймает уже существующий merge-dedup
    механизм, отдельная защита от двойного клика не нужна.

    3 новых сценарных теста через реальный движок (контент объединяет оба
    поля, чистый отказ без активного персонажа, чистый отказ на пустой
    карточке) — доказаны bypass-then-restore.

11. **LLM-driven семантические регионы при бутстрапе из Lorebook** — самая
    крупная переделка Memory Graph за весь сеанс, план
    `rosy-wishing-beacon.md`. Живая проверка на реальном лорбуке (61
    запись) показала: **~80% нод без единой связи**. Причина — единственный
    механизм связывания, `extractCharacterNames()`, ловит связь ТОЛЬКО при
    дословном упоминании чужого имени; для локаций/фракций/лора это
    почти никогда не срабатывает. Плюс сама раскладка по 15 абстрактным
    ячейкам дартса не несёт смысловой нагрузки.

    Решено с пользователем (несколько раундов обсуждения, включая явную
    проверку числами и компромиссами): для БУТСТРАПА — LLM видит Lorebook
    целиком и явно расставляет структуру и связи. Органический рост
    графа во время игры (`checkAndPlace()`) **остаётся на старом
    дартборде** — решено явно: цена LLM приемлема РАЗОВО (бутстрап), не на
    каждый ход генерации. Дартборд-геометрия
    (`SECTORS`/`RINGS`/`regionKey`/`regionAdjacency`/`vectorProbsForAllRegions`/
    `decideFirstPlacement`/`enforceRegionCapacity`/`enforceBackboneConnectivity`)
    НЕ удалена — по-прежнему полностью обслуживает `checkAndPlace()`.

    **Новый пайплайн `bootstrapFromLorebook()`** (3 прогона SideCar + эмбединг-присвоение):
    1. Читает ВЕСЬ Lorebook целиком, без немедленного размещения.
    2. **Проход 1** — один вызов `model.generate` с ПОЛНЫМ текстом
       Lorebook + `baseRegionNames` (по умолчанию
       `['Locations', 'Main Characters', 'Factions']`). Для каждого
       подходящего региона ИЗ ЭТОГО списка — 2 записи-под-центра по
       номеру. (Изначально промпт разрешал LLM ещё и предлагать СВОИ
       регионы здесь же — пользователь поймал это как ошибку дизайна,
       см. п. 13 — теперь Проход 1 может ТОЛЬКО раскладывать под-центры
       по заданному списку, изобретение новых регионов сверху —
       исключительно Проход 2.)
    3. **Проход 2** — центр для КАЖДОГО региона из Прохода 1 (у него пока
       только под-центры) + новые регионы сверх них, до целевой плотности
       `entriesPerRegionCenter` (по умолчанию 20 — один центр примерно на
       N записей).
    4. Центры/под-центры размещаются с ЯВНОЙ ролью
       (`attachToRegionByKey(node, key, {forceRole: 'center'|'subCenter'})`)
       — LLM уже решила, не порядок прибытия.
    5. Остальные записи — `pickNearestRegion()`: argmax косинуса к уже
       размещённым центрам/под-центрам (не ко всем 15 дартборд-ячейкам —
       их просто нет). Всегда находит дом, нет "накопителя" для этого пути.
    6. **Проход 3** — по ОДНОМУ вызову НА КАЖДЫЙ регион: список его нод
       без существующих рёбер, LLM предлагает связи → двусторонние рёбра
       типа `'related'` (новый тип, отдельно от `mentions`/`backbone`).
       Межрегиональные связи — СТАРЫЙ `extractCharacterNames()`, решено
       явно "пока оставим старым", отрабатывает как обычно внутри
       `attachToRegionByKey()` для каждой размещённой ноды.
    7. Бэкбон (`enforceBackboneConnectivity()`) + бонус важности за связи
       — как раньше, без изменений, работает одинаково для любого ключа
       региона.

    Отказ Прохода 1/2 → весь бутстрап прерывается, `false`, граф пустым
    (тот же паттерн, что у пустого Lorebook). Отказ Прохода 3 для ОДНОГО
    региона НЕ блокирует остальные (тот же принцип, что у
    `escalateToSideCar()`).

    **Рефакторинг фундамента**: `attachToRegion(node, sector, ring)`
    разложен на `attachToRegionByKey(node, key, {createRegion, forceRole})` +
    тонкая обёртка. `forceRole` — `'center'`/`'subCenter'`/`'ordinary'`/`null`.
    **Реальный баг, найденный при написании тестов**: записи, присвоенные
    через `pickNearestRegion()` (argmax), изначально шли с `forceRole: null`
    и ПОДХВАТЫВАЛИ старую авто-детекцию под-центра по порядку вставки
    (`region.subCenterIds.length < settings.subCentersPerRegion`) —
    третья запись в свежесозданном регионе неожиданно становилась
    под-центром, затем `enforceBackboneConnectivity()` тянул её в бэкбон,
    ломая тест на бонус важности (оба узла получали одинаковый degree=2
    вместо разного). Исправлено: `forceRole: 'ordinary'` для argmax-пути —
    явный отказ от авто-детекции, независимо от `subCentersPerRegion`.
    Поймано bypass-then-restore.

    **Область действия обёртки не изменилась** — `attachToRegion(node, sector, ring)`
    (дартборд) вызывает `bumpWordProfile()` (дартборд-специфичный, семантическим
    регионам не нужен — они не участвуют в keyword-логитах) и делегирует в
    `attachToRegionByKey()`; все существующие вызовы (`checkAndPlace`,
    `createNodeManually`, `moveNodeManually`, `escalateToSideCar`) не изменились.

    **Тестовая инфраструктура**: `fakeFetchReplying(reply)` (один и тот же
    ответ на каждый вызов) расширена `fakeFetchSequence(replies)` (разный
    ответ на КАЖДЫЙ последовательный вызов `model.generate`, последний
    элемент повторяется сверх длины массива) — `buildEngine()` получила
    новый параметр `fetchReplies` (и `fetchOverride` для полного контроля,
    нужен тесту на частичный отказ Прохода 3 — один конкретный вызов
    должен вернуть `ok:false`, обычной очереди ответов для этого мало).
    `buildRealLorebookAndGraph()` тоже донастроена (Settings Core +
    Models Core) — раньше ей это было не нужно, старый бутстрап SideCar
    не звал вовсе.

    **~24 существующих сценарных теста бутстрапа переписаны** под новый
    контракт (нужны реалистичные ответы Прохода 1/2/3, не старый
    единственный `fetchReply`). Часть тестов, которые проверяли
    ДАРТБОРД-специфичное поведение (self-reinforcing regionId бага,
    авто-детекция под-центра по порядку прибытия), **перенесены на
    `checkAndPlace()`/ручное создание** — регрессии, которые они
    доказывают, теперь актуальны только там, не в бутстрапе. Плюс 12+
    новых тестов: юнит-тесты на все новые чистые функции
    (`buildRegionSkeletonPrompt`/`parseRegionSkeletonResponse`/
    `buildAdditionalCentersPrompt`/`parseAdditionalCentersResponse`/
    `pickNearestRegion`/`buildRegionEdgesPrompt`/`parseRegionEdgesResponse`),
    сценарные тесты на отказ Прохода 1/2 (граф остаётся пустым), частичный
    отказ Прохода 3 (остальные регионы не блокируются), успешное создание
    `related`-ребра. Все 920 тестов зелёные, ключевые места доказаны
    bypass-then-restore.

    **UI-защита (не полноценная визуализация — решено с пользователем,
    отдельный заход)**: `cores/ui/memory-graph-panel.js`'s `nodeElements()`
    раньше делал `regionId.split(':').map(Number)` безусловно — для
    семантического `regionId` (например `"Locations"`) это дало бы
    `NaN`-координаты. Добавлен `fallbackSemanticPosition()` — хэш строки
    региона в стабильный угол, чисто временная защита от невидимых/
    накладывающихся нод, не финальная раскладка.

12. **Проходы 1-3 молча укладывались в дефолтный лимит модели (1000
    токенов)** — найдено живьём на реальном лорбуке. Ни один из трёх новых
    `call('model.generate', ...)` не передавал `maxTokens` явно, поэтому
    `resolveGenerateRequest()` (`cores/models/internal-engine.js`) падал на
    `REQUEST_DEFAULTS.maxTokens = 1000` — рассчитан на короткие ответы
    трекеров/одной ноды, не на структурированный JSON нескольких регионов
    или связей целого региона. Усечённый посреди объекта JSON просто не
    парсится (`parseModelJson()` тихо отдаёт `undefined`), из-за чего
    Проход 1/2 мог молча проваливаться на реальном (не игрушечном) лорбуке.
    Новая настройка `bootstrapMaxTokens` (изначально по умолчанию 4000 —
    **живьём оказалось мало на реальном лорбуке** ("он не вывозит"),
    поднято до 50000; клэмп 100-200000, потолок ВЫШЕ, чем у
    `clampSamplerSettings()` в internal-engine.js (32768) — тот рассчитан
    под обычный чат-сэмплер, бутстрапу реально нужно больше), передаётся
    явно во всех трёх вызовах. Не тронут дефолт ДРУГИХ SideCar-вызовов
    этого же файла (`askSideCarForNode`/`askSideCarForMerge`/
    `askSideCarForReconsolidation`) — их ответы короткие (одна нода/вердикт),
    1000 токенов достаточно, менять незачем. 2 новых сценарных теста
    (реальный `max_tokens` в исходящем HTTP-теле запроса — дефолт,
    настраиваемое значение уважается) — доказаны bypass-then-restore.

13. **Проход 1 не должен был изобретать регионы сам — пользователь поймал
    это как отдельный дизайн-баг** ("ты ужасно сделал, что за один прогон
    он и выводит под-центры в регионы и добавляет новые центры"). У
    `buildRegionSkeletonPrompt()` (Проход 1) была фраза "You may propose
    your OWN additional region names too" — та же работа, что уже
    ЧЕСТНО делает Проход 2 (`buildAdditionalCentersPrompt()`), просто
    менее контролируемо (без цели по плотности `entriesPerRegionCenter`,
    без явного учёта уже выбранных). Убрано: промпт Прохода 1 теперь
    говорит прямо "Use ONLY these regions — do NOT invent, rename,
    merge, or add any others" — изобретение новых регионов сверх
    `baseRegionNames` осталось ИСКЛЮЧИТЕЛЬНО работой Прохода 2.

    Заодно, тем же запросом пользователя, сэмплер всех трёх Проходов
    занижен (структурированная JSON-раскладка по правилам — не
    творчество, вариативность и долгие раздумья тут не нужны, а
    реальная жалоба была именно на них): новые настройки
    `bootstrapTemperature` (0.4, клэмп 0-2) и `bootstrapReasoningEffort`
    (`'low'`, из `['low','medium','high']`) читаются во всех трёх
    `call('model.generate', ...)`. Плюс общий `BOOTSTRAP_SYSTEM_PROMPT`
    (экспортирован для тестов) — явная инструкция "follow exactly,
    don't add/skip/invent, decide quickly, no extended reasoning, ONLY
    the requested JSON" — едет `systemPrompt`'ом на каждый вызов, как
    подстраховка для воркеров, где `reasoningEffort` не действует вовсе
    (см. ниже).

    **Найдено при написании прувинг-теста**: `reasoningEffort` САМ ПО
    СЕБЕ ничего не делает — оба unified-`reasoning`-билдера в
    `libraries/core/provider-request.js` (`buildOpenAiReasoning()` для
    OpenRouter-формата, `buildAnthropicReasoningExtras()`) возвращают
    `{}`, пока `reasoningMode` не `'enabled'`/`'disabled'` ЯВНО (дефолт —
    `'inherit'`, молчит). Поэтому в самих вызовах бутстрапа
    `reasoningMode: 'enabled'` зашито явно (не настройка — это не
    "выключить ризонинг", а "включить, но по низкому эффорту"). Плюс
    `reasoning.effort`/`reasoning.enabled` реально уезжают в запросе
    ТОЛЬКО у воркеров с `endpoint`, матчащим `openrouter.ai`
    (`isOpenRouter()`) — для остальных форматов (`anthropic`/`google`/
    обычный `openai`) поле `reasoning` просто не строится, температура и
    system-сообщение при этом всё равно уходят всегда (не gated
    форматом).

    3 новых сценарных теста: Проход 1 текстом больше не приглашает
    изобретать регионы (юнит-тест на сам промпт, `memory-graph-core.test.js`);
    температура 0.4 и system-сообщение с `BOOTSTRAP_SYSTEM_PROMPT` реально
    уезжают в HTTP-теле на каждом Проходе; настраиваемые
    `bootstrapTemperature`/`bootstrapReasoningEffort` уважаются поверх
    дефолтов (второй тест намеренно гоняет воркера с `openrouter.ai`
    endpoint'ом, иначе `reasoning`-поле в теле вообще не появилось бы).
    Все доказаны bypass-then-restore. Итог — 925/925 тестов.

## Решено

1. **Кто создаёт/связывает ноды** — ТОЛЬКО SideCar (тихий фоновый вызов
   модели, как у `tracking.poll()`/BasicSummary's `foldRawUnits()`), не
   настоящий ST-инструмент (в отличие от Notebook) и не ручное редактирование
   пользователем по умолчанию.
2. **Триггер SideCar-прогона** — не "каждый ответ". Пользователь хочет
   вынести решение "когда вообще звать модель" в дешёвую математику
   (эмбеддинги/метрики), и звать SideCar только при СИЛЬНЫХ изменениях —
   экономия реальных LLM-вызовов. Точная метрика "силы изменения" ещё не
   определена (кандидат: расстояние эмбеддинга нового контента до ближайшей
   существующей ноды/центра, отслеживание накопленного отклонения).
3. **Куда идёт результат** — в промпт ОСНОВНОЙ (ролевой) модели, тем же
   путём, что Notebook/BasicSummary: этап `generation.beforeSend`, живая
   мутация `chat`, не `setExtensionPrompt`.
4. **Центр графа** — центральный узел (постоянный якорь) плюс граф ветвится
   от него. Не "то, что сейчас активно" — фиксированная точка входа.
5. **Что реально извлекается для промпта — НЕ "активные ноды", а маяки
   (beacons).** Компонент отбора:
   - Маяки — самые "яркие"/информационно богатые ноды, отобранные
     ПРЕИМУЩЕСТВЕННО через эмбединг (близость к текущему контексту).
   - В промпт идёт МАРШРУТ по графу между центром и маяками (обход/путь по
     типизированным рёбрам), а не просто список ближайших по эмбедингу нод
     по отдельности.
   - Плюс небольшие ответвления от маршрута "по принципу шума" — случайно/
     вероятностно подмешанные соседние ноды рядом с маршрутом, для
     серендипности/текстуры, не только строгий кратчайший путь.
6. **Рёбра — типизированные** (несут смысл: "знает", "находится в",
   "является частью" и т.д.), не голая ссылка как в обычном Obsidian.

## Важный технический факт — эмбеддинги

Проверено по РЕАЛЬНОМУ исходнику ST (`public/scripts/extensions/vectors/index.js`,
актуальная release-ветка):

- У родного расширения Vectors **нет публичного API на `getContext()`** —
  оно экспортирует только `EXTENSION_PROMPT_TAG`/`EXTENSION_PROMPT_TAG_DB`/
  `init()`. Внутренняя логика эмбеддинга (`getAdditionalArgs`,
  `getVectorsRequestBody` и т.д.) НЕ экспортируется вообще — достучаться до
  неё изнутри нашего расширения (даже динамическим импортом, как у Lorebook
  с `selected_world_info`) невозможно, там просто нет нужных экспортов.
- НО у ST есть настоящие СЕРВЕРНЫЕ REST-эндпоинты, которые это расширение
  само дёргает обычным `fetch()` с `getRequestHeaders()`:
  `/api/vector/insert`, `/api/vector/query`, `/api/vector/list`,
  `/api/vector/delete`, `/api/vector/purge`, `/api/vector/query-multi`.
  Тело запроса — `{ collectionId, items/text, source, ...настройки
  конкретного провайдера эмбеддингов }` (см. `getVectorsRequestBody()`,
  `insertVectorItems()`, строки ~925-1070 файла).
- Значит МЫ МОЖЕМ дёргать эти эндпоинты НАПРЯМУЮ сами, тем же приёмом, что и
  остальные наши Сервисы (`http.request` через Гейт сети, тот же
  same-origin fetch) — переиспользуя embedding-провайдера, который
  пользователь УЖЕ настроил в родных настройках Vectors, без своего
  отдельного API-ключа. Работаем со СВОИМ `collectionId` (свой неймспейс,
  не пересекается с нативным RAG чата/WI пользователя).
- Риск: это серверные HTTP-роуты самой ST, не документированный публичный
  API расширений — могут поменяться между версиями ST без предупреждения
  (тот же класс риска, что уже был у `selected_world_info` в Lorebook, но
  без даже дынамического импорта как страховки — тут только реальный
  HTTP-контракт). Достаточно устоявшаяся, долгоживущая часть ST (Vector
  Storage — давняя фича), но версионный дрейф всё равно возможен.

## Tier-система — Graph и BasicSummary не сосуществуют

Это НЕ две независимые системы, конкурирующие за бюджет промпта — это ДВЕ
РЕАЛИЗАЦИИ одного слота «долгосрочная память в промпте», между которыми
пользователь выбирает пресетом:

- **LowTier** = BasicSummary (уже построен, дешёвый — обычные фолды).
- **TopTier** = Граф (эмбединги + SideCar + маршрут+шум).
- Строго одно из двух активно одновременно, никогда оба сразу.

**Следствие для уже готового BasicSummary**: сейчас он всегда включён
безусловно (обычное `official`-Ядро). Чтобы Tier-переключатель реально
работал, активацию BasicSummary тоже придётся сделать УСЛОВНОЙ (проверка
общей настройки тира при `load()`/подписке на её смену) — это ретрофит уже
сданного кода, не только новая фича. Пока не начат.

## Переиспользование Tracker'а (`cores/tracking/index.js`)

Решено: SideCar графа зовёт модель ТЕМ ЖЕ приёмом, что `tracking.poll()` —
`model.generate` с пиннингом на конкретный воркер, свои
sampler/reasoning-параметры отдельно от воркера. Это переиспользуемо
буквально — не копия логики, а тот же контракт.

**Уточнение (моя трактовка, требует подтверждения):** ЧТО поллить —
переиспользуем механику вызова, а не механику триггеров Director'а
(`trigger-modes.js`). У Director'а сейчас нет условия "по порогу метрики" —
только `{event}`/`{event, every}`/`{every:{ms}}`. "Сильное изменение" — это
не одно из этих условий, а собственная проверка внутри `generation.prepare`
графа (посчитать дешёвую метрику, и, если порог превышен, самим вызвать
`model.generate`), а не что-то, что можно выразить существующим `when`
Director'а без его расширения. Тоже не подтверждено пользователем.

## Физика графа — регионы (предложено пользователем)

Не вольный граф, а ФИКСИРОВАННАЯ топология — «дартс»: круг режется на 5
угловых секторов, каждый сектор — на 3 кольца по удалению от центра. Клетка
(сектор × кольцо) = **регион**. У региона свой центр, до 2 под-центров под
ним, и узлы под каждым под-центром. Регион может соединяться ТОЛЬКО с
соседними по сетке регионами (сектор±1 то же кольцо, или то же
сектор±1 кольцо) — эмерджентных дальних рёбер нет, соседство задаётся
геометрией, а не LLM.

**Зачем это лучше вольного графа**: снимает главный риск вольной версии
(неограниченный disorderный рост) — ёмкость структурно ограничена, и путь
между двумя точками всегда определён геометрией сетки, а не зависит от того,
насколько разумно LLM развела рёбра.

- **Что такое 5 секторов**: НЕ фиксированные категории (не мы решаем «сектор
  1 = персонажи») — просто разделы, LLM сама решает, куда класть новый факт
  (вероятно — по близости эмбединга к центру региона).
- **Переполнение региона** — три механизма разом: **реконсолидация**
  (пересжатие нескольких мелких записей региона в одну более плотную, в духе
  фолда BasicSummary, но локально внутри региона), **объединение**
  (слияние дублирующих/сильно похожих узлов), **Memory Decay** (со временем
  важность узла падает, и то, что упало ниже порога, попадает под
  реконсолидацию/объединение первым).
- **Важность** — присваивается узлу В МОМЕНТ СОХРАНЕНИЯ (SideCar сам
  оценивает, вероятно числом). Двигает decay: важные узлы держатся дольше.
  Не решено: что именно ДВИЖЕТ decay по времени — число сообщений (как
  protectedWindow у BasicSummary), реальное время чата, игровое время
  (Модуль «RP Time» уже считает его отдельно) — или комбинация.
- **Точная арифметика "12 записей на регион"** — озвученная пользователем не
  сходилась (1 центр + 2 под-центра + "до 10 у каждого" = 23, не 12).
  **Решено**: 23, буквально по формуле — см. "Переполнение региона"
  ближе к концу документа.
- **Formula веса/decay — композит из 4 факторов** (подтверждено):
  1. Время (какое именно время ещё не выбрано — см. открытые вопросы).
  2. Важность события (оценка, присвоенная SideCar при сохранении).
  3. Количество связей узла (degree — чем больше связей, тем весомее/
     устойчивее узел; тот же принцип, что centrality в графах).
  4. Недавность (recency) — свежие события временно весят больше, вес
     остывает со временем, если узел не важен/не защищён.
  Похоже на формулу ретрива из "Generative Agents" (Park et al.) —
  `recency + importance + relevance`, здесь плюс явный вес связности и
  отдельный уровень "защищённости".
- **Защищённые узлы** — не decay-immune навсегда автоматически, а отдельная
  категория: изначально ЗАДАЁМ их сами (например, региональные центры при
  бутстрапе), дальше граф САМ выдвигает новые защищённые узлы естественно —
  по накоплению связей. Защищённые узлы получают приоритет и на decay
  (не вымываются), и на вывод (приоритет при отборе маяков/маршрута).

**На перспективу (не проектируем сейчас, но держим в схеме место под это)**:
блочная/фрактальная система — весь круг (все 15 регионов) сам становится
ОДНОЙ нодой в графе более высокого уровня (для очень длинных кампаний —
несколько кругов = несколько "эпох", соединённые между собой). Чтобы это не
потребовало переделки схемы позже, круг с самого начала обязан иметь ту же
"внешнюю форму", что и обычный узел (свой embedding, свою важность, свою
метку) — self-similar по конструкции.

## Математика вместо части SideCar-решений (ответ на риски оценки)

Два риска из последней оценки адресованы явно:

- **Нестабильность распределения по секторам** (риск: один и тот же тип
  факта в разные моменты уедет в разные секторы, раз рубрики нет) —
  смягчается: "тенденция" сектора считается МАТЕМАТИКОЙ (частотность
  ключевых слов по семантике, стоп-слова/типичные слова исключаются из
  подсчёта), а не отдаётся целиком на усмотрение LLM каждый раз. Похоже на
  TF-IDF/keyword-centroid против уже накопленного "словаря" региона. SideCar,
  видимо, всё ещё подтверждает/фиксирует финально, но с математической
  тягой в конкретную сторону, а не с нуля каждый раз — не полностью убирает
  нестабильность (LLM может переопределить тенденцию), но снижает её.
- **Стоимость (2-3 обращения к модели на событие)** — тот же принцип, что
  уже был у триггера "сильного изменения": минимизировать САМ ВЫЗОВ SideCar
  математикой везде, где это в принципе возможно, не только на входе
  (когда звать), но и внутри пайплайна классификации/оценки важности —
  меньше решений реально идёт через дорогой вызов модели.

## Варианты алгоритма "тенденции сектора" (нужно тестить эмпирически)

Четыре кандидата, не выбрано — решаем после прогона на реальных данных:

1. **TF-IDF по накопленному словарю региона.** Каждый регион держит частотную
   таблицу слов (без стоп-слов). Новый текст считается против всех 5 таблиц,
   максимум — тенденция. Просто, дёшево, полностью локально, эмбединг не
   нужен. Слабость: чисто лексический — синонимы/парафраз мимо ("меч" и
   "клинок" — разные слова для него).
2. **Косинус к центроиду эмбединга региона.** Регион держит СРЕДНИЙ эмбединг
   своих узлов (центроид). Новый эмбединг (который и так считаем для
   маяков/ретрива — см. секцию про `/api/vector/query`) сравнивается с 5
   центроидами. Плюс: переиспользует уже нужный вызов эмбединга, ловит
   смысл, а не только буквы. Естественный кандидат №1, раз эмбединг уже
   всё равно на пути.
3. **Лёгкая экстракция ключевых слов (RAKE/YAKE, без модели) + профиль
   ключевых слов на сектор.** Ближе всего к буквальной формулировке
   ("считаем ключевые слова, исключая типичные") — короткий список
   значимых слов из нового текста против растущего bag-of-keywords каждого
   сектора.
4. **Гибрид**: keyword-overlap как первый быстрый фильтр (отсекает явно не
   те секторы почти бесплатно), эмбединг-центроид — только чтобы разрешить
   спор между 1-2 оставшимися кандидатами.

**Вес относительно SideCar** — тоже кандидаты, не решено:
- (a) Математика — подсказка в промпте SideCar'у, он вправе переопределить.
- (b) Математика — жёсткое умолчание, SideCar зовётся ТОЛЬКО если топ-2
  сектора близки по счёту (снова принцип "минимизировать вызов SideCar").
- (c) Математика — только для triage при переполнении/decay региона, не
  для начального распределения вообще.

Рекомендация на первый прогон: (2) центроид эмбединга + (b) жёсткое
умолчание с эскалацией к SideCar только при близких счётах — меньше всего
новой инфраструктуры (эмбединг и так нужен), меньше всего лишних вызовов
модели. Но без реальных данных не проверить — заносим как план на
тестирование, не финальное решение.

## Эмбединг — ЛОКАЛЬНО в браузере, не через `/api/vector/*` ST (пересмотрено)

Проверено по актуальным источникам (не по памяти) — реально:

- **`@huggingface/transformers`** (бывший Xenova/transformers.js) — гоняет
  ONNX прямо в браузере через WASM/WebGPU, без сервера, без llama.cpp.
  Грузится обычным ESM-импортом с CDN (jsDelivr), без бандлера — тем же
  способом, каким уже грузится весь остальной код проекта.
- **Модель**: `Xenova/paraphrase-multilingual-MiniLM-L12-v2` — 118M
  параметров, 384-мерный эмбединг, 50+ языков (русский включён), ~440-470MB
  исходно, с int8-квантованием ~110-140MB — укладывается в бюджет 500MB.
- **Реальное ограничение**: max sequence length 128 токенов у этой модели —
  длинные куски текста ноды придётся резать/сокращать перед эмбедингом, не
  подавать целиком.
- **Компромисс против `/api/vector/*`** (см. секцию выше, ещё актуальна как
  запасной вариант): локальная модель = ноль зависимости от того, настроил
  ли пользователь родной Vectors ST вообще, ноль стоимости за вызов (считает
  на клиенте). Цена — одноразовая закачка весов в кэш браузера при первом
  использовании (сотни MB, один раз, дальше из кэша) и инференс на
  клиентском CPU/GPU (задержка на слабом железе).
- Источники: huggingface.co/docs/transformers.js, huggingface.co (карточки
  моделей Xenova/paraphrase-multilingual-MiniLM-L12-v2 и
  sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2),
  github.com/huggingface/transformers.js.

**Текущая склонность**: локальный эмбединг как основной путь, `/api/vector/*`
ST — как запасной/альтернативный (например, для тех, кто не хочет качать
модель). Не решено окончательно.

### Какую именно модель — пересмотрено, первая рекомендация была слабой

Проверил по бенчмаркам (не по памяти) — `paraphrase-multilingual-MiniLM-L12-v2`
(предложенная выше) обучена на парафраз/сходство, НЕ на асимметричный
retrieval — на реальных бенчмарках её результаты называют "disappointing".
Плохой выбор для отбора маяков/тенденции сектора.

Три реальных кандидата (сравнение):

| Модель | Параметры | Размер (квант.) | Плюсы | Минусы |
|---|---|---|---|---|
| paraphrase-multilingual-MiniLM-L12-v2 | 118M | ~110-140MB (int8) | маленькая | слабая на retrieval (проверено бенчмарком) |
| **multilingual-e5-small** | 118M | ~110-140MB (int8) | та же цена, что выше, но контрастивно дообучена ИМЕННО под retrieval — заметно лучше на бенчмарках; обычно 512 токенов контекста (не 128) | нет |
| Qwen3-Embedding-0.6B | 0.6B | нужен INT4 (~300MB), INT8 не влезает в 500MB | SOTA-класс (8B-версия — топ MTEB multilingual) | INT4 обычно даёт бОльшую просадку качества, чем INT8, и совместимость embedding-варианта именно с transformers.js в браузере не подтверждена напрямую (генеративные Qwen3 0.8B/1.7B в браузере работают, embedding-ветка — не нашёл примера) |

**Текущая рекомендация**: `multilingual-e5-small` как дефолт — тот же
бюджет, что и первая (провалившаяся) идея, но реально подходит под задачу.
Qwen3-Embedding-0.6B — держать в уме как путь апгрейда, если e5-small
окажется недостаточно точной на практике.

**Q5/Q6-квантование недоступно в этом стеке.** У `transformers.js`/ONNX
Runtime Web квантование дискретное: `fp32`/`fp16`/`q8`(int8)/`q4`(int4) —
без промежуточных 5-/6-битных уровней. Q5_K_M/Q6_K — это схема конкретно
GGUF/llama.cpp, другой рантайм; взять её означало бы притащить llama.cpp,
ровно то, от чего решили уйти. Для Qwen3-Embedding-0.6B выбор строго
бинарный: q8 (~600MB, мимо бюджета) или q4 (~300MB, просадка больше, чем
дал бы гипотетический Q5/Q6) — середины нет. Ещё один довод в пользу
`multilingual-e5-small`: она настолько маленькая, что в эту вилку вообще не
упирается — fp16/q8 без агрессивного квантования укладывается в бюджет с
запасом.

## Связи vs Сектор — два разных механизма, не один

Уточнение от пользователя развело задачу на две независимые части:

- **Связи новой ноды с существующими** — по имени персонажа (точное
  совпадение, не эмбединг). Надёжно, однозначно, дёшево — эмбединг-сходство
  тут может обмануть (два разных персонажа с похожим описанием характера
  дадут высокий косинус, хотя это разные сущности). Имя — для связей,
  вектор/ключевые слова — для сектора. Разные механизмы, не путать.
- **Сектор новой ноды** — чистый вектор рискован: без якоря секторы "плывут"
  (по сути k-means на 5 кластеров без фиксированной инициализации,
  чувствителен к порядку поступления данных — несколько ранних ошибок
  сдвигают центроид, и дальше сектор притягивает всё более похожее на свою
  же ошибку). Простое СРЕДНЕЕ вектор+keyword тоже не идеал — размывает
  сильный сигнал слабым, если один шумный.
  **Текущая склонность**: вектор — основной сигнал, ключевые слова —
  tie-breaker ТОЛЬКО когда топ-2 сектора у вектора близки по счёту (условное
  подключение, не постоянное среднее). Отдельно, против дрейфа: сравнивать
  новую ноду с ЦЕНТРОМ РЕГИОНА (уже "защищённый", самый стабильный
  представитель темы), а не со средним всех нод сектора.
  Не решено окончательно, нужен реальный прогон.

### Формула отбора региона — сложение логитов + softmax (как в семплере)

Заменяет и "среднее", и hard-coded tie-breaker выше — то же поведение
получается САМО, гладко, без branch на "близко/не близко":

```
logit_i = ln(vector_prob_i) + w · ln(1 + keyword_matches_i)
p_i = softmax(logit_i) = exp(logit_i) / Σ exp(logit_j)
```

- `ln(1 + k_i)`, не голое `k_i` — ноль keyword-совпадений даёт логит 0
  (НЕЙТРАЛЬНО, не штраф региону, у которого просто нет активности в
  словаре).
- `w` — единственный откручиваемый параметр (сила keyword-сигнала
  относительно векторного), тот же принцип, что температура/logit_bias в
  реальном семплере. Кандидат на эмпирическую настройку.
- Проверено на примере пользователя (v=0.6/0.4/0.1, keyword-счёт 5/10/0,
  w=1) → p≈(0.44, 0.54, 0.01), качественно совпадает с ожиданием
  пользователя (0.49/0.50/0.01) — регион с меньшим vector-приоритетом, но
  большим keyword-подтверждением обгоняет; регион без keyword-совпадений
  почти обнуляется. Точное w под финальный численный результат — предмет
  реального прогона, не решено окончательно.
- Автоматически даёт "keyword решает только когда вектор не уверен": при
  большом разрыве vector-логитов keyword-сигналу нужно намного больше веса,
  чтобы перебить; при близких vector-вероятностях даже небольшая
  keyword-разница легко переворачивает исход.

**Оценка идеи (не только "совпало с примером")**: подход в целом хороший —
сложение логитов независимых источников свидетельства статистически
корректно (та же логика, что Naive Bayes/log-linear модели), не хак; та же
ментальная модель, что уже реально используется в движке (семплер). Три
реальных сомнения, не для галочки:
1. `ln(1+k)` — разумный дефолт (та же логика у TF-IDF), но не доказан
   именно для этой задачи; альтернативы (sqrt, насыщающая k/(k+c)) не
   исключены.
2. **Сырой счёт совпадений не нормирован на размер словаря региона** —
   регион с БОЛЬШИМ накопленным профилем ключевых слов будет систематически
   получать больше хитов не из истинной релевантности, а из размера
   словаря ("богатый богатеет"). Вероятно нужна нормировка (TF-IDF-стиль),
   не голый счёт — записать как пункт на тестирование, не финал.
3. Фундаментальный потолок тот же, что и раньше: нет эталонных данных для
   численной проверки точности классификации — оценка будет "выглядит
   разумно", не измеримый процент. Формула упорядочивает решение, но не
   снимает эту проблему.

## Концептуально другие подходы к определению региона (не вариации логит-формулы)

Запрошено явно — не сравнение/тюнинг текущего подхода, а другие парадигмы:

1. **Через связи, не через контент (topological/graph-based, label
   propagation).** Если новая нода уже связалась с существующими по имени
   персонажа (уже решённый механизм), взять регион БОЛЬШИНСТВА её соседей —
   вместо сравнения контента с центроидом вообще. Вектор/keyword — только
   для нод БЕЗ готовых связей (новая тема/персонаж). **Оценка: стоит
   добавить как первичный сигнал** — дёшево, инфраструктура (имена) уже
   есть, и это ортогонально текущей логит-формуле, не конфликтует.
2. **kNN вместо центроида.** Сравнивать новую ноду с K конкретными
   ближайшими нодами по эмбедингу СРЕДИ ВСЕХ регионов (голосование), а не с
   одной усреднённой точкой региона. Решает проблему многотемных регионов
   (центроид усреднил бы разнородные темы в бессмысленную точку). **Оценка:
   держать как апгрейд**, если центроид на практике окажется слишком
   грубым.
3. **Периодическая batch-пересборка кластеров** (k-means/иерархическая НАД
   ВСЕМИ нодами разом, не por-node online-решение). Снимает дрейф
   полностью, но ноды могут ПЕРЕСКАКИВАТЬ между регионами при пересборке.
   **Оценка: вычеркнуть** — конфликтует с требованием стабильности
   защищённых узлов/топологии соседства регионов.
4. **Чистое решение LLM, без математики вообще** (исходная идея до решения
   экономить вызовы SideCar). Технически другая парадигма, но
   противоречит уже принятому принципу минимизации вызовов и менее
   стабильна без фиксированной рубрики. **Оценка: не годится**, уже отвергнуто
   раньше по другой причине (стоимость), здесь просто фиксируем, что и по
   стабильности тоже не лучше.

## Каскад размещения ноды (объединяет маяки + регионы + SideCar-фоллбек)

Собрано пользователем в единый пайплайн — реально закрывает риск порчи
центроида региона неуверенным/неверным попаданием, поднятый в оценке выше:

1. **Маяки — приоритет №1.** Текущие маяки (уже загруженные под ретрив
   этого хода) проверяются первыми — текущий момент разговора и так с ними
   связан, дёшево (не новый вызов, переиспользование).
2. **Не подошло → полная система региона** (логит-формула вектор+keyword,
   плюс связи по имени персонажа — секция выше).
3. **Всё ещё неуверенно → отдельное хранилище-накопитель** ("нода ожидает
   подключения"), НЕ принудительное размещение в лучший-из-плохих регион.
   Продолжает перепроверяться по той же системе со временем/по мере
   эволюции графа.
4. **SideCar батчем, редко** — только "совсем потеряшки" (не разместились
   после накопителя), сразу несколько нод на одно суждение полноценной LLM
   разом — амортизирует стоимость вызова.

**Оценка**: сильное дополнение, снимает риск дрейфа центроида от слабых
попаданий явно (неуверенные ноды просто не попадают в регион вообще, а не
портят его). Два места нужно решить явно, иначе накопитель рискует стать
чёрной дырой:
- **Видимость для ретрива, пока нода в накопителе** — у ноды уже есть
  эмбединг, логично оставить её доступной как отдельный маяк напрямую (без
  региона/связей), а не прятать до размещения — иначе факт эффективно
  теряется на неопределённый срок.
- **Порог "совсем потеряшка"** — сколько циклов/попыток висения в
  накопителе до батч-эскалации к SideCar. Без явного порога условие
  эскалации может никогда не сработать, и накопитель растёт бесконечно.
Оба пункта решены (см. ниже) — конкретная state machine, готова к реализации.

### State machine накопителя — конкретные числа

- **Видимость**: НЕВИДИМА для ретрива, пока нода в накопителе (закрывает
  первый открытый пункт выше).
- **Попытка 1** (при создании ноды): каскад маяки→регион. Нет явного
  победителя → в накопитель, невидима.
- **Ретрай через 5 ходов**: каскад повторяется против текущего состояния
  графа. Победитель есть → размещается, покидает накопитель.
- **Попытка 2 тоже без победителя**: нода ждёт ЛИБО (a) пока накопится
  пачка из 5 таких же "дважды не размещённых" нод, ЛИБО (b) ещё 20 ходов —
  что раньше, то и триггерит отправку. Батч (даже неполный, если сработал
  таймаут) уходит на суждение SideCar разом.
- Худший случай задержки одной ноды до финального решения — около 30 ходов
  (5+5+20), не бесконечность. Тот же паттерн, что у флаша очереди сообщений
  "по размеру ИЛИ по времени, что раньше" (Kafka producer batching и т.п.) —
  проверенное инженерное решение, не изобретение с нуля.
- **Решено**: если SideCar сам не может уверенно разместить ноду из батча —
  нода ПРОСТО ОТБРАСЫВАЕТСЯ (не force-placement в ближайший регион, не
  вечное хранение). Правильный выбор в духе всей системы: не портить
  структуру региона натянутым размещением, не плодить постоянную "чёрную
  дыру" в накопителе. Риск потери факта есть, но это уже редкий крайний
  случай (дважды не прошёл математику И не прошёл суждение полноценной
  LLM) — приемлемый компромисс.

**Каскад размещения ноды полностью специфицирован, открытых пунктов не
осталось.**

### Три решения перед стартом реализации Phase 1

1. **Порог "сильного изменения" — ДИНАМИЧЕСКИЙ, не фиксированный.**
   Подстраивается в рамках одного графа/чата, не абсолютная константа —
   разные кампании имеют разный разброс эмбединг-дистанций, фиксированное
   число работало бы плохо универсально. Реализация: бегущее
   среднее+отклонение расстояний (экспоненциальное скользящее, не хранить
   всю историю), триггер — `distance > mean + k·stddev`, `k` — единственный
   настраиваемый множитель (дефолт даю сам при реализации, DEFAULT_SETTINGS
   как у BasicSummary).
2. **Бутстрап региона — два разных пути:**
   - **Есть активный Lorebook у игрока** → граф ДОЛЖЕН перестроиться из
     него при инициализации — новая интеграция, не заложенная в
     первоначальный план: чтение через уже существующие
     `lorebook.find()`/`lorebook.get()` ([cores/lorebook/index.js](cores/lorebook/index.js)),
     каждая запись проходит через (вариант) каскада размещения, чтобы
     засеять начальные регионы/центры. Одноразовая операция при бутстрапе,
     освобождена от обычного "минимизировать вызовы SideCar" — это
     разовый импорт, не текущая работа.
   - **Новый мир, WI пуст** → SideCar получает ПОДСКАЗКУ в промпте
     ("рассмотри Локации/ГГ/Персонажей как кандидатов на исходные центры"),
     но решает сам, сколько из 5 регионов реально завести и какие именно —
     НЕ жёсткий список из 3, секторы остаются свободными по духу уже
     принятого решения "секторы решает LLM".
3. **Decay без RP Time (gameTime = null)** — фолбэк на число сообщений с
   момента создания ноды, тот же принцип, что уже есть у BasicSummary
   (`protectedWindow`-стиль). Когда RP Time активен — decay считается по
   игровому времени; когда нет — по числу сообщений. Оба режима — не выбор
   пользователя, а автоматическое переключение по наличию `gameTime`.

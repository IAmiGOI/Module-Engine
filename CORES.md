# ST Module Engine — Beta: каталог Ядер

Черновой каталог всех Ядер, которые нужны системе, по мотивам
[ARCHITECTURE.md](ARCHITECTURE.md). Только перечисление и назначение — без
кода, без API, без сигнатур. Цель — увидеть всю картину и не забыть ни одно
Ядро, прежде чем переходить к написанию хоть чего-то.

Приоритет 1 — высший, 5 — низший (порядок разработки).

См. также [UI.md](UI.md) — философия интерфейса (слои, иерархия, цвет,
кнопки, сворачиваемость). И [PIPELINE.md](PIPELINE.md) — как Ядро пайплайнов, Ядро жизненного
цикла генерации и Ядро внутреннего Prompt Manager складываются в рабочий
пайплайн генерации.

## Модельные Ядра (бывшее единое "Ядро SideCar" — разделено)

"Ядро SideCar" убрано как единая сущность — разделено на отдельные Ядра по
типу модели, у каждого свои connection-семантика/доступность:

| Ядро | Приоритет | Назначение |
|---|---|---|
| ✅ **Ядро внутренних моделей движка** (бывший SideCar) | 1 (реализовано) | [cores/models/internal-engine.js](cores/models/internal-engine.js) — удалённые API-совместимые воркеры (openai/anthropic/google-формат; то, чем был весь SideCar в Alpha) — основная рабочая лошадка. Регистрирует `model.generate` на Шине ядер; сам не делает HTTP — строит запрос через [provider-request.js](libraries/core/provider-request.js) и балансирует через [dispatch-queue.js](libraries/core/dispatch-queue.js), реальный вызов идёт через `host.network` (Гейт для сети → Сервис HTTP), тот же Ядро/Сервис-разрез, что и у DOM. Требует `networkAccess: true` при регистрации — без него физически не достучится до сети. Настройки воркеров реально персистятся через `storage.settings` ([persisted-list.js](libraries/core/persisted-list.js) — `configureWorkers()` пишет, `restoreWorkers()` читает при старте движка); проверено настоящей перезагрузкой страницы харнесса, не только тестом. `model.generate` принимает опциональный `workerId` — пиннинг на конкретного воркера (всё ещё через ту же очередь, просто пул кандидатов сужен до одного), для Ядра трекинга ("каждый трекер привязан к сайдкару"); без него — обычный пул с балансировкой. |
| **Ядро основной модели ST и API пресетов** | 2 | Подключение к ГЛАВНОЙ модели самого ST (то, что пользователь настроил в самом SillyTavern для обычной генерации) + её пресетам/сэмплерам. |
| **Ядро эмбеддинг моделей** | 2 | Text→vector, отдельный контракт от генерации текста (как Embedding в Alpha, но теперь полноценное отдельное Ядро, не подкапот SidecarManager). |
| **Ядро локал-хост моделей** | 3 | Модели, которые крутятся на машине пользователя локально (свой connection-профиль, не сеть вовне). |
| **Ядро TTS моделей** | 5 | Text-to-speech. |
| **Ядро diffusion** | 5 | Генерация изображений. |

**Общая Библиотека для очереди+балансировки+диспатча — реализована**:
[libraries/core/dispatch-queue.js](libraries/core/dispatch-queue.js), уже
используется Ядром внутренних моделей движка выше и предназначена для
остальных 4 модельных Ядер тоже (сам по себе не знает ни про HTTP, ни про
конкретную форму запроса — только "какой воркер и когда"). Формат
запроса/ответа для HTTP-совместимых провайдеров —
[libraries/core/provider-request.js](libraries/core/provider-request.js),
чистые функции, без сети.

Оба выше — тонкие обёртки с разной семантикой над одним общим механизмом:
[libraries/shared/ui-mount-registry.js](libraries/shared/ui-mount-registry.js)
(каждый ключ — свой независимый Final UI, иначе пути деревьев сталкиваются

ARCHITECTURE.md, где сначала была ошибочная попытка обойти это, потом исправлено). Сквозной тест signal→diff→реальный Гейт→реальное дерево пройден. |
| ✅ **Ядро подвала сообщения** | 1 (реализовано) | [cores/ui/message-footer.js](cores/ui/message-footer.js) — полоса во всю ширину чата под последним сообщением, ровно ТРИ места под независимые виджеты (у каждого свой Final UI). Контракты `ui.messageFooter.claim/release/slots`. **Модель этого не видит и не может увидеть**: подвал живёт только в DOM, в `message.mes` не пишется ничего, и Ядру нечем туда написать — контракта на правку сообщения оно не знает. **Защита от перерисовки НЕ кооперативная** (в отличие от Alpha, где бейдж выживал, только если правивший вежливо звал `reapply()` — реролл и ручная правка не звали, и бейдж подтверждённо пропадал): три рубежа — события ST, наблюдатель за `#chat` на случай перерисовки без событий, и идемпотентный `attach()`, который чинит только реально отвалившееся. |
| ✅ **Ядро уведомлений** | 1 (реализовано) | [cores/ui/notifications.js](cores/ui/notifications.js) — одна общая плавающая полоса сообщений в углу ЭКРАНА, контракт `ui.notify` доступен любому Ядру и (через Гейт) Модулю. **Почему отдельное Ядро, а не слот**: у поверхности есть свой жизненный цикл — очередь, потолок в 4 штуки, автоснятие по времени, схлопывание повторов; как только появляется жизненный цикл, это уже не слот. Место ему при этом даёт обычный именованный слот Ядра UI для Engine — своего механизма монтирования не заводится. Появилось затем, что словесные результаты («OK · 3117ms») жили плашками внутри карточек и растягивали блок, к которому относились. |
| ✅ **Ядро панели движка** | 1 (реализовано) | [cores/ui/engine-panel.js](cores/ui/engine-panel.js) — сам экран движка: слева живое состояние Ядер/Сервисов (реестр контрактов, состояние прогона, счётчик событий), справа Модули. **Почему Ядро, а не Модуль** — по критерию из ARCHITECTURE.md: Модуль подключает пользователь, без Ядра движок не работает; экран настроек движка нельзя «не подключить». Ничего не знает про DOM и ST напрямую: строится из [libraries/shared/widgets.js](libraries/shared/widgets.js), данные берёт ТОЛЬКО через контракты и события (`model.workers.get/set`, `model.generate` для кнопки Test, события `events.any` и `generation.beforeSend`/`generation.completed`, плюс интроспекция Директора `contracts()`), рисуется через Ядро финального UI. |
| **Ядро финального UI для Android** | 4 | То же самое, для Android. |
| **Ядро финального UI для iOS** | 5 | То же самое, для iOS. |

✅ **Примитивы готовы и протестированы** —
[cores/ui/reactive.js](cores/ui/reactive.js) (сигналы/effect),
[tree.js](cores/ui/tree.js) (`h()`), [diff.js](cores/ui/diff.js)
(keyed + fine-grained диффинг). Уточнение по факту кода: это ОДНО общее
"Ядро UI" (примитивы), а не 3 отдельные реализации реактивности — "Ядро UI
модулей" и "Ядро UI для Engine" из таблицы выше не отдельный код, а разные
ПОТРЕБИТЕЛИ одного и того же примитива (какой контент через него рендерится).
Только "Ядро финального UI" по платформам — генуинно отдельный код на
каждую (patch-applier, применяющий один и тот же поток патчей по-разному).

## Ядра из систематического прохода по модулям Alpha

Вопрос к каждому модулю Alpha: это конкретная фича, которую пользователь
включает (остаётся Модулем), или переиспользуемая инфраструктура, на которой
строятся другие вещи (становится Ядром + тонкий Модуль/UI поверх)?

| Было в Alpha | Становится | Почему |
|---|---|---|
| **Tracker** | ✅ **Ядро трекинга** — [cores/tracking/index.js](cores/tracking/index.js) (реализовано) | Конфигурируемые поля + триггеры опроса + публикация — уже в Alpha использовалось как сервис-провайдер другими модулями (Music дёргал `classify`), не просто фича. Два вида трекера — `user`/`system` — оба привязаны к конкретному воркеру Ядра внутренних моделей движка (`workerId`, через новый параметр пиннинга в `model.generate` — см. это Ядро). Триггер опроса — список имён событий Шины событий (любое из PIPELINE.md `generation.*`, или произвольное своё) — несколько триггеров на трекер одновременно; ручной опрос — тот же `tracking.poll` напрямую. Обновление ВСЕГДА публикует событие — `tracking.blocks.changed` для user, `tracking.systemBlocks.changed` для system, структурно разделены. User-трекер при каждом обновлении поля зовёт `onUserFieldRegistered` — теперь реально подключено к Ядру исполнения макросов ([harness/engine-wiring.js](harness/engine-wiring.js), см. ниже); system-трекер её не зовёт вовсе. Промпт строится через новую [fill-template.js](libraries/core/fill-template.js), ответ модели разбирается через новую [parse-model-json.js](libraries/core/parse-model-json.js) — обе анонсированы в LIBRARIES.md заранее. Конфигурация трекеров реально персистится через `storage.settings` ([persisted-list.js](libraries/core/persisted-list.js) — `configureTrackers()`/`restoreTrackers()`), как и у Ядра внутренних моделей движка. |
| **RP Time** | Схлопывается, отдельного кода нет | По сути Трекер с одним предопределённым полем ("время") и мульти-сообщенческим контекстом — просто дефолтный конфиг Ядра трекинга. |
| **Macros** | ✅ **Ядро исполнения макросов** — [cores/macros/index.js](cores/macros/index.js) (реализовано) | Мини-язык выполнения программ ([macro-language.js](libraries/core/macro-language.js) — токенизатор/парсер/интерпретатор, перенесён из Alpha почти без изменений: уже был чистой Библиотекой там), не привязан к конкретной фиче — движок, не фича. Два источника `{{macro}}`: пользовательские программы (`kind: 'text'`/`'code'`, через `configurePrograms()`) и внешние value-макросы (`setValueMacro()`/`clearValueMacro()` — именно сюда стучится Ядро трекинга). ST зовёт зарегистрированный handler синхронно на каждый `{{name}}` — handler просто читает уже закэшированное значение; async-обновление кэша (`runProgram()`) идёт по тому же триггер-событийному принципу, что и Ядро трекинга. `get "trackerId:fieldName"` внутри code-программы читает `tracking.value` (единственный подключённый источник на сейчас); голое `get "key"`/`save x as "key"` — собственное состояние программы через `storage.chatMemory`. Упавшая программа кэширует `[macro error: name]` — {{macro}} никогда не пропадает молча (то же поведение, что в Alpha). Реальная регистрация в ST — тонкий Сервис [st-macros.js](services/st-macros.js) (`context.macros.register` + легаси `context.registerMacro`-фоллбэк, скопировано с уже проверенного кода Alpha). Конфигурация программ реально персистится через `storage.settings` ([persisted-list.js](libraries/core/persisted-list.js) — `configurePrograms()`/`restorePrograms()`), третий реальный потребитель той же Библиотеки. |
| Post-Turn Processor | ✅ **Ядро пайплайнов** — [cores/pipeline/index.js](cores/pipeline/index.js) (реализовано) | Генерический исполнитель объявленного набора этапов; про генерацию и промпт не знает ничего, Ядро жизненного цикла — его первый ПОТРЕБИТЕЛЬ, а не владелец. Этап это ДАННЫЕ (`{id, contract, params, needs, fallbacks, onExhausted}`), не колбэк — иначе Гейт не проверит, что этап реально делает, а определение нельзя ни показать, ни сохранить. Режимы `collect` (DAG, независимое параллельно) и `fold` (цепочка над одним значением); параллельность — следствие графа, а не третий режим. **Реестр этапов ЕСТЬ Блок**: `pipeline.stages.add` и есть регистрация в Блоке, смена состава публикует `pipeline.stagesChanged` — отдельного механизма discovery не заводится. **Этап исполняется под правами СВОЕГО владельца** (`resolveAs` из сборки движка), владелец берётся от Директора, а не из `params` — иначе пайплайн был бы обходным путём вокруг Гейтов. Отказ: цепочка `fallbacks` (другой воркер/другой контракт/пауза), исчерпана — `onExhausted: 'abort'` роняет весь пайплайн (`'flag'` уже работает, это будущий переключатель). Таймаут динамический: спрашивает `statistics.expectedDuration`, если поставщик есть, иначе считает по своим замерам. |
| Lorebook Service | **Ядро работы с WI** (+ тонкий Сервис для реального loadWorldInfo) | В Alpha логика (resolveBookNames/merge/publish) была смешана с прямыми ST-вызовами в одном файле — по нашим правилам это обязано разъехаться. |

## Закрытые вопросы

- **Мультиплатформенность — подтверждена как реальная цель**, не "было бы
  неплохо". Beta целится не только в ST-браузерное расширение, но и в
  отдельные PC/Android/iOS-приложения, разделяющие ту же логику
  модулей/ядер через один и тот же абстрактный UI-дифф + разные Финальные
  UI Ядра-адаптеры. Причина закладывать это заранее: если архитектура уже
  это предусматривает, вероятность, что это реально будет сделано — выше.
- **5 модельных Ядер разделяют общую Библиотеку** для паттерна
  очередь+балансировка-по-нагрузке+диспатч — подтверждено и реализовано, см.
  таблицу выше.
- **Ядро синхронизации** — шире, чем просто настройки: желательно
  транслировать **весь контекст ST** между устройствами пользователя, не
  только состояние модулей/ядер через Ядро сохранения.
- **Ядро логирования / Ядро Dev-panel** — разделение "данные / презентация"
  подтверждено верно.

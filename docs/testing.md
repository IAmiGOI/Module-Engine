# Тесты и типизация

## Два уровня тестов

**Юнит-тесты** проверяют одну чистую функцию, одно ядро или один модуль. Всё вокруг (шины, контекст) подменяется минимальным фейком под конкретный тест. Тестов много, каждый проверяет одно поведение или один баг.

**Сценарные тесты** поднимают настоящий движок целиком: Runner, шины, шлюзы, ядро прав, ядра и модули. Подменяется только слой сервисов, потому что это единственная граница с внешним миром. Фейки для этого уже есть в `libraries/shared/fake-buses.js`, отдельный тестовый фреймворк не нужен.

Пример сценария: пользователь отправил сообщение, ядро трекинга опросило модель, значение опубликовано, макрос его подставил. Весь путь проходит через настоящие шины, шлюзы и права, а «модель» на другом конце сервиса отвечает заранее заданными данными.

Когда какой уровень:

- юнит-тест пишется для каждой функции, ядра и модуля, по ходу написания;
- сценарный тест пишется для каждого значимого сквозного сценария, то есть того, что реально делает пользователь. Он доказывает, что слои правильно работают вместе.

## Правила

- **Имя теста это полное предложение о поведении**, а не `testFoo1` или `edge case 2`.
- **Регрессионный тест должен ловить свой баг.** Перед коммитом временно откатите исправление, убедитесь, что тест падает с ожидаемым сообщением, и верните исправление.
- **Чистая логика выносится из ядра** в отдельные функции или библиотеки, чтобы проверять её без подъёма всего ядра.

## Команды

```bash
npm test                     # все тесты, node --test
npm run typecheck            # проверка типов во всех файлах с // @ts-check
npm run typecheck:progress   # сколько файлов под проверкой и где остались ошибки
```

Нужен Node.js 22 или новее.

## Типизация без TypeScript

Типы записываются в JSDoc внутри обычных `.js` файлов. Нет `.ts`, нет сборки и нет новых зависимостей: в продакшн уходит ровно тот код, который написан. Компилятор TypeScript используется только как проверяющий, он скачивается через `npx` при первом запуске и в движок не импортируется.

Зачем: движок состоит из шин, контрактов и множества модулей, которые обмениваются простыми объектами. Самые дорогие баги здесь это несовпадение формы, до которого тесты не дошли: не то поле в конверте, `null` на одной из веток, унаследованное свойство, принятое за ключ. Проверка типов находит такие ошибки ещё при наборе кода.

### Как это работает

1. Файл включается в проверку строкой `// @ts-check` в самом начале. Файл без неё не проверяется.
2. Режим строгий (`strict: true` в `jsconfig.json`). Включённый файл обязан проходить проверку без ошибок. `@ts-ignore` в проверяемых файлах не используется.
3. Включение постепенное: `checkJs` глобально выключен, поэтому непроверяемые файлы не ломают `npm run typecheck`. Однажды включённый файл остаётся без ошибок.

Редакторы с поддержкой JSDoc (VS Code, WebStorm) читают `jsconfig.json` и показывают те же ошибки при наборе.

### Где лежат типы

Типы описаны через `@typedef` в отдельных файлах без кода. Каждый такой файл заканчивается `export {};`.

| Файл | Что описывает |
|---|---|
| `libraries/shared/bus-types.js` | `Envelope`, `Host`, `Engine`, шины, шлюзы, `RightsConfig`, `RightsCore` |
| `cores/ui/ui-types.js` | `Signal`, `UiNode`, `UiProps`, `UiChild` |
| `libraries/core/module-types.js` | Заголовок модуля, `Analysis`, формы Runner и установщика |

```js
// @ts-check
/** @typedef {import('../shared/bus-types.js').Host} Host */
/** @template [T=any] @typedef {import('../../cores/ui/ui-types.js').Signal<T>} Signal */
```

### Как писать аннотации

- Описание функции и теги `@param`/`@returns` пишутся одним блоком `/** ... */` прямо над функцией. `@typedef` ставятся в начале файла.
- Точные объединения лучше `any`. `Envelope<T>` это `{ ok: true, value: T } | { ok: false, error }`, и сужение делается проверкой `if (!result.ok) return`, а не приведением типа.
- Данные снаружи (разобранный JSON, значения из хранилища, ответы GitHub) имеют тип `unknown` и проверяются.
- Приведение `/** @type {X} */ (value)` используется только там, где компилятор не может знать того, что гарантирует код, и сопровождается комментарием.
- Тип не расширяется ради того, чтобы убрать ошибку. Сначала стоит проверить, не настоящий ли это баг.
- Пустым коллекциям нужен явный тип: `/** @type {Map<string, Entry>} */ const byId = new Map();`.

### Как включить новый файл

1. `npm run typecheck:progress`, выбрать файл с небольшим числом ошибок, лучше тот, который импортирует уже типизированный код.
2. Добавить `// @ts-check` и запустить `npm run typecheck`.
3. Исправлять изнутри наружу: общие типы, потом сигнатуры, потом локальные переменные.
4. Прогнать тесты этой области.
5. Если проверка нашла настоящий баг, исправить его и добавить регрессионный тест.

Порядок: листовые библиотеки `libraries/core`, затем сервисы, затем ядра, которые уже используют типизированные шины. Большие ядра (`memory-graph`, `sync`, `ui`) в последнюю очередь, предварительно разделив их на файлы поменьше.

### Что пока не покрыто

- **Контракты не типизированы.** Шина не знает, что `storage.settings.get` принимает `{ namespace, key, fallback }`. Карта «имя контракта: параметры и результат» дала бы типизированные вызовы `request()`, её стоит вводить по одному контракту.
- **Тесты не проверяются** (`tests/` исключён), потому что в них намеренно используются частичные заглушки.
- **Модули из каталога** проверить из движка нельзя. Автор модуля может включить `// @ts-check` у себя и использовать типы выше.

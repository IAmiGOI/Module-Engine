# Архитектура

Как устроен движок: слои, шины, контракты, права и обработка ошибок. Загрузка модулей описана отдельно в [runtime.md](runtime.md), пайплайн генерации в [pipeline.md](pipeline.md).

## Принципы

Любое спорное решение в движке проверяется по этому списку, в порядке приоритета.

1. **Модуль пишется просто.** Автор модуля знает минимум инфраструктуры. Подписки, ожидание условий, выбор поставщика и повторные попытки берут на себя ядра и шины.
2. **Любой слой заменяем.** Ядро или сервис можно заменить или расширить, не трогая остальной код.
3. **Связи динамические.** Контракты, события и поставщики регистрируются и снимаются в рантайме. Согласованием занимается шина, а не модуль.
4. **Модули совместимы друг с другом.** Модуль просит возможность по имени и не знает, кто её реализует.
5. **Изменения SillyTavern изолированы.** Всё, что зависит от SillyTavern, живёт в одном слое.
6. **Plug and play.** Модуль включается и выключается без перезагрузки и без правок в чужом коде.

## Пять слоёв

| Слой | Папка | Роль |
|---|---|---|
| Runner | `cores/runner` | Поднимает систему по порядку: сервисы, библиотеки, ядра, модули. Помнит, какие модули включены, и восстанавливает их при запуске. |
| Services | `services/` | Единственный слой, который обращается к внешнему миру: API SillyTavern, DOM, сеть, таймеры, хранилища браузера. Без бизнес-логики. |
| Libraries | `libraries/` | Чистые функции без состояния и без внешнего мира. `core/` для ядер, `shared/` для всех. |
| Cores | `cores/` | Логика движка. SillyTavern напрямую не трогают, друг друга напрямую не знают. |
| Modules | `modules/` | То, что подключает пользователь. Почти без инфраструктурного кода. |

**Ядро или модуль.** Модуль подключает пользователь, а без ядра движок не работает. Интерфейс движка поэтому ядро, а Notebook, Music или Dice это модули: движок работает и без них.

Сервис нельзя вызвать по ссылке на файл. Доступ к нему есть только через шину сервисов, даже когда поставщик всего один. Так права проверяются на каждом обращении, включая обращения к DOM.

## Шины

| Шина | В `host` | Что по ней ходит |
|---|---|---|
| События | `host.events` | Широковещательные события: от SillyTavern (через `services/st-events.js`) и от ядер и модулей |
| Ядра | `host.cores` | Вызовы контрактов, которые реализуют ядра |
| Модули | `host.modules` | Вызовы контрактов, которые реализуют модули |
| Сервисы | `host.services` | Единственный путь к сервисам |
| Сеть | `host.network` | Единственный путь в интернет, контракты `http.*` |
| Своя | `host.own` | Шина собственного домена, без шлюза |

Шина сети физически отдельная. Если бы `http.*` жили на шине сервисов, любой вызывающий с правом на какой-нибудь сервисный контракт мог бы дойти до сети через обычный шлюз, и проверка сетевого права не выполнилась бы вовсе. Отдельная шина делает такой обход невозможным, а не маловероятным.

### Контракты

Контракт это имя запроса с заранее оговорённой формой параметров и ответа. Поставщик регистрирует обработчик, заказчик просит по имени. Других способов адресации на шинах нет.

```js
// поставщик
host.own.register('dice.roll', ({ sides = 6 }) => 1 + Math.floor(Math.random() * sides));

// заказчик
const result = await request(host.modules, 'dice.roll', { params: { sides: 20 } });
if (result.ok) console.log(result.value);
```

У шины два метода:

- `subscribe(contract, { params, when }, callback)` это постоянная подписка. Условие `when` описывает, когда доставлять ответ: по событию, на каждое N-е событие, по таймеру. Модификаторы `debounceMs`, `throttleMs`, `dedupe`, `once` тоже задаются здесь. Счётчики и таймеры поэтому не пишутся ни в одном модуле, весь словарь условий живёт в шине (`libraries/shared/delivery-filters.js`).
- `contracts()` показывает, что зарегистрировано и сколько поставщиков у каждого контракта. Через этот метод ничего нельзя исполнить, он нужен для панели состояния движка.

Разовый запрос `request()` (`libraries/shared/request.js`) это не примитив шины, а обёртка над `subscribe()`: подписаться, дождаться первого ответа, отписаться. Таймаут опционален.

Если поставщиков несколько, шина выбирает наименее загруженного по метрике, которую поставщик передал при регистрации (`loadMetric`).

### Конверт ответа

Любой ответ приходит в одной форме:

```js
{ ok: true, value }
{ ok: false, error: { message, code? } }
```

- Шина перехватывает исключение на каждом шаге цепочки. Сырое исключение не пересекает границу шины никогда.
- `request()` не отклоняет промис. Ошибку видно по `ok: false`.
- Упавший подписчик не мешает доставке остальным.
- Контракт без поставщика возвращает тот же отказ, что и любая другая ошибка. Поэтому вызов инструмента, который модель выдумала, не требует отдельной обработки.

### Блоки

Внутри шины записи группируются в блоки по категориям, например `pipeline.stages` или `picker.insertableValues`. Когда содержимое блока меняется, владелец публикует событие `<блок>.changed`, и потребители перечитывают состав обычным запросом. Так новый модуль попадает в чужой список без правок в чужом коде: он регистрирует запись в известной категории, и её подхватывает любой потребитель этой категории.

### События `started` / `completed` / `failed`

Тройку событий получает не каждый контракт, а только операция, которая:

- трогает SillyTavern (DOM, её события, её API) и поэтому непредсказуема по времени;
- может частично не выполниться или зависит от внешнего состояния;
- иногда легитимно ничего не делает, и вызывающему важно отличить «случилось» от «пропущено»;
- длится неопределённое время.

Имя события повторяет имя контракта: `ui.messageFooter.attach.completed`. Подписчик сразу видит, к какому действию оно относится.

## Шлюзы и права

Каждый переход между доменами (модуль к ядру, ядро к сервису и так далее) проходит через шлюз (`libraries/shared/gate.js`). Шлюз не выбирает поставщика, он только проверяет права. Выбор делает шина на той стороне.

```
Ядро -> шина ядер -> шлюз (права) -> шина сервисов (выбор поставщика) -> сервис
```

Права вызывающего знает реестр ядра прав (`cores/rights`), который заполняется при регистрации. Вызывающий не может заявить свои права сам или подделать чужое имя: шлюз передаёт поставщику настоящий `callerId` вторым аргументом (`handler(params, { callerId })`).

Приоритет запроса влияет только на порядок в очереди. Проверка прав выполняется всегда, для любого приоритета.

### Уровни доверия

| Уровень | Кому | Права |
|---|---|---|
| `official` | Встроенные ядра и модули | Без ограничений по контрактам |
| `community` | Проверенные сторонние модули | Только явно разрешённые контракты |
| `scanned-safe` | Сторонний модуль, в котором сканер не нашёл опасного | Всё, кроме запрещённого сканом |
| `scanned-unsafe` | Сторонний модуль с подозрительными находками | То же, но с более строгим списком запретов |

Права плоские: один набор на модуль, а не на каждый вызов.

**Сеть** это отдельное право `networkAccess`, оно не следует из уровня. Даже `official` по умолчанию не ходит в интернет. Проверяет его сетевой шлюз (`libraries/shared/network-gate.js`) при подписке и при каждой доставке.

**Нарушение.** Если сторонний модуль просит то, что ему не положено, он попадает в карантин: модуль отключается, на его карточке появляется метка, текущая генерация продолжается. Подробности в [runtime.md](runtime.md#карантин).

### Исполнение от чужого имени

`engine.resolveAs(callerId, contract, params)` исполняет контракт с правами другого вызывающего, через тот же шлюз. Эту возможность получает только ядро пайплайнов. Оно исполняет этапы, которые объявили модули, и без `resolveAs` делало бы это со своими правами: модуль мог бы объявить этап и получить доступ, которого у него нет.

## Хранение данных

Модули и ядра не пишут в настройки SillyTavern напрямую. Путь всегда один:

```
модуль -> шлюз -> ядро хранения (пространства имён) -> сервис (запись)
```

| Ядро | Контракты | Что хранит |
|---|---|---|
| `cores/settings` | `storage.settings.*` | Настройки и конфигурация |
| `cores/memory` | `storage.chatMemory.*` | Данные, привязанные к чату |

Пространство имён передаётся параметром запроса. Шлюз проверяет право вызвать контракт, но не то, в какое пространство пишет вызов. Для `official` это не важно, а сторонний модуль без явного права до этих контрактов не дойдёт.

## Генерация

Движок не дописывает свой кусок к промпту SillyTavern, а ведёт отправку на модель целиком (`services/st-generation.js`). Цена такого решения в том, что стороннее расширение, которое рассчитывает на нетронутый путь отправки SillyTavern, может работать иначе. Поэтому движок обязан вести отправку аккуратно:

- незнакомое тело запроса уходит нетронутым;
- обёртка `fetch` смотрит только на пути генерации и только на POST;
- `uninstall()` возвращает SillyTavern её собственный `fetch` и не оставляет следов;
- отказ пайплайна отменяет генерацию, а не отправляет неполный промпт.

Подробно в [pipeline.md](pipeline.md).

## Приоритет запросов

Приоритет обычно задаёт поставщик при регистрации контракта: интерфейс регистрируется как `immediate`, фоновые вызовы модели как `queued`. Исключение `model.generate`: один и тот же контракт обслуживает и ответ пользователю, и фоновые проверки, поэтому приоритет передаётся в вызове (`request(bus, contract, { priority })`) и решает порядок в очереди `libraries/core/dispatch-queue.js`.

## Сообщения для модели

`model.generate` принимает `messages: [{ role, content }, ...]` с любым числом ходов. Короткая форма `prompt` и `systemPrompt` разворачивается в два сообщения. Многоходовый формат поддержан для OpenAI-совместимых API. Для форматов `google` и `anthropic` поле `messages` игнорируется, и запрос строится из `prompt` и `systemPrompt`.

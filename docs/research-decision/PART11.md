# Директор, часть 11: проверка ответа писателя классификатором

**Решение владельца** (`DIRECTOR-SPEC.md`, раздел «Скрипты по классификатору»):
- Классификатор проверяет текст писателя **по мере стриминга**.
- При нарушении **обрывается всё сообщение целиком**, и писатель пишет ответ заново с дополнительным промптом о причине. **Не по абзацам.**
- **Вариант Б:** стрим держится до конца проверки. Пользователь видит только готовый проверенный ответ и перезапусков не видит.

Тексты утверждений и промпта переписывания — `PROMPTS.md`, раздел 13, **дословно**.

Ветка `research/decision`. **Делать после части 10** — она меняет те же файлы директора. Если часть 10 ещё в работе, дождаться её STOP.

## Замысел
- Работает, когда писатель ходит через **подключение ME** (прокси части 6, `cores/decision/writer-proxy.js`). Там ME сам получает поток от модели и сам отдаёт ответ ST.
- Если у писателя выбрано «SillyTavern connection», проверки нет: поток идёт мимо ME. Это записать в отчёт.
- **Ход проверки:**
  1. Прокси читает поток писателя, **ничего не отдавая ST**.
  2. Каждые ~150 токенов и в конце — запрос к классификатору по накопленному тексту, с двумя утверждениями: `user_agency` и `past_resolution`. Срез: Push хода, последнее сообщение пользователя, накопленный ответ.
  3. Вероятность выше порога (настройка, по умолчанию **0,85**) → поток писателя **обрывается сразу** (`AbortController`), запрос отменяется.
  4. **Цитата для причины:** после обрыва — один запрос к классификатору по предложениям оборванного текста с тем же утверждением. Самое вероятное предложение и есть `{{quote}}`. Не вышло — строка причины без цитаты.
  5. Новый запрос писателю: тот же контекст + промпт переписывания из раздела 13 системным сообщением **после Push**, с причинами и номером попытки.
  6. **Не больше двух переписываний.** Третья попытка с нарушением всё равно отдаётся, с пометкой в окне директора.
  7. Ответ прошёл (или исчерпаны попытки) → готовый текст отдаётся ST в той форме, какой ST ждёт. При стриминге — потоком SSE, хоть одним-двумя кадрами. «Стоп» ST в любой момент обрывает и писателя, и проверку.
- **Классификатор** — подключение из ядра Classifiers (`classifier.decide`). Какое — настройка в карточке Director / Writer, по умолчанию первое. Нет подключения или классификатор упал → ответ отдаётся без проверки, с пометкой. Ход не ломается.
- **Между 0,6 и порогом** — только пометка в окне директора, без обрыва.
- **Окно директора:** строка о каждой проверке — вероятности, обрыв, причина, номер попытки.

### q1. Проверка и переписывание
- Накопление, проверки по ходу и в конце, обрыв, поиск цитаты, промпт переписывания, лимит попыток, отдача ST.
- Настройки: подключение классификатора, порог (0,85), шаг проверки (~150 токенов), лимит переписываний (2).
- Тесты на фейковом писателе и фейковом классификаторе:
  - чистый ответ отдаётся целиком, ST видит один ответ;
  - нарушение посреди потока → поток оборван, второй запрос с промптом переписывания после Push, ST видит только второй ответ;
  - третья неудача отдаётся с пометкой;
  - классификатор упал → ответ без проверки;
  - «Стоп» обрывает всё;
  - путь через «SillyTavern connection» не трогается;
  - промпты совпадают с `PROMPTS.md`.

### q1b. Проверка формы директора — знания (добавлено владельцем)
- **Зачем:** главная живая проблема — директор путает, кто что знает. Как кодинг-агенту возвращают упавший тест, так директору возвращается форма, если персонаж действует на то, чего не знает.
- Перед принятием `submit_turn`, после проверки полей, по каждому персонажу формы — утверждение `knowledge_conflict` (раздел 14 `PROMPTS.md`, дословно).
  - Срез: последние сообщения сцены (окно директора), банк персонажа, его знания, его решение, действие и реплика.
  - Персонаж пользователя не проверяется: его действий в форме нет.
- **Выше порога** (тот же, 0,85) → `submit_turn` отвечает текстом из раздела 14 вместо принятия формы. Директор правит или записывает `character_knowledge` и вызывает снова.
- **Не больше одного возврата на персонажа за ход.** Второй раз форма принимается с пометкой в окне директора, без зацикливания.
- Персонажи проверяются **параллельно** одним запросом к классификатору, со всеми утверждениями сразу.
- Классификатор не настроен или упал → форма принимается без проверки, с пометкой.
- **Тесты:**
  - конфликт → форма возвращена с текстом раздела 14;
  - повтор с тем же конфликтом → принята с пометкой;
  - запись `character_knowledge` между попытками → вторая попытка проверяется с новыми знаниями;
  - без классификатора — без проверки;
  - персонаж пользователя не проверяется.

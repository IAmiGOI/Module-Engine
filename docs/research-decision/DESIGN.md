# Директор и прозаик: схема

Роли в коде — `decider` (директор) и `writer` (прозаик), ядро —
`cores/decision`, контракты — `decision.*`. В документации по-русски
допустимы «директор» и «прозаик».

Ядро **выключено по умолчанию**. Пока оно выключено, этапы не
регистрируются, и путь генерации остаётся ровно тем, что описан в
[LOG.md](LOG.md).

## Контракты

Публичные (на Шине ядер, доступны панели/будущим потребителям):

| Контракт | Параметры | Ответ |
|---|---|---|
| `decision.settings` | — | текущие настройки |
| `decision.configure` | `{ patch }` | сохранённые настройки |
| `decision.blocks` | — | блоки о персонаже текущего чата |
| `decision.runs` | — | записи прогонов текущего чата по `mesid` |
| `decision.lastRun` | — | последняя запись или `null` |
| `decision.reload` | — | перечитать блоки/прогоны текущего чата |

Этапные (регистрируются на `host.own`, вызываются пайплайном под правами
ядра; публичными для Модулей не считаются):

| Контракт | Где | Что делает |
|---|---|---|
| `decision.decide` | `generation.beforeSend` | собирает контекст директора, зовёт `model.generate`, разбирает ответ, кладёт прогон в память |
| `decision.rewrite` | `generation.payload` | заменяет тело основного запроса контекстом прозаика |

## События

- `decision.started` `{ runId, type }` — прогон директора начался.
- `decision.completed` `{ runId, edits, blocks, workerId }` — ответ разобран.
- `decision.failed` `{ runId, message }` — попытка директора провалилась.
- `decision.blocks.changed` `{ count }` — Блок блоков о персонаже изменился
  (имена — по `CONVENTIONS.md`: `<домен>.<категория>.changed`).

Запись прогона и правки блоков **не** коммитятся по `decision.completed`:
событие говорит «директор ответил», коммит делает Ядро жизненного цикла
генерации по успешному концу прогона (см. «Жизненный цикл»).

## Формат ответа директора

Директор отвечает **одним JSON-объектом**, без прозы вокруг:

```json
{
  "decision": "Что персонаж делает и говорит в этом ходе и чего добивается.",
  "blocks": [
    { "op": "add", "title": "Оружие", "text": "Носит кинжал под плащом." },
    { "op": "update", "id": "blk_1_alias", "text": "Уже знает, что это не сон." },
    { "op": "remove", "id": "blk_2_alias" }
  ]
}
```

- `decision` — обязательная непустая строка. Это **решение**, а не проза:
  прозаик получает его как руководство.
- `blocks` — необязательный массив правок. `op` может отсутствовать:
  существующий блок (по `id` или `title`) обновляется, несуществующий
  добавляется. `remove` надо назвать явно.
- Разбор: сначала снимается markdown-забор, затем `parseModelJson`.
  Не-JSON, не-объект, пустая/отсутствующая `decision` — **ошибка прогона**
  (повтор, затем отмена), не падение.
- Испорченные элементы `blocks` (нет текста у add/update, нет id/title у
  remove) отбрасываются по одному; из-за них прогон не падает.
- Защитные потолки: не больше 20 правок за ответ и 8000 символов на блок;
  лишнее отбрасывается с предупреждением в записи прогона.

## Хранение

### Память чата (`storage.chatMemory`, namespace `core.decision`)

`blocks` — блоки о персонаже, живут между ходами:

```json
[{ "id": "blk_1_alias", "title": "Оружие", "text": "…", "updatedAt": 0 }]
```

`runs` — записи прогонов под номером сообщения, к которому относится ход:

```json
{
  "42": {
    "id": "dec_…",
    "mesid": "42",
    "at": 0,
    "type": "normal",
    "decision": "…",
    "reasoning": "…",
    "steps": [{ "attempt": 0, "workerId": "backup", "durationMs": 0, "error": null }],
    "workerId": "…"
  }
}
```

`reasoning` — ризонинг провайдера, если его удалось прочитать из
`model.generate.raw`; у стримингового ответа его может не быть — тогда
пустая строка. `steps` — попытки директора (одна запись на попытку).

### Настройки (`storage.settings`, namespace `core.decision`, ключ `settings`)

```json
{
  "enabled": false,
  "rules": "",
  "regen": "decider",
  "decider": {
    "workerId": "", "samplerPreset": "",
    "temperature": 0.7, "topP": 1, "topK": 0, "maxTokens": 2000,
    "reasoningMode": "inherit", "reasoningEffort": "medium", "reasoningBudget": 0
  },
  "writer": {
    "workerId": "", "samplerPreset": "", "applySampler": false,
    "temperature": 0.9, "topP": 1, "topK": 0, "maxTokens": 1000
  }
}
```

- `enabled` — единственный переключатель; по умолчанию `false`.
- `rules` — правила директора, пишет пользователь; глобальные, не per-chat.
- `regen` — `decider` (по умолчанию) или `writer`: на свайпе/регенерации
  звать директора заново или только переписать прозу по прошлому решению.
- `writer.applySampler` — навязывать ли сэмплер прозаика поверх пресета PM
  и настроек ST. Ризонинг прозаика выключается **всегда**, независимо от
  этого флага.

## Состав контекстов (порядок — от стабильного к меняющемуся)

### Директор

1. **system** — роль директора + правила пользователя. Меняется только
   правкой правил.
2. **system** — все активные саммари (`summary.list`), от старых к новым.
   Только дописываются.
3. **system** — записи всех прошлых прогонов директора этого чата, от
   старых к новым: решение + ризонинг. Только дописываются.
4. **system** — блоки о персонаже. Меняются директором каждый ход.
5. **история** — последние 20 логических единиц истории, от старых к новым;
   цепочка «вызов инструмента + результат» не рвётся.
6. **user** — задание на этот ход и формат ответа. Меняется каждый ход,
   поэтому стоит последним.

Для `openai`-воркера это `messages`; для `anthropic`/`google` те же части
плющатся в `systemPrompt` + `prompt` (multi-turn у этих форматов
`model.generate` не поддерживает). Кэш префикса: стабильные правила и
саммари впереди, изменчивые блоки/решение/задание — в конце.

### Прозаик

1. **system** — роль прозаика: писать по решению, не решать самому, не
   упоминать блоки/решение/инструкцию.
2. **system** — все активные саммари, от старых к новым.
3. **system** — блоки о персонаже.
4. **system** — решение текущего хода.
5. **история** — последние 20 логических единиц, цепочки инструментов целы.

Последним сообщением остаётся хвост истории: обычный ход — реплика
пользователя, `continue` — реплика персонажа (продолжение), `impersonate` —
то, что ST собирается дописать от лица пользователя. Дополнительного
`user`-сообщения прозаику не добавляется, иначе он ответил бы не на ту
реплику.

### Что считается «последними 20 сообщениями»

- Берётся хвост **мутируемой копии `chat`**, которую ST передал
  перехватчику: в нём уже нет скрытых сообщений и видны вставки модулей.
- Логическая единица: одно обычное сообщение; либо серия
  `isToolCall`-сообщений вместе со следующим за ней настоящим ответом.
  Так пара «вызов + результат» не разрезается. Скрытые `Summary`-вставки
  из хвоста исключаются: все саммари и так идут отдельной частью.
- В API-сообщения единицы разворачиваются `chatToMessages()` из
  [libraries/core/pm-history.js](../../libraries/core/pm-history.js)
  (assistant + `tool_calls` → `tool`-результаты), поэтому прозаик видит
  историю в той же форме, что и PM.

## Точка подмены тела

`generation.payload` — `fold`-цепочка. Этап прозаика
(`decision:rewrite`) регистрируется с `needs: ['prompt-manager:rewrite']`,
если PM уже зарегистрировал свой этап. Тем самым:

- PM отрабатывает первым и, если включён, собирает свой запрос;
- прозаик идёт **последним** и перекрывает `messages` / `prompt`;
- любой будущий этап `payload` без явной зависимости окажется раньше
  прозаика; этап, которому нужно идти после, объявит `needs` на
  `decision:rewrite`.

Если PM ещё не загружен (например, узкий тест), этап сначала
регистрируется без зависимости, а по `pipeline.stagesChanged` с появлением
`prompt-manager:rewrite` перерегистрируется с `needs`.

Что берётся из тела:

- Chat Completion (`payload.messages` — массив): заменяется только
  `messages`; остальные поля тела сохраняются.
- Text Completion (`payload.prompt` — строка): заменяется `prompt`
  плоским текстом в том же порядке частей.
- Неизвестное тело (нет ни `messages`, ни `prompt`): уходит нетронутым.
- `stream` не трогается: ST разбирает ответ по своей настройке, и
  расхождение с телом сломало бы приём.
- `model` переопределяется, только если у выбранного воркера прозаика есть
  непустая модель и это не `st-main`.

**Перекрытие с PM осознанное.** Пока ядро включено, в исходящем теле
остаётся контекст прозаика, а не собранный PM пресет. Значит, вклады,
попадающие только в PM-сборку (лорбук, макросы, вставки Модулей,
Guided CoT), до прозаика не доходят. При выключенном ядре PM работает
ровно как раньше. Если Guided CoT включён вместе с ядром, шаги CoT
по-прежнему выполняются и записываются, но их вставка в тело перекрывается
прозаиком — это стоит явно советовать владельцу выключать CoT при
включённом ядре.

## Ризонинг прозаика

Выключается **всегда**:

- из тела удаляются `reasoning_effort`, `reasoning`, `include_reasoning`,
  `reasoning_budget`, `thinking`, `thinkingConfig`;
- явное выключение там, где формат говорит на своём языке:
  - `openai` + источник `openrouter` → `reasoning: { enabled: false }`;
  - `anthropic` (источник `claude`/`anthropic`) → `thinking: { type: 'disabled' }`;
  - `google` (источник `makersuite`/`vertexai`/`gemini`) →
    `thinkingConfig: { thinkingBudget: 0 }`.
- Text Completion ризонинга не имеет; там только удаляются ключи.

Формат определяется по `chat_completion_source` в теле; без источника —
`openai`. Точное принятие этих ключей сервером ST для проксируемых
источников — живая проверка владельца (см. «Открытые вопросы»).

## Жизненный цикл

- **Директор упал** (сеть/пустой ответ/не разобрался JSON): этап
  `decision:decide` имеет одну повторную попытку. Исчерпал — `onExhausted:
  'abort'`, генерация отменяется, `generation.aborted` несёт
  `stage: 'decision:decide'`, ядро показывает уведомление.
- **Успех**: решение и правки лежат в памяти до отправки. Прозаик берёт
  решение оттуда. На `generation.completed` с `outcome: 'ended'` правки
  применяются к блокам и запись прогона кладётся в `runs` под последний
  `mesid`; затем `decision.blocks.changed`.
- **Вытесненный/отменённый/остановленный прогон**: `superseded` или
  `aborted` (а также `stopped` — консервативно считаем отменой) очищают
  ожидание; блоки и `runs` не трогаются. Полузаписанных блоков не бывает:
  правки живут в памяти целиком до коммита.
- **Смена чата** (`st.chatChanged`): перечитать `blocks`/`runs`.
- **Свайп/регенерация**: `regen: 'decider'` — директор заново;
  `regen: 'writer'` — взять последнюю запись из `runs` и не звать
  директора. Если записи нет — директор всё равно запускается.
- **Выключение на ходу**: этапы снимаются, ожидание очищается; следующий
  ход идёт старым путём.

## Открытые вопросы владельцу

1. **Вклады Модулей в контекст директора.** Сейчас трекер/время/граф
   памяти в контекст не входят: решение владельца перечисляет только
   блоки, историю и саммари. Если они нужны директору — это отдельное
   расширение состава, не побочный эффект замены тела.
2. **Воркер прозаика.** Замена тела может переопределить `model` и
   сэмплер, но не эндпоинт и не ключ: авторизация остаётся у основного
   подключения ST. Панель должна честно называть это «модель в рамках
   подключения ST», а не «другое подключение».
3. **Явное выключение ризонинга для проксируемых источников ST** —
   требует живой проверки (ключи `thinking`/`thinkingConfig` может
   понимать не каждый источник).
4. **Свёрнутая запись решения у сообщения** (d4) — если не помещается в
   блок, уходит в долги.
5. **Остановленная генерация.** Консервативно не коммитим решение; если
   владелец захочет сохранять уже принятое решение при «Стоп», это одна
   строка в условии коммита.

# Часть 2: постоянный агент с инструментами и двумя циклами

Замысел — [DIRECTOR-SPEC.md](DIRECTOR-SPEC.md), он главнее
[PART2.md](PART2.md). Всё из части 1, что не названо ниже, остаётся в силе.
Роли в коде те же: `decider` (директор), `writer` (прозаик), ядро
`cores/decision`, контракты `decision.*`.

## Что меняется в схеме части 1

- Директор отвечает **не одним JSON**, а циклом вызовов инструментов. Форма
  хода — инструмент `submit_turn`; после него прозаик сразу получает Push.
- У директора свой **лог** (сообщения цикла, вызовы, результаты, thinking).
  Он не попадает ни в чат, ни в историю ST, ни прозаику.
- Все существующие ToolCalls (Notebook, Secrets, всё через
  `generation.registerTool`) при включённом ядре доступны **только
  директору**. Прозаик получает тело без `tools`/`tool_choice`/`functions`.
- Блоки части 1 остаются, но Character Notes (≤ 4 на персонажа) их
  заменяют по смыслу: это те же «блоки о персонаже», теперь с жёстким
  потолком и привязкой к библиотеке.
- Добавляются: ростер, библиотека, планы персонажей, банк памяти, план
  директора, арки, имена, веб-субагент.

## Два цикла

**Активный (событие «начало хода»).** `generation.beforeSend` → директор
зовёт `model.generate` с `tools` и `messages`, пока не вызовет
`submit_turn` или `await`. На каждом ходе форма обязательна: без неё
прозаик не пишет. Оценки (`assess`) идут **до** формы — директор пишет
«почему успех или провал», уже зная степень.

**Пассивный (между ходами).** После `submit_turn` директор продолжает
работать в фоне: проверяет конец планов по RP Time, пишет результаты и
новые планы, ведёт банк памяти, библиотеку и общий план. Заканчивается
`await`. Пассивный цикл не задерживает ход прозаика: он стартует
асинхронно, а `generation.beforeSend` возвращает управление сразу после
формы.

**Порядок на ходу:** ход → форма → прозаик начинает писать → пассивный
цикл → `await`. До формы разрешены только чтение, `assess`, `update_roster`
и `character_note`.

**Предохранители.** Лимит шагов подряд без `await` (по умолчанию 50) и
бюджет токенов между ходами. Сработал — принудительный `await` и
предупреждение в лог. Таймаут формы — настройка (по умолчанию 180 с): не
успел — генерация отменяется с уведомлением (если не включена заготовка
хода, e11).

## Библиотека, планы и RP-часы

Библиотека (`library`) хранит имя, уровень 1–5 и обновляется инструментами
`set_character_level` / `set_character_plan`. Планы (`plans`) — отдельный
список; у каждого срок `dueAt` в **монотонных RP-минутах** (`clock`).
Минуты берутся из строки RP Time при первом ходе (`Day N, HH:MM`) и дальше
двигаются только числом `scene.minutes`; модель для этого не нужна.

| уровень | срок плана | поведение |
|---|---|---|
| 1 | 180–720 мин (3–12 ч) | несколько действий |
| 2 | 1440–10080 мин (1–7 дней) | менее подробно |
| 3 | 720–4320 мин (12 ч – 3 дня) | подробно, без особых деталей |
| 4 | — | планов нет, `set_character_plan` отказывает |
| 5 | — | только в ростере; ушёл — запись удалена |

- Персонаж в ростере: план **прерывается** (`interrupted: true`,
  `approximate: true`, `dueAt: null`) — без времени.
- Вышел из ростера: план снова ставится в очередь (`dueAt = часы`), и
  пассивный цикл пишет результат + новый план.
- Конец плана: `duePlans()` сортирует по `dueAt`; пассивный цикл разбирает
  **по одному**, ход прозаика не ждёт. Если планов нет — модель не зовётся
  вовсе.

## Предложения e11 (каждое — отдельной настройкой)

| Настройка | По умолчанию | Что делает |
|---|---|---|
| `snapshots` | **вкл** | снимок состояния до хода; свайп/удаление/отмена возвращают ростер, планы, заметки, библиотеку, план, арки и часы |
| `adaptiveReasoning` | **вкл** | на ходу — `reasoningEffort: low`, в пассивном цикле — `high` |
| `turnDraft` | выкл | пассивный цикл может сохранить `save_draft`; при таймауте формы прозаик пишет по заготовке, а не отменяет ход |
| `implicitAwait` | выкл | ответ без инструмента считается `await` |
| `costCounter` | **вкл** | в лог цикла пишутся `usage.prompt/completion/cached` из `model.generate.raw` |
| `startOnTyping` | выкл | при начале набора текста запускается фоновый черновик (нужна `turnDraft`) |

Снимок снимается **до** первого вызова инструментов; при отказе директора
он же откатывается, чтобы повтор/свайп не увидели полу-состояние. При
успешном конце снимок кладётся под `mesid`; свайп/удаление восстанавливают
его. Заготовка хода очищается после использования.

## Имена

Встроенная библиотека (`decision-names.js` + `decision-names-data/*`):
пол (male/female), культура (germany, poland, czech, latvia, china, japan),
сеттинг (modern/fictional). Для каждой ячейки — **не меньше 80** имён;
современные списки реальные, вымышленные собираются из слогов в духе
культуры. Фамилии есть у всех; у Китая и Японии полное имя — «фамилия имя».

`recall_name` выдаёт невыданное имя и пишет ключ в `names` этого чата
(атомарно, через очередь). Кончились — честный отказ, без повтора.

## Веб-субагент

Свой воркер (`researcher.workerId`) и те же веб-инструменты, что у гида Mea:
`stWebSearch.search/open/view/find`. Директор ставит задачу
`spawn_researcher` и **обязан не ждать**: `start()` возвращает id сразу.
Не больше `researcher.maxTasks` (2) задач одновременно; третья — отказ
«дождись отчёта», не очередь. Не больше `researcher.maxSteps` (50) шагов,
потом отчёт.

Отчёт сохраняется в `research` (задача, шаги, отчёт, trace), пишется в лог
директора событием и публикуется `decision.researcher.report`. Если директор
между циклами (`awaiting`), отчёт его будит отдельным фоновым циклом; если
идёт ход — отчёт просто попадёт в контекст следующего цикла. Последние
отчёты и строка «в работе» входят в контекст.

## Банк памяти и сжатие

Записи (`memoryBank`) привязаны к персонажу и плану. `important` ставит
директор, когда пишет результат; такие записи **не сжимаются никогда**.
Обычные сжимает **отдельная модель** (`compression.workerId`) в один
сжатый рекорд, когда раздел персонажа достигает `compression.thresholdTokens`
(по умолчанию 50 000; в тестах маленький). Сжатый рекорд сохраняет имена,
causal links, обещания и незакрытые линии; важные остаются рядом.
Ошибка сжатия не ломает запись результата — банк остаётся как был.

В контекст директора попадает только **индекс** банка (персонаж, число
записей, последняя строка). Полное чтение — инструментом `memory`, чтобы
кеш префикса не рушился от мегабайтов.

## Инструменты директора

Каждый вызов **обязан** нести `comment` — не меньше одного предложения
(строка с буквами и знаком конца предложения). Без него движок отвечает
ошибкой, вызов не исполняется. Это же правило действует для Notebook,
Secrets и любого инструмента, зарегистрированного через
`generation.registerTool`: их схемы движок дополняет полем `comment`.

| Инструмент | Параметры | Ответ | Проверки |
|---|---|---|---|
| `update_roster` | `{ add?: [{name, reason?}], remove?: string[], comment }` | `{ active: string[], added, removed }` | ростера нет дублей; имена непустые; ушедший уровень 5 удаляется из библиотеки, имя остаётся выданным |

| `submit_turn` | `{ scene: { minutes, place? }, resolution, userResult, characters: [{ name, decision, decisionReason, action, actionReason, speech?, assessId, outcome }], comment }` | `{ ok: true, turnId }` или `{ ok: false, missing: string[] }` | каждый активный ровно один раз; все поля непустые; `assessId` существует; `minutes` 0…1440; повтор после ошибки разрешён |

| `library` | `{ character?, comment }` | `{ ok, characters }` | только чтение |

ST; событие `generation.toolCall`/`toolResult` по-прежнему публикуется.

## Форма и Push

Форма — единственный источник истины хода. Движок **сам** собирает Push:

```
This turn took 12 minutes.
Place: the east corridor (KEEP → EAST WING → EAST CORRIDOR).
Resolution: she gets out before the guard turns the corner.
The user's push of the door: succeeds, but the lock tears the sleeve.
Lena will open the east door because she needs air — cleanly, without a hitch.
```

- Место — автоматически из `map.position.get` + `map.nodes.containmentPath`.
- Время — одно число `scene.minutes`, уходит в RP Time событием
  `decision.timeShift` (без модели, см. ниже).
- Исход действия пользователя — только **результат**; директор не решает
  за пользователя.
- Степень (`assess.words`) идёт в Push дословно.
- Прозаик получает Push + Character Notes + последние 20 сообщений + все
  саммари. В его промпте прямо написано: **успевает ли противник на
  контратаку — решает он**, директор этого не решает.

## Что видит каждая роль

| Кто | Видит | Не видит |
|---|---|---|
| Директор | правила, саммари, свой лог, историю, библиотеку/планы/банк (через `memory`), блоки и заметки, ростер, состояние, свои инструменты | прозу, чат целиком, ключи |
| Прозаик | Push, Character Notes, 20 сообщений, саммари | лог директора, инструменты, ризонинг, решения о противнике |
| Субагент | свою задачу и веб-инструменты | чат, роли, лог целиком (только отчёт) |

## Лог директора

Отдельное хранилище, не чат. Один цикл — одна запись:

```json
{
  "id": "cyc_…", "at": 0, "event": "turn|time|roster|researcher",
  "messages": [{ "role": "…", "content": "…" }],
  "toolCalls": [{ "name": "assess", "args": {}, "comment": "…", "result": {}, "error": null, "durationMs": 0 }],
  "thinking": "…", "tokens": 0, "warnings": []
}
```

Thinking хранится за текущий цикл и два предыдущих. Удаление — **пачками
на границе циклов** (не каждый цикл). Почему и цифры — в разделе «Кеш».

## Хранение

Всё — в `storage.chatMemory`, namespace `core.decision` (как блоки и
прогоны части 1). Ключи:

| Ключ | Что | Оценка объёма |
|---|---|---|
| `blocks` | блоки о персонаже (часть 1) | < 50 КБ |
| `runs` | прогоны части 1 | < 100 КБ |
| `log` | циклы, thinking, вызовы | до 500 тыс. токенов ≈ **2,0–2,4 МБ** |
| `logArchive` | сырьё завершённых арок | растёт вместе с логом |
| `roster` | активные | < 5 КБ |
| `library` | персонажи, уровни, заметки | < 100 КБ |
| `plans` | планы персонажей | < 100 КБ |
| `memoryBank` | записи банка по персонажам | 50 тыс. токенов на персонажа ≈ **0,2–0,25 МБ** |
| `directorPlan`, `arcs`, `names`, `snapshots` | план, арки, выданные имена, снимки хода | < 100 КБ |

Замеры: английский текст — 4,66 символа на токен, русский — 2,48
(`pm-tokens.js`). 500 тыс. токенов — это 2,3 млн символов по-английски и
1,24 млн по-русски; в UTF-8 оба случая дают около 2,3 МБ. Банк на 20
персонажей по 50 тыс. токенов — **4–5 МБ**.

`chatMetadata` физически лежит в файле чата ST, поэтому лог и банк
**синхронизируются и бэкапятся вместе с чатом** штатными средствами ST без
отдельного кода. Минус честный: чат раздувается. Поэтому:
- лог режется порогом 500 тыс. токенов, сырьё уходит в `logArchive`;
- банк сжимает только обычные записи отдельной моделью при 50 тыс. токенов
  на раздел персонажа;
- всё пишется через `storage.chatMemory.set` + `flush` (тот же приём, что
  у саммари), чтобы перезагрузка страницы не теряла запись.

## RP Time без модели

Контракта «сдвинуть время на N минут» в Модуле времени нет. Добавляется
минимальный путь **без вызова модели**:

- директор читает текущую отметку через `chatHistory.annotations`
  (namespace `module.time`) — тот же приём, что у саммари;
- после формы публикуется событие `decision.timeShift { minutes }`;
- Модуль времени подписан на него и двигает часы чистым разбором часового
  пресета (`HH:MM`, 12/24 ч), пишет новую отметку под текущее сообщение и
  обновляет бейдж. Если формат не разобрать — предупреждение в лог, время
  не меняется. Модель не зовётся ни разу.
- При выключенном ядре Модуль времени не подписан и работает ровно как
  сейчас.

## Место без модели

`map.position.get` → `{ nodeId }`; если позиция есть,
`map.nodes.containmentPath { id: nodeId }` → путь имён. Нет позиции — в
`current_state` честный `null` с причиной `'no-position'`, а в Push —
«Place: unknown». Никакой модели для этого не нужно.

## Forced Memory

Точка — `cores/summary/index.js`, `checkAndFold()`, цикл
`for (let levelIndex = 1; …)` **перед** `foldChildSummaries(batch, …)`.
Перед свёрткой Stage 1 → Stage 2 движок зовёт контракт
`decision.forcedMemory { batch }` (регистрируется только при включённом
ядре). Директор отвечает `{ keep: [summaryId] }`; помеченное саммари
получает `forced: true`, остаётся активным и **не** сворачивается. Снять
пометку можно тем же инструментом `forced_memory { op: 'unkeep' }`.
Ядро выключено или директор не ответил — свёртка идёт как сейчас.

## Инструменты в `model.generate` (e0)

`tools` и `tool_calls` в `model.generate` **не было**. Добавлено
**opt-in**, поэтому нынешние вызывающие не ломаются:

- `buildOpenAiRequest()` добавляет `tools`, `tool_choice`,
  `parallel_tool_calls` только если в запросе есть непустой `tools`;
  без него тело байт в байт прежнее.
- Определение принимается и в форме ST (`{name, description, parameters}`),
  и в форме OpenAI (`{type:'function', function:{…}}`).
- Ответ читается новым `resolveProviderResponseMessage()`:
  `{ text, toolCalls, finishReason }`; `openai` — `choices[0].message`,
  `anthropic` — блоки `tool_use`, `google` — `functionCall`.
- `model.generate` с `returnMessage: true` возвращает объект; без флага —
  прежнюю строку. Multi-turn `messages` по-прежнему только `openai`;
  директору и субагенту на `anthropic`/`google` карточка показывает
  понятную ошибку.

## Снятие инструментов с основного запроса ST

При включённом ядре прозаик — это основной запрос ST с заменённым телом.
`computeWriterPayload()` дополнительно вызывает `stripTools()`: удаляются
`tools`, `tool_choice`, `functions`, `function_call`, `parallel_tool_calls`,
`tool_config` (и те же ключи внутри `generationConfig`). Тело без них не
меняется. Тем самым ST/провайдер не могут позвать инструмент мимо
директора.

## Кеш: thinking за три цикла

Замер по `pm-cache.js`/`pm-tokens.js` на представительном запросе
(правила 4000 симв., 5 саммари по 1800, лог, 20+ сообщений истории,
задача; всего ≈ 6700 токенов; один thinking ≈ 507 токенов):

| Порядок частей | Общий префикс | Что ломается |
|---|---|---|
| лог **до** истории, без удаления | 4328 ток. (64,6 %) | добавление thinking в конец лога |
| лог **до** истории, удалять каждый цикл | 2780 ток. (41,5 %) | начало лога: −1548 ток. (≈ 3 thinking) |
| лог **до** истории, удалять пачкой раз в 3 цикла | в среднем ≈ 4091 ток. (61,1 %) | −1548 раз в три цикла, ≈ 237/цикл |
| лог **после** истории | 5020 ток. (74,9 %) | история скользит (последние 20), поэтому лог всё равно не кешируется |

Вывод: история — скользящее окно (последние 20), её начало меняется
каждый ход, поэтому всё, что стоит после неё, в кеш не попадает. Лог
ставится **до** истории, thinking удаляется **пачками на границе циклов**
(раз в три), а не каждый цикл: цена падения префикса платится раз в три
хода, а не каждый.

Повторный замер на реальном `buildDeciderContext` (правила, 3 саммари,
план, арки, заметки, библиотека, ростер, прогоны, 5 thinking по ~1000
симв., блоки, 20 сообщений; всего ≈ 4946 токенов):

| Способ хранения thinking | Общий префикс | Цена |
|---|---|---|
| отдельными сообщениями, дописать новое | 3447 (67 %) | теряется только хвост истории |
| один склеенный блок, дописать новое | 1966 (38 %) | теряется ВСЁ thinking: блок изменился целиком |
| отдельными, удалить самое старое | 2337 (52 %) | −1110 токенов, раз в три цикла ≈ 370/цикл |

Поэтому thinking — **отдельные system-сообщения на цикл** (`thinkingMessages`),
а не один блок: добавление не меняет предыдущие сообщения. Удаление —
пачкой раз в три цикла.

## Вероятность и степени (Guided random)

Шкалы — по опорным фразам (директор пишет английские слова, e5-small —
английская):

- сложность: `trivial 0 → very easy 0.15 → easy 0.35 → moderate 0.5 →
  hard 0.7 → very hard 0.85 → impossible 1`;
- опыт: `novice 0 → basic 0.2 → competent 0.4 → skilled 0.6 → expert 0.8 →
  master 1`.

Слово проецируется на шкалу мягким максимумом по близости к опорам
(e5-small; без модели — лексическое пересечение слов, честный фоллбэк).
Если ни одна опора не похожа — середина шкалы.

Сложность переводится в абсолютную шкалу `2·d − 0.5`: «trivial» ниже
любого опыта, «moderate» — между новичком и мастером, «impossible» — выше
мастера. Иначе равные концы обеих шкал гасили бы друг друга.

```
p = 1 / (1 + exp(−4 · (опыт − (2·сложность − 0.5))))
```

Бросок делает движок (mulberry32 от `seed` в тестах, `Math.random` в бою):
`margin = p − roll`. Полосы степени:

| margin | степень | слова в Push |
|---|---|---|
| ≥ 0.45 | flawless | «flawlessly, exactly as intended» |
| 0.20…0.45 | clean | «cleanly, without a hitch» |
| 0…0.20 | barely | «barely, with visible effort» |
| −0.20…0 | clumsy | «clumsily, with a mistake» |
| < −0.20 | botched | «badly botched» |

Примеры:

| слова директора | p | при seed 1 |
|---|---|---|
| novice / trivial | 0.88 | flawless |
| competent / moderate | 0.50 | зависит от броска |
| master / trivial | ≈ 0.998 | flawless |
| novice / impossible | ≈ 0.002 | botched |
| master / impossible | 0.12 | botched |

Это вероятность «смог ли сделать задуманное», а не исход сцены. Успевает
ли противник — решает прозаик.

## Открытые вопросы и расхождения

- **PART2 против DIRECTOR-SPEC.** PART2 в e0 просит итог в `DESIGN.md`,
  e12 — в `REPORT.md`; сделано и то и другое. Расхождений по правам не
  найдено: DIRECTOR-SPEC уточняет уровни библиотеки (5 — только в ростере,
  4 — без планов), форма и Push описаны по нему.
- **`storage.chatMemory` — файл чата.** Лог и банк на мегабайты раздувают
  чат; штатный sync/backup переносит их вместе с чатом. Отдельного
  хранилища (IndexedDB) в движке нет; заводить его — отдельное решение.
- **Thinking за три цикла** уменьшает непрерывность рассуждений; выбран
  как компромисс с кешем.
- **Таймаут формы 180 с** — настройка; живая проверка задержек не
  проводилась (по условию задачи).
- **Субагент** — фоновый, отчёт приходит в лог и будит `await`; живого
  веб-поиска в тестах нет, только фейки.

# Часть 4: окно промптов как Prompt Manager, два раздела

## Что это

Часть 3 оставила в карточке Director / Writer два текстовых поля. Владелец
просил два **раздела интерфейса**, как в старом Prompt Manager. Часть 4
возвращает окно PM выборочно и под именами директора; Ядро PM
(`cores/prompt-manager`) не возвращается.

Разделы: **Director** и **Writer**. В каждом:

- закреплённые системные строки — встроенный промпт (`decision-prompts.js`),
  только чтение: нельзя сдвинуть, удалить или выключить;
- один блок пользователя — дерево своих промптов и групп. Внутри блока
  промпты двигаются только относительно друг друга; блок целиком встаёт на
  автоматическую глубину (у директора 2 цикла, у прозаика @5 — как в части 3,
  размещение не меняется).

Окно открывается той же иконкой ST «AI Response Configuration», что и старый
PM, и кнопкой «Open prompts» из карточки.

## Слои и файлы

Библиотеки (чистые данные, без DOM и шин):

- `libraries/core/decision-prompt-model.js` — модель раздела, нормализация,
  миграция двух полей части 3, операции над системными строками (отказ на
  сдвиг/удаление/выключение);
- `libraries/core/decision-prompt-conditions.js` — вычисление условий;
- `libraries/core/decision-prompt-macros.js` — собственный движок макросов
  (синтаксис ST, без зависимости от PM);
- `libraries/core/decision-prompt-assemble.js` — сборка блока: порядок,
  вкл/выкл, условия, макросы, группы с обёртками;
- `libraries/core/decision-prompt-presets.js` — пресеты раздела, импорт

## Модель раздела

Хранится в `settings.promptSections` (см. «Хранение»):

```js
{
  director: {
    blocks: [{ id, name, role, content }],
    tree: [
      { type: 'item', block, enabled, condition? },
      { type: 'group', id, name, tag, enabled, skipWhenEmpty, condition?, children: [...] }
    ],
    presets: [{ id, name, blocks, tree }],
    activePresetId: ''
  },
  writer: { ... }
}
```

Системные строки в настройках **не хранятся**: они собираются из
`decision-prompts.js` (`DIRECTOR_SYSTEM`, `WRITER_SYSTEM`) при каждом
чтении. Поэтому их нельзя ни выключить, ни переписать через настройки.

## Сборка

1. Дерево обходится в порядке отправки. Узел выключен — пропуск. Условие
   ложно — пропуск. Группа без содержимого и с `skipWhenEmpty` не отправляет
   даже теги.
2. Текст блока проходит через макросы. Пустой текст не отправляется.
3. Группа с обёрткой отдаёт одно сообщение `<tag>\n…\n</tag>`.
4. Получившиеся сообщения вставляются **одной точкой** на глубину раздела:
   директор — перед последними двумя циклами, прозаик — за пять сообщений
   от конца. Пустой блок или всё выключено — вставки нет.
5. Роли блоков сохраняются: каждый промпт остаётся отдельным сообщением со
   своей ролью; вставка — это одна точка в истории, а не один текст.

Условия вычисляются **до** подстановки макросов в узел, как в PM; переменные,
записанные предыдущими блоками (`{{setvar::…}}`), видны условиям следующих.

## Условия: что возвращаем

| тип | источник без PM | возвращаем |
|---|---|---|
| `all` / `any` / `not` | сам движок | да |
| `keyword` | сообщения чата | да |
| `messageLength` | сообщения чата | да |
| `variable` | переменные макросов этой сборки | да |
| `chance` | `Math.random` | да |
| `everyN` | длина чата | да |
| `cooldown` | состояние чата, ключ `promptCooldowns` | да |
| `tracker` | `tracking.value` (значения предзагружаются) | да |
| `jev` | `classifier.decide` есть, но это лишний вызов модели на критическом пути хода | нет |
| типы плагинов PM | плагинов PM больше нет | нет |

`chance` и `cooldown` меняют текст блока между ходами, то есть ломают кеш
префикса. В предпросмотре они показываются предупреждением; это
осознанный выбор пользователя, а не скрытое поведение.

## Макросы

Свой движок, синтаксис совместим со ST; PM-движок не возвращается.

- значения: `user`, `char`, `persona`, `description`, `personality`,
  `scenario`, `group`, `lastMessage`, `lastUserMessage`,
  `lastCharMessage`, `input`, `model`;
- переменные: `setvar/getvar/addvar/incvar/decvar`,
  `setglobalvar/getglobalvar/…` — в пределах одной сборки, как в PM;
- случайность: `random/pick/roll` (ломает кеш, если попадёт в текст);
- время: `time/date/isotime/isodate/weekday`;
- `trim`, `newline`, `<USER>/<BOT>/<CHAR>`;
- пользовательские макросы ME — через `macros.snapshot` (кэш Ядра
  макросов). Неизвестные макросы остаются текстом и попадают в
  предупреждения предпросмотра.

## Хранение и миграция

- Разделы и пресеты — в `storage.settings`, namespace `core.decision`,
  ключ `settings`, поле `promptSections`: бэкап и синхронизация покрывают их
  без новой категории.
- Состояние кулдаунов — в памяти чата (`storage.chatMemory`, namespace
  `core.decision`, ключ `promptCooldowns`): оно привязано к чату, а не к
  установке.
- Миграция двух полей части 3: если `prompts.director` непуст и у раздела
  Director ещё нет блоков, текст становится первым промптом блока (роль
  `system`). То же для `prompts.writer`. Пустое поле не создаёт блок.
  Повторная загрузка миграцию не повторяет.

## Предпросмотр

`decision.preview({ section })` собирает скелет, не огромные тексты:

- системные строки раздела;
- блок пользователя — собранный текст (или «nothing will be sent»);
- места данных: лорбук, саммари, план, арки, заметки, библиотека/лог,
  ростер, прогоны, thinking, история для директора; саммари, заметки,
  история и Push для прозаика — плашками с количеством и размером;
- место вставки блока (глубина) относительно истории;
- предупреждения: необработанные макросы, случайные макросы, условия.

## Часть 5. Окно директора — разведка (h0)

### Что уже лежит в логе

Запись цикла — `createCycleRecord()` (`libraries/core/decision-log.js`):
`{ id, runId, at, event, messages, toolCalls, thinking, warnings, usage, tokens }`.
Цикл дописывается в `storage.chatMemory` (`core.decision`, ключ `log`) только
ПОСЛЕ завершения (`appendCycle` в `cores/decision/store.js`), поэтому в
сохранённом виде есть только «прошлое». `toolCalls` — плоский список
`{ name, args, comment, result, error, durationMs, at }`, `messages` —
сообщения диалога с моделью. Мы уже видим: пробуждение (`event`), thinking
(текст провайдера), вызовы с комментариями, аргументы и результаты, assess
(в `result` вызова), предупреждения, расходы (`usage`), пометку отвергнутого
(`rejected`, `rejectedAt` ставит `journal.markRejected`).

### Чего не хватает ленте — дописать в лог, не вычислять в окне

| Строка ленты | Чего нет теперь | Откуда брать после правки |
|---|---|---|
| Заголовок цикла | нет причины пробуждения словами, номера хода, RP-времени и длительности | новые поля `wake { type, label, detail }`, `turn`, `clockMinutes`, `endedAt`, `durationMs` |
| Форма хода | `submit_turn` отдаёт форму, но в запись цикла она не попадает | поле `form` в записи цикла |
| Push | собирается в `cycle.run()` уже после записи и живёт только в `pending` до конца генерации | поле `push` в записи цикла |
| Отчёты субагента | текст отчёта есть только в задании цикла | `wake.detail` + `wake.task`/`wake.report` |
| Сообщения директору | их нет вовсе: поля ввода и контракта нет | запись `event: 'message'` с полем `message` и отдельный цикл-пробуждение |
| «thinking…» | снаружи не видно, что шаг идёт | событие «шаг начат» |

`assess` отдельной строкой вычисляется из `toolCalls[].result` — это тот же
факт, что уже пришёл модели; дублировать его в записи не нужно. Отвергнутый
цикл уже помечен, ленте остаётся его приглушить.

### Каких событий не хватает

Сейчас Ядро публикует `decision.started`, `decision.completed`,
`decision.failed`, `decision.cycle.ended`, `decision.cycle.submitted`,
`decision.cycle.draft_used`, `decision.passive.ended`, `decision.timeShift`,
`decision.log.warning`, `decision.log.compacted`, `decision.bank.compressed`,
`decision.researcher.report`. Для живого потока этого мало: всё интересное
происходит МЕЖДУ `decision.started` и концом цикла, а запись появляется
только в конце.

Добавить ровно события хода, с данными, которых хватит строке ленты без
перечитывания лога: `decision.cycle.started`, `decision.cycle.step`
(модель думает / ответила), `decision.tool.called`, `decision.tool.result`,
`decision.cycle.thinking`, `decision.cycle.form` (форма + Push),
`decision.cycle.finished` (готовая запись), `decision.message.added`.
Чистая модель ленты (`libraries/core/decision-feed.js`) принимает старые
циклы плюс эти события и дописывает строки; полное перестроение — только
при первой загрузке и при «показать ещё».

### Поток с инструментами

Сейчас директор зовёт модель с `stream: false`
(`cores/decision/cycle.js`, `generateFor`). Поток текста сам по себе уже
есть (`model.generate.chunk`, `resolveStreamDelta`), но включить его как
есть нельзя: при `stream: true` и `returnMessage: true`
`cores/models/internal-engine.js` разбирает `lastRaw.body` как один JSON, а
тело потока — это SSE-кадры. Разбор падает, и `tool_calls` теряются. Вдобавок
`resolveStreamDelta` читает только `choices[0].delta.content` — дельты
`tool_calls` и `reasoning_content` пропускаются.

Значит, поток с инструментами **возможен, но требует правки разбора**, а не
только флага: `resolveStreamDelta` для `openai` отдаёт ещё и дельты
`tool_calls` (сборка по `index`, склейка `function.arguments`) и
`reasoning_content`; `dispatchToWorker` копит их рядом с текстом;
`model.generate` при `returnMessage` берёт накопленные вызовы, если тело —
SSE. Директор получает `stream: true` и события
`decision.cycle.step`/`decision.cycle.thinking` по мере прихода. Это h3 —
отдельным блоком, с тестами на фейковых кадрах, без живых запросов.

### Кнопка и объём

Кнопка «Open director» — в карточке Director / Writer (вместо свёрнутых
«Director log» и «Researcher reports»); постоянная круглая кнопка
`DockButton` — в собственном дереве окна, рядом с чатом. Окно открывается
событием `decisionWindow.openRequested`.

До 500 тыс. токенов окно рисует последние N циклов (30) и кнопку «Load
older» сверху — DOM растёт порциями, виртуализация не нужна. Архив сжатия
(`e6`) — отдельная свёрнутая секция «Archived arcs». Никакого
`requestAnimationFrame`: индикатор ожидания обновляет текст раз в секунду.

## Часть 6. Прозаик ходит через своё подключение ME (i0)

### Что ST ждёт от своего бэкенда

ST зовёт `/api/backends/chat-completions/generate` и разбирает ответ по
`chat_completion_source` (`public/scripts/openai.js`):
- **без потока** — `response.json()`, дальше `extractMessageFromData()`:
  для `main_api = openai` берётся `content[].text` (Claude) либо
  `choices[0].message.content` / `choices[0].text`. Сервер ST для **всех**
  источников заворачивает ответ провайдера в
  `{ choices: [{ message: { content } }], content? }`
  (`src/endpoints/backends/chat-completions.js`).
- **поток** — SSE-кадры, `data: <json>`, конец — `data: [DONE]`; разбор
  опять по источнику (`getStreamingReply`):
  Claude — `delta.text`/`delta.thinking`; Google —
  `candidates[0].content.parts[].text`; Cohere —
  `delta.message.content.text`; все openai-совместимые (OpenRouter,
  OpenAI, custom, NanoGPT, DeepSeek, xAI, MistralAI и т. д.) —
  `choices[0].delta.content`.

Вывод: **openai-совместимые источники пробрасываются почти как есть**, для
Claude/Google/Cohere кадры переводятся из openai-дельт в форму источника.
Без потока JSON подключения уже годится для всех: ST читает из него
`choices[0].message.content`. Не-chat эндпоинты (text-completions, kobold,
novelai) не покрываются — там прозаик остаётся на ST, потому что
подключение прозаика — chat-completions.

### Новый исход обёртки

`services/st-generation.js`, `installSendHook` уже знает исход
`{ replyWith }` (готовый JSON, 200). Рядом добавляется
`{ respondWith: Response }`: обёртка возвращает этот объект ST как есть,
паспорт к бэкенду ST не делается. Обработчику дополнительно передаётся
`signal: init.signal` и `endpoint` — без сигнала «Стоп» не дойдёт.

От этапа `decision:rewrite` до обёртки исход идёт через результат `fold`:
этап возвращает `{ respondWith }`, `onSend` узнаёт его и отдаёт наверх.
Сигнал и эндпоинт передаются этапу рядом с payload — через `$context`
пайплайна (новое поле `context` у `pipeline.run`, не ломает `$input`).

### Отмена

`init.signal` из fetch ST кладётся в `$context.signal`; этап передаёт его в
`http.request` сетевого Сервиса. Тот уже пробрасывает сигнал в настоящий
fetch (`dispatchStreamingRequest`) и обрывает запрос к подключению
прозаика. Поток, который мы отдаём ST, при отмене закрывается молча.

### Сетевой путь

Ядро решений получает `networkAccess: true` при регистрации (сейчас его
нет). Запрос к подключению строится `buildProviderRequest()` из
`libraries/core/provider-request.js` (openai-формат, ключ только в заголовке
этого запроса) и уходит через `host.network` → `http.request`; прямого
`fetch` в Ядре нет. Ошибки 401/429/5xx и обрыв возвращаются ST как его
обычный отказ: JSON `{ error: { message } }` с именем подключения, а в
потоке — последним кадром ошибки до `[DONE]`.

### Состав

- `libraries/core/writer-response.js` — чистый перевод кадров openai → форма
  источника ST и ответы об ошибке.
- `cores/decision/writer-proxy.js` — выбор подключения, запрос через сеть,
  Response (поток/JSON), отмена.
- `cores/decision/rewrite.js` — сборка контекста прозаика и решение
  «ответить самим / отдать тело ST»; выносится из `index.js` (305 строк).
- `cores/decision/index.js` — только проводка.
- Тесты: фейковый `fetch`/сеть, регрессия «в ST OpenRouter, у прозаика
  NanoGPT — запрос ушёл на NanoGPT с его ключом и моделью».

## Часть 7. Карточки персонажей → дата-банки (j0)

### Что отдают источники

- **Карточка ST** — `characterCard.get { avatar | name }` →
  `{ avatar, fields }`; плоские поля `description`, `personality`,
  `scenario`, `mes_example`, `post_history_instructions`, `system_prompt`.
  В банк идут `description` и `personality` (и `post_history_instructions`,
  если это уточнения, а не копия описания); `scenario` — отдельным банком
  «World / Scene»; `mes_example` — в контекст прозаика как есть, не в банк;
  `system_prompt` не используется нигде.
- **Лорбук** — `lorebook.entries` → `{ book, uid, comment, content, key,
  disable, constant }`. Категории у записи нет. Персонажи отделяются
  **разделом книги**: запись-разделитель (`comment` или первая строка
  `content`) вида `-- CHARACTERS --` открывает секцию, следующая такая же
  строка её закрывает; записи внутри — персонажи. Дополнительно принимается
  явный префикс `Character:`/`CHARACTER:` в `comment`. Порядок — по `uid`
  внутри книги; `disable` пропускается.
- **Персона** — ST держит `power_user.personas[user_avatar]` (имя) и
  `power_user.persona_descriptions[user_avatar].description` (описание).
  Сервис `services/st-character.js` получит контракт `stCharacter.persona`;
  для группового чата — `stCharacter.chatCharacters` (текущий персонаж или
  участники группы).
- **Активный ростер** — имена из `decision.roster`; банки строятся по
  источникам, а ростер решает только, кого видит прозаик.

### Хранение

Два слоя, оба в `core.decision`:
- **базовый** — `storage.settings`, ключ `characterBanks`: `{ [sourceKey]:
  { sourceHash, sourceKind, name, text, sizeBand, updatedAt } }`. Бэкап и
  синхронизация уже возят все extension settings, отдельного хранилища не
  нужно; ключ — `card:<avatar>`, `lorebook:<book>:<uid>`,
  `persona:<avatar>`, `scene:<cardAvatar>`.
- **копия в чате** — `storage.chatMemory`, ключи `characterBanks` (та же
  форма плюс `rawSource`, `status`, `error`) и `bankColdStart`
  `{ status, total, done, startedAt, updatedAt }`.

`sourceHash` — хеш текста источника (без `system_prompt` и `mes_example` у
карточки, с `comment` у записи). Совпал хеш — банк копируется из базового
слоя без модели; изменился — пересобирается.

### Холодный запуск

`decide()` и `st.chatChanged` запускают `banks.ensureColdStart()`. Он
собирает источники чата, копирует готовые базовые банки и ставит недостающие
задачи субагенту; одновременно не больше двух (лимит исследователя).
Первый ход ждёт этот промис. Ограничение — `bankColdStartTimeoutMs`
(по умолчанию 120000): по таймауту ход не отменяется, банки остаются
`pending`, а прозаик получает `rawSource`; окно директора показывает
«собрано N из M» и ошибки. Ошибка одного банка не валит остальные.

Новый персонаж в ростере без банка: директор пишет короткую версию из
известного источника сразу, полная сборка — фоновой задачей; ход её не ждёт.

### Формат банка и субагент

Банк — микро-карточка по `guide/knowledge/character-rules.md` и
`character-cards.md`: тот же скелет (Core goal, Core Personality traits,
Behaviour, Awareness, Speech, Guidelines, затем свободные разделы), короче.
`size_band`: `key` — уровни библиотеки 1–2 и главный персонаж карточки,
`minor` — остальные. Промпт субагента — `PROMPTS.md`, раздел 10, дословно,
через `fillPrompt`; подстановки `name`, `source_kind`, `source`,
`canon_hint`, `size_band`, `steps`.

### Что видит каждая роль

- **Директор** — все банки в стабильной части контекста (включая
  «World / Scene» и персону).
- **Прозаик** — только банки активного ростера и банк персоны, плюс
  «World / Scene»; примеры диалогов активных карточек — в самом начале
  стабильной части; `system_prompt` карточки — нигде.

### Инструменты директора

`character_bank` (`read` / `write` / `rebuild`) с обязательным `comment`;
чтение и правка — чатовой копии, пересборка — задача субагенту. Схема
добавляется в `decision-tool-schemas-world.js`, исполнение — в
`handlers.js`.

### Файлы

- `libraries/core/decision-banks.js` — чистые ключи, хеши, выбор источников,
  модель банка и размерные полосы.
- `cores/decision/banks.js` — два слоя, холодный запуск, очередь задач,
  инструменты.
- `libraries/core/decision-lorebook.js` — выделение записей персонажей.
- `libraries/core/decision-context.js` — банки в контекстах, примеры в
  начале.
- `cores/decision/window` / окно директора (`cores/ui/decision-window.js`) —
  список банков, текст, ручная правка, прогресс.

## Часть 8. Разметка лорбука, имена, важность, франшиза (k0)

### Где встаёт разметка

Холодный запуск уже собирает источники в `banks.collectSources()`. Перед
этим добавляется шаг **разметки книг**: для каждой подключённой книги — один
вызов воркера директора с промптом `PROMPTS.md`, раздел 11. Ответ —
`mark_lorebook_characters` с `uid`, чистым `name`, `aliases`, `importance`
(`key`/`minor`) и `franchise` (может быть пусто). Один вызов на книгу, не на
запись.

### Хранение

В базовом слое `storage.settings` (`core.decision`) — ключ `lorebookMarks`:
`{ [book]: { sourceHash, marks: [{ uid, name, aliases, importance, franchise }], at } }`.
`sourceHash` — хеш списка записей книги (`uid + comment + keys + text`).
Хеш совпал — разметка берётся без запроса; изменился — книга размечается
заново. Пустой ответ — законная разметка «персонажей нет»; в хранилище она
тоже лежит и повторно модель не зовёт.

### Кто использует разметку

- `bankSourcesForChat()` получает `lorebookMarks` и строит записи-персонажи
  из отмеченных `uid`, а не из разделов.
- `withoutCharacterEntries()` и оба лорбука (директора и прозаика) исключают
  ровно отмеченные записи; запись-персонаж не дублируется текстом.
- Имя банка — `name` из разметки; алиасы хранятся в записи банка и
  участвуют в `findBankSource`, `ensureName`, `recordsFor` без учёта
  регистра.
- `importance: key` → полоса `key`; уровни библиотеки 1–2 тоже `key`.
- `franchise` из разметки идёт в `canon_hint`; пусто — пустая строка,
  франшиза не выдумывается ни из карточки, ни из памяти модели.
- `aliases` уходят в промпт субагента (раздел 10 обновлён).

### Запасной путь

Если воркера директора нет, вызов упал, ответ не разобрался или книга не
размечена — остаётся прежний поиск по разделам (`-- CHARACTERS --`,
`Character:`), а в `bankColdStart.warnings` и в окне директора появляется
предупреждение. Ошибка разметки одной книги не мешает размечать остальные.

### Файлы

- `libraries/core/decision-banks.js` — `lorebookHash`, `lorebookSections`,
  `characterLorebookEntries(entries, marks)`, источники с алиасами и
  важностью.
- `libraries/core/decision-prompts.js` — разделы 10 (обновлён) и 11
  дословно.
- `cores/decision/lorebook-marker.js` — один вызов директора на книгу,
  проверка `mark_lorebook_characters`, запасной путь.
- `cores/decision/bank-store.js` — базовый слой `lorebookMarks`.
- `cores/decision/banks.js` — разметка перед сборкой, предупреждения,
  сопоставление по алиасам.
- `libraries/core/decision-lorebook.js` — исключение записей по разметке.
- `cores/decision/handlers.js`, `decision-tool-schemas-world.js` — схема
  инструмента (только для разметки, не в обычном списке директора).

# Часть 9: сжатый префикс лога

Решение владельца — `DIRECTOR-SPEC.md`, раздел «Сжатый префикс лога».
Цель: держать контекст директора маленьким, а кеш стабильным. После каждого
хода ход, выпавший из окна полных, один раз сжимается и **дописывается** в
конец сжатой части префикса. Сжатое никогда не переписывается (кроме сводок
закрытых арок), полными остаются два последних хода.

## Что было до части 9

Порядок `buildDeciderContext()` (`libraries/core/decision-context.js`):

1. `DIRECTOR_SYSTEM`;
2. лорбук (`lorebookText`);
3. саммари (`summariesSection`);
4. план директора (`planSection`);
5. арки (`arcsSection`);
6. заметки (`notesSection`);
7. дата-банки (`banksText`);
8. библиотека, планы, индекс банка и отчёты (`libraryText`);
9. ростер (`rosterSection`);
10. прошлые решения (`runsSection`);
11. thinking (`thoughtMessages`, отдельным сообщением на цикл);
12. история чата с блоком пользователя на глубине 2 цикла;
13. задание хода (`user`).

Меняемое стояло **перед** логом: план, арки, заметки, ростер и библиотека
правятся почти каждый ход и ломали кеш раньше истории. Thinking резался по
циклам: `store.appendCycle()` раз в три цикла вызывал `trimThinking(log, 2)`
(текущий + два предыдущих). Лог и архив жили в `log`, `logArchive`
(`storage.chatMemory`, `core.decision`); при 500 тыс. токенов
`cores/decision/compaction.js` сначала писал сводки закрытых арок, затем
`compactLog()` уводил самые старые циклы в архив. Полных ходов в контексте
не было вовсе — вместо них шли `runs` (решение + ризонинг) и thinking.

## Что становится

### Порядок контекста

1. **Неизменное:** встроенный `DIRECTOR_SYSTEM`, дата-банки, лорбук.
2. **Сжатые ходы** — готовый текст из `turnDigests`, только дописывается.
3. **Два последних хода полностью** — все циклы хода, включая пассивные:
   сообщения, thinking, вызовы, результаты, формы, Push, предупреждения.
4. **Изменяемое состояние:** план, арки, заметки, ростер, библиотека и
   планы персонажей, индекс банка памяти, саммари, отчёты субагента.
5. **История чата** с блоком пользователя на глубине 2 цикла и **задание
   хода**.

`runsSection` из контекста уходит: прошлое теперь говорят сжатые и полные
ходы. Блок пользователя остаётся в истории на прежней глубине.

### Ход и сжатая запись

Ход — все циклы от цикла с событием начала хода (`turn`, `regenerate`,
`swipe`) до следующего такого цикла. Сжатая запись (без модели):

- заголовок: номер хода, RP-время, место;
- Push хода целиком;
- комментарий к каждому вызову, по строке, с именем инструмента;
- строки изменений записывающих инструментов (`character_note`,
  `set_character_plan`, `update_roster`, `assess`, `memory write`,
  `set_plan`, `arc`, `recall_name`, `resolve_character_plan`,
  `set_character_level`, `character_bank`, `spawn_researcher`);
- сообщения владельца и ответы директора — как есть;
- отчёт субагента — задача и первые ~300 символов;
- предупреждения — одной строкой.

Результаты инструментов чтения и thinking выбрасываются: они лежат в
хранилище и повторно читаются инструментами. Полные циклы уходят в
`logArchive` без изменений.

### Хранение и запись

- `storage.chatMemory`, `core.decision`, новый ключ `turnDigests` — массив
  дописанных записей `{ key, turn, at, runIds, text, tokens }`. Записи
  только дописываются; порядок и текст не меняются.
- `log` теперь содержит только два последних хода; более старые циклы после
  сжатия уходят в `logArchive`. Thinking поэтому живёт ровно два хода — одно
  правило вместо «thinking за три цикла».
- Синхронизация — `cores/decision/prefix.js` после каждого цикла (активного,
  пассивного и сообщения) и при загрузке ядра.
- Свайп и перегенерация касаются только полных ходов: отвергнутые ходы не
  сжимаются и сжатую часть не меняют.
- Удаление/правка старого сообщения дописывает в конец сжатой части строку
  `turn N: message deleted/edited by the user`.
- Сводки закрытых арок — единственное исключение: когда размер **сжатой
  части** превышает `compressedLimitTokens` (по умолчанию 100 000), модель
  пишет сводку, и записи ходов закрытой арки заменяются ею.

### Файлы

- `libraries/core/decision-turn-digest.js` — группировка лога в ходы, чистая
  функция «ход → сжатая запись», рендер сжатой части и полного хода.
- `cores/decision/prefix.js` — синхронизация после хода: дописывание
  сжатого, перенос полных циклов в архив, поправки, сводки арок.
- `libraries/core/decision-context.js` — новый порядок частей.
- `cores/decision/cycle-context.js` — сжатая часть и два полных хода в
  контекст директора.
- `cores/decision/store.js`, `store-load.js` — ключ `turnDigests`, отказ от
  чистки thinking по циклам.
- `libraries/core/decision-settings.js`, карточка — `compressedLimitTokens`.
- Тесты: `tests/decision-turn-digest.test.js`,
  `tests/decision-prefix.test.js`, обновлённые контекстные и сценарные.

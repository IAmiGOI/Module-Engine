## 0. Решения владельца (не менять)

### Виды нод (`kind`) — что это
- **`entity`** — Сущность: любое живое существо (персонаж, животное…). Может быть в любом регионе.
- **`object`** — Объект: вещь, артефакт, а также **место и организация** (подвид, см. `subtype`). Ведёт себя как сущность, в любом регионе.
- **`fact`** — Факт: лор, устойчивое знание о мире («Кира — наследница трона»).
- **`event`** — Событие: то, что случилось, точка на таймлайне («Кира призналась, что она наследница»). Живёт **только приращённым** к другим нодам.

### Уровень (`core`) — насколько важно для сюжета
- **Core** — любой элемент (любого вида, включая событие), самый важный для сюжета. **Только Core становятся центрами регионов** — существующего или нового.
- **Core защищены**: никогда не вытесняются, не сливаются автоматически в другую ноду и **не разжалуются** (ни автоматически, ни из окна — нет операции «разжаловать»; убрать можно только удалением ноды).
- **Core полностью игнорирует правила таймлайна** (см. таблицу ниже).

### Правило рёбер
Рёбра слоя лора (сущность/объект/факт между собой) — двусторонние, как сейчас. Для событий рёбра **направленные**.

| Ребро (from → to) | Обычные ноды | Если хотя бы один конец — Core |
|---|---|---|
| не-событие ↔ не-событие (лор) | можно | можно |
| любая нода → событие | можно (тип `participates`) | можно |
| событие → событие (цепочка, тип `next`) | можно | можно |
| событие → не-событие | **нельзя** | **можно** |

Проверка на примерах владельца: Факт→Событие→Событие ✓; Факт→Событие←Факт ✓; Факт→Событие→Сущность ✗ (если ни один конец не Core); Факт→Событие←Сущность←Факт ✓.
Смысл: событие «отрастает» от лора как ветвь; из ветви нельзя вырастить ствол лора. Поэтому лор не зависит от таймлайна: событие можно свернуть или удалить, связность лора не рвётся.

### Что не решено владельцем — стоят значения по умолчанию (можно поменять одной константой)
- Повышение до Core: модель **предлагает** (`core: true` в JSON), граф **подтверждает** (проверка пороги в этапе 6), человек **закрепляет** вручную в окне. Потолок числа Core: `coreMaxShare = 0.08` (8 % от числа нод, но не меньше 5); ручное закрепление потолок не проверяет.
- Core в существующем регионе становится под-центром; если он важнее текущего центра (больше `importance`, при равенстве — больше связей) — они меняются местами (старый центр остаётся Core-под-центром).
- Блок «сюжетный каркас» (подписи 5–8 главных Core в промпт) — настройка `plotSkeletonInPrompt`, **по умолчанию выключена**.

### Что нужно помнить про текущую реализацию (найдено ранее)
- Регион описывается **ключом** (`regionId`), не парой `sector/ring` — семантические регионы не имеют `sector/ring`. Всегда работай по ключу (`attachToRegionByKey`, `regionKeyOf`).
- Рёбра в данных двусторонние: при связывании обе стороны добавляют свою запись. Для событий это меняется (этап 2).
- Органически регионы сегодня **не создаются** — только бутстрап (этап 6 это меняет).
- Ёмкость региона — `maxNodesPerRegion` (23); при переполнении: слияние дублей → реконсолидация → вытеснение слабейшего незащищённого.

Правило `checkEdge`:
1. `from` или `to` — Core → `ok`.
2. `from` — событие, `to` — не событие → `{ ok: false, reason: 'An event can only continue into another event.' }`.
3. Иначе `ok`.
Рёбра слоя лора (оба не события) остаются двусторонними. Ребро с концом-событием хранится **направленно**: только у `from` в его `edges` запись `{ to, type, dir: 'out' }`, у `to` — обратная запись `{ to: from, type, dir: 'in' }` (чтобы обход графа по-прежнему мог идти в обе стороны, но направление не терялось). Для рёбер без `dir` — прежнее двустороннее поведение.

Что сделать в Ядре (`index.js`):
1. `placeNewNode`/`createNodeManually`/бутстрап: новая нода получает `kind` (по умолчанию `'fact'`), `subtype` (только у `object`), `core: false`.
2. **Миграция `protectedNode` → `core`**: при `loadState()` для каждой ноды с `protectedNode: true` и без поля `core` — выставить `core: true` и сохранить (флаг миграции — само появление поля `core` хотя бы у одной ноды; ноды-новички получают `core: false` явно). `protectedNode` остаётся в данных как **вычисляемый синоним** (`protectedNode = core`) на весь переходный период — существующий код и тесты его читают. `isCore` читает только `node.core`; `protectedNode` поддерживается Ядром как синоним `core` (запись в обе стороны).
3. Каждое место, где сегодня создаётся ребро (`attachToRegionByKey` — связывание по имени, `addBackboneEdge`, `createEdgeManually`, `foldNodesInGraph`/`combineEdges`, реконсолидация, бутстрап-проходы рёбер регионов и сирот) — пропускай ребро через `checkEdge`; нарушение — не создаётся (в ручном создании — `{ ok: false, error: reason }`). Найди все места командой `grep -n "edges" cores/memory-graph/index.js` и проверь каждое.
4. `foldNodesInGraph` (слияние/реконсолидация): **не сливать ноды разных `kind`** (кандидаты слияния — только одного вида); Core-ноду не «поглощать» — если в паре есть Core, побеждает он, второй сливается в него.
5. Контракты: `memoryGraph.nodes` отдаёт `kind`/`subtype`/`core`; `memoryGraph.nodes.create`/`update` принимают `kind`, `subtype`, `core` (**`core: false` в `update` для Core игнорируется** — разжаловать нельзя; `core: true` разрешён — ручное закрепление).
6. Тесты (`tests/memory-graph-kinds.test.js`, чистые + orchestration):
   - таблица `checkEdge`: все комбинации {fact, entity, object, event} × {Core, обычный} × направление — сверка с таблицей выше;
   - миграция: нода с `protectedNode: true` без `core` после загрузки — `core: true`; старая нода без `kind` — `fact`;
   - `createEdgeManually` события в не-событие — ошибка; из Core-события — ок;
   - слияние не смешивает виды; Core не поглощается;
   - `core: false` в `update` для Core — без эффекта.

## Этап 2. Направленные рёбра и таймлайн

1. Хранение и связывание — как в этапе 1, п. «Ребро с концом-событием хранится направленно». Функция-помощник `addDirectedEdge(from, to, type)` в новом `cores/memory-graph/edges.js` (пишет обе записи, `degree` обоих +1, потолок `ordinaryMaxDegree` для обычных нод соблюдается).
2. **Удаление ребра** (`deleteEdgeManually`) и **удаление ноды** (`removeNodeFromGraph`) должны чистить обе записи (`dir: 'out'` у одного и `dir: 'in'` у другого).
3. **Обход графа**: `findShortestPath`/`buildBeaconTree`/`expandNoiseNodes` ходят по `edges` в обе стороны (записи `in` и `out` присутствуют у обоих концов) — **менять их не нужно**, проверь тестом, что маршрут проходит Факт → Событие ← Факт.
4. **Таймлайн**: у события поля `gameTime` (уже есть) и `createdTurn`; порядок цепочки — по рёбрам `next`. Помощник `timelineOf(nodeId)` (чистый, в `kinds.js` или `edges.js`): от ноды-якоря собрать связанные события (`participates` входящие), вернуть их отсортированными по `gameTime`/`createdTurn`, цепочки `next` — по порядку.
5. **Ёмкость и вытеснение**: события **не считаются** в `maxNodesPerRegion` (`enforceRegionCapacity` пропускает `kind === 'event'`) и не участвуют в `pickEvictionCandidate`. Регион для события не хранится (`regionId: null`, не путать с накопителем): событие показывается рядом со своей якорной нодой (первое `participates`-ребро). Для **накопителя** (`staging`) события не проходят вообще.
6. **Сворачивание старых событий** (вместо вытеснения): новый файл `cores/memory-graph/timeline-compact.js`, функция `pickEventsToFold(events, { keepRecent = 12, foldBatch = 6 })` — самые старые события одной цепочки, не входящие в последние `keepRecent`; вызывающий (`sweepTimeline()` в Ядре, по образцу `sweepMergeQueue`) складывает пачку в одно событие-сводку (`content` — пересказ моделью в одном вызове, `kind: 'event'`, связи `participates` объединяются, цепочка `next` пере-замыкается: предыдущее → сводка → следующее). Запуск — из `manualCheck` после остальных прогонов, не чаще раза в `timelineFoldEveryTurns = 20` часов-сообщений. Core-события не сворачиваются.
7. Тесты: ребро события хранится с `dir` у обоих концов; удаление ноды чистит обе записи; события не считаются в ёмкость региона; сворачивание оставляет последние N, цепочка остаётся связной; Core-событие не сворачивается.

## Этап 3. Извлечение: вид, субъекты, время

Файл `cores/memory-graph/extraction-prompt.js`. Расширить JSON факта (все новые поля **необязательные** — ответ старого формата принимается как раньше):

```json
{ "facts": [{
  "op": "create",
  "kind": "entity | object | fact | event",
  "subtype": "item | place | group",       // только для object
  "label": "...", "content": "...", "importance": 0-10,
  "core": false,                            // модель ПРЕДЛАГАЕТ; решает граф (этап 6)
  "subjects": ["Kira"],                    // о ком/чём; первое — главное
  "related": [{ "name": "Marcus", "relation": "is hiding her from" }],
  "time": "in-world or relative moment, if the text states it",
  "aliases": { "Kira": ["the princess"] }
}]}
```
1. **В промпт добавить два списка**: имена известных сущностей/объектов графа (только метки, до 60 штук, сортировать по недавности касания, потом по важности) и имена главных героев чата (персонаж карточки + персона). Правило: «используй имена из списка ТОЧНО; новое имя — только если такого нет».
2. **Объяснение видов в промпте** (кратко, с примерами): *fact* — что верно и продолжает быть верным; *event* — что произошло в определённый момент («призналась», «ушёл», «был убит»); *entity/object* — кто или что участвует. Пример: «Кира призналась, что она наследница» → `event` «Kira reveals her heritage» **и** `fact` «Kira is the heir…» (факт указывает на событие).
3. `parseExtractionResponse`: пропускает неизвестные `kind` (→ `fact`), нормализует `subjects`/`related`/`aliases`, не роняет ответ на битом поле.
4. **Разрешение субъектов** — новый файл `cores/memory-graph/subjects.js`: `resolveSubject(name, nodes)` → id ноды или `null`: (а) точное совпадение метки без учёта регистра, (б) по алиасам ноды (`node.aliases`), (в) префикс/вхождение целого слова, (г) иначе `null`. Алиасы из ответа модели дописываются в `node.aliases` (массив строк, без дублей, максимум 8).
5. В `checkAndPlace` для каждого созданного факта: `subjects[0]` разрешён → нода **получает регион главного субъекта** (`decideFirstPlacement` принимает новый параметр `subjectRegion` — приоритет между `nameMatchRegion` и сходством; причина `'subject'`); все `subjects` и `related` превращаются в рёбра через `checkEdge`/`edgeTypeFor` (тип связи — `relation` из `related`, для событий — `participates`); неразрешённый субъект-сущность создаётся заглушкой-сущностью **только со второй встречи** (счётчик `pendingSubjects` в состоянии: имя → число раз; порог `subjectCreateAfter = 2`), чтобы не плодить ноды под случайных статистов.
6. **Событие** размещается без региона, рёбра `participates` из всех разрешённых субъектов (и из фактов, которые оно установило), якорь — первый субъект. Если у события нет ни одного разрешённого субъекта — не создаётся (журнал решений: причина `'event-without-anchor'`).
7. `checkAndPlace`: журнал решений (`decision-log.js`) пишет `kind`, разрешённых субъектов, число созданных рёбер.
8. Тесты (`tests/memory-graph-extraction.test.js`): парсинг всех форматов, включая старый; неизвестный `kind` → `fact`; `resolveSubject` по метке, алиасу, целому слову; нода с известным субъектом попадает в его регион (семантический тоже); незнакомый субъект создаётся только со второй встречи; событие без якоря не создаётся; факт указывает на установившее его событие.

## Этап 4. Core: центры регионов, повышение, защита

Новый файл `cores/memory-graph/core-tier.js` (чистые функции) + правки Ядра.

1. `protectedNode` для обычных нод больше не выставляется ни в `attachToRegionByKey`, ни в бутстрапе автоматически как «первый в регионе = центр». **Центр региона — только Core.** Регион, у которого нет Core, невозможен: нода, созданная в существующем регионе, становится обычной; регион без центра при загрузке старых данных получает центром существующий `centerNodeId` (он уже Core по миграции этапа 1).
2. Бутстрап из лорбука: то, что раньше получало роль центра/под-центра региона (`centerUid`/`subCenterUids` в ответах модели), — становится `core: true`. Запись лорбука с `constant: true` — кандидат в Core (учитывается в оценке, этап 6). Классификация записей лорбука по `kind` — отдельным проходом: `classifyEntriesPrompt(entries)` в `bootstrap-prompts.js` (одна пачка → `{uid: {kind, subtype}}`; при недоступной модели — все `fact`).
3. `pickEvictionCandidate` и `enforceRegionCapacity`: Core пропускаются (как сегодня `protectedNode`). Если весь регион из Core — ёмкость временно превышается (задокументированный край, как сейчас).
4. **Core в существующем регионе**: при повышении ноды до Core (модель, ручное закрепление, автоповышение) — `promoteToCore(nodeId)` в Ядре: нода становится под-центром своего региона (`subCenterIds`, лимит `subCentersPerRegion` — при превышении она всё равно Core, но без роли под-центра); если её `importance` выше центра (при равенстве — больше `degree`) — центр и она меняются ролями, старый центр остаётся под-центром.
5. Обычные ноды-события и события-Core не имеют региона (`regionId: null`), а Core-событие как центр региона — исключение: у него `regionId` задан (оно центр). Проверь `layoutGraph`, `collectAnchors` (центр с эмбеддингом), бэкбон (`enforceBackboneConnectivity` — рёбра между центрами остаются двусторонними: Core игнорирует правила таймлайна).
6. Потолок: `coreMaxShare` (0.08) и `coreMinCap` (5) — новые настройки в `math.js` (`DEFAULT_SETTINGS`, `clampGraphSettings`). Автоповышение и «модель предложила» не превышают `max(coreMinCap, ceil(coreMaxShare × число нод))`; ручное закрепление — не ограничено.
7. Разжаловать нельзя: в `updateNodeManually` `core: false` для Core игнорируется (этап 1), окно не показывает такой кнопки.
8. Тесты: центр региона — всегда Core; повышение до Core в регионе делает под-центр; более важный Core меняется ролью с центром; Core не вытесняется при переполнении; потолок автоповышения соблюдается, ручное закрепление его обходит; бутстрап делает центры Core.

## Этап 5. Новые регионы вокруг Core

Цель: органически растущий граф получает новые регионы (сегодня только бутстрап).

1. Новый файл `cores/memory-graph/region-birth.js`: `shouldSeedRegion(embedding, anchors, { minRelativeGap })` — Core-кандидат **не похож ни на один центр**, если его сходство с лучшим центром ниже `mean − seedZ·σ` сходств кандидата ко всем центрам (нормировка внутри набора, как в `beacons.js` — абсолютные пороги для E5 не работают; значение `seedZ = 1.0`, при менее чем 4 центрах — не засевать).
2. В `promoteToCore` (этап 4): если `shouldSeedRegion` → **создать новый регион** с ключом `region:<slug метки>` (уникальный; при коллизии `-2`, `-3`), ноду — центром, `regions[key] = { centerNodeId, subCenterIds: [], nodeIds: [id], wordProfile: {} }`, публикация события `memoryGraph.regionCreated`. Иначе — существующий регион (этап 4, п. 4).
3. Потолок числа регионов: `maxRegions = 24` (раскладка окна выдерживает около 30). При достижении — новый Core просто идёт в ближайший регион.
4. Регион без нод, кроме центра, не удаляется. Регион не распускается автоматически (Core не разжалуются, пустых регионов не бывает).
5. Повышение до Core и рождение региона — только внутри `enqueueWrite` и с проверкой `stillSameChat` (как остальные мутации после ожидания модели/эмбеддинга).
6. Тесты: Core, далёкий от всех центров, засевает новый регион; близкий — попадает в существующий; при `maxRegions` регион не создаётся; при менее чем 4 центрах не засевается; событие `memoryGraph.regionCreated` опубликовано.

## Этап 6. Откуда берутся Core

1. Новый файл `cores/memory-graph/core-candidates.js`: `coreScore(node, ctx)` (чистая функция) — сумма нормированных сигналов: `importance ≥ 9` (+2), предложение модели `coreProposed` (+2), `degree` выше 75-го процентиля графа (+1), `retrievedCount` выше 75-го процентиля (+1), `constant`-запись лорбука (+1), Core-подобная связность (связана с ≥ 2 существующими Core, +1). Повышение — при `coreScore ≥ 4`.
2. Проверка **после каждого** размещения и раз в `coreSweepEveryTurns = 10` часов-сообщений: `sweepCores()` в Ядре — кандидаты по убыванию `coreScore`, каждый через `promoteToCore` (этап 4–5) пока не исчерпан потолок. Журнал решений: причина повышения.
3. Модель-предложение: поле `core` из JSON извлечения (этап 3) сохраняется на ноде как `coreProposed: true`, **само по себе Core не делает**.
4. Ручное закрепление: контракт `memoryGraph.nodes.pin({ id })` → `promoteToCore` без потолка; в окне — кнопка **«Make core»** в форме ноды (только для не-Core).
5. Настройка `plotSkeletonInPrompt` (по умолчанию `false`): при включении `injectIntoPrompt` добавляет отдельным сообщением «Plot core: <подпись 1>, <подпись 2>, …» — до 8 Core по убыванию `importance`, затем `degree` (только метки). Не входит в закреплённый блок ретрива и не влияет на кэш маяков.
6. Ретрив: `selectBeacons` — Core получает небольшой постоянный бонус (константа `protectedBonus` в `beacons.js` уже есть, переименуй в `coreBonus`, значение оставить), вместо прежнего «защищённые = бесконечность». Проверить, что `weightOf` для Core в `beacons.js` остаётся конечным.
7. Тесты: `coreScore` — таблица сигналов; `sweepCores` не превышает потолок; модель-предложение само не повышает; ручное закрепление работает; блок «сюжетный каркас» включается настройкой и не входит в sticky.

## Этап 8. Окно графа

Файлы `cores/ui/memory-graph/*` и `cores/ui/memory-graph-panel.js`.
1. **Формы нод по виду** (стили `stylesheet.js`, значения из `data(kind)`): entity — круг; object — квадрат со скруглением (`round-rectangle`); fact — ромб (`diamond`); event — шестиугольник (`hexagon`). Place/group — подвиды объекта, форма та же, подсказка в тултипе.
2. **Core** — крупная обводка (толщина 3, светлая) и **постоянная подпись** независимо от масштаба; уже существующая белая обводка защищённых нод — это она и есть (переиспользовать стиль, привязать к `data(core)`).
3. **Рёбра событий — со стрелкой** (`target-arrow-shape: triangle`) от `from` к `to`; цепочки `next` — толще; лоровые рёбра — как раньше, без стрелок. Рёбра берутся по `dir: 'out'`, чтобы не рисовать одно ребро дважды.
4. **События на карте**: без региона — раскладка `layout.js` ставит событие **рядом со своей якорной нодой** (по орбите вокруг якоря, вне диска региона, чтобы не влиять на зазоры и ёмкость); цепочка `next` — дугой. Позиция события детерминирована (по `createdAt`, потом `id`) и не сдвигает остальные.
5. **Метрики** (`metrics.js`): метрика `kind` (категориальная; цвета по видам) и `core` (Core — яркая, остальные — приглушённые); режим карты **«Plot»** = `color: core`, `size: connections`, `glow: core`.
6. **Форма ноды**: выбор вида (`kind`, подвид у объекта), кнопка **«Make core»** (этап 6), блок «Events» в форме сущности/факта — таймлайн связанных событий (`timelineOf`, этап 2); создание ребра из формы проходит через `checkEdge`, при отказе — подсказка с `reason`.
7. **Фильтры**: флажки Show — Entities / Objects / Facts / Events / Core only (класс `.filtered`, раскладка не пересчитывается).
8. Тесты: чистые функции стилей и метрик (`kind`/`core`), позиция события рядом с якорем и её детерминизм, ребро события не рисуется дважды, форма создания ребра показывает `reason` на нарушении правила.

- Не разжаловать Core ни автоматически, ни из окна. Не вытеснять и не сливать Core в обычную ноду.

# ST Module Engine — Beta Architecture (design log)

Живой документ. Фиксирует решения по мере обсуждения, включая ещё не закрытые
вопросы — чтобы ничего не терялось между сессиями. Alpha (`../Alpha/`) —
идейный референс, рабочая версия, не переписывается под Beta напрямую.

## Приоритеты (высокоуровневые, определяют любое спорное решение ниже)

1. **Простота написания модуля** — автор модуля должен знать/писать минимум
   инфраструктурного кода.
2. **Полная кастомизация** — любой слой заменяем/расширяем без правок
   остального движка.
3. **Простые, но динамические соединения с hot-swap**, регулируемые
   **на уровне ядра, без участия модулей** — модуль никогда не пишет свою
   реконсиляцию/подписки вручную (в Alpha это были `turnCounters`,
   `pollTimers`, `syncPollTimers()`, `waitForPostProcess()` — руками, в
   каждом модуле отдельно).
4. **Соединение почти ЛЮБЫХ модулей друг с другом** — максимальная
   совместимость, без искусственных стен.
5. **Безопасность от изменений ST** — вся ST-специфика изолирована в одном
   слое (Сервисы), остальное её не касается.
6. **Plug and Play — максимальный приоритет.**

## Пять слоёв

1. **Раннер** — точка входа. Поднимает всё в порядке:
   Сервисы → Библиотеки → Ядра → Модули. Сам по себе не содержит бизнес-логики.
2. **Сервисы** — единственный слой, касающийся всего, что "за движком": ST API
   (`getContext()`, `eventSource`, `chatMetadata`, macros...), DOM, сеть,
   таймеры. Каждый сервис — отдельный файл, своя semver-версия, обновляется
   независимо. **Доступ к сервису только через Шину сервисов** — никто и
   никогда не держит прямую ссылку на конкретный файл сервиса.
3. **Библиотеки** — чистые хелперы без состояния и без внешнего мира.
   Разделены на библиотеки модулей и библиотеки ядер. Пример: Ядро UI
   (примитивы — реактивность, диффинг) внизу, а Библиотека — готовые виджеты
   (Toggle/Select/DraggableList) поверх, доступна и модулям, и ядрам.
4. **Ядра** — реальная логика движка, ST вообще не касаются (за этим — только
   через Сервисы). Друг друга напрямую не знают — любое Ядро↔Ядро идёт через
   Шину ядер. Примеры: Ядро UI, Ядро SideCar, Ядро TTS, сами Шины (см. ниже).
5. **Модули** — как в Alpha (Tracker, RP Time...), но радикально проще:
   почти вся инфраструктура (реконсиляция, ожидание условий, выбор
   поставщика) уезжает в Ядра/Шины и модулю не видна.

## Ядро или Модуль — критерий

**Модуль подключает пользователь. Без Ядра движок не работает.** Это и есть
вся проверка, и она отвечает на вопросы, которые раньше решались «на глаз»:

- UI движка — **Ядро**: движок без своего интерфейса не функционирует, и
  пользователь его не выбирает и не отключает.
- Notebook, Music, Dice — **Модули**: движок прекрасно работает, если их
  никто не поставил.

Из этого же следует, что «первый настоящий Модуль» появится не тогда, когда
мы напишем что-то с UI, а тогда, когда напишем что-то **отключаемое**.

*(Пограничный случай, не закрыт: Ядро Dev-panel и Ядро статистики по
буквальному прочтению критерия не обязательны для работы движка, но и
пользователем не устанавливаются — они поставляются с движком. Похоже,
критерий двухчастный: «ставит пользователь → Модуль; поставляется с движком
→ Ядро». Формулировку надо подтвердить, прежде чем переразмечать таблицу в
CORES.md.)*

## Система Шин / Директоров (ядро связности)

Несколько типизированных Ядер-Шин, каждая — свой домен, список открыт:

- **Шина событий** — broadcast pub/sub, тупой транспорт. Всё, что на неё
  попадает, проходит через **Ядро событий**
  ([cores/events/index.js](cores/events/index.js)): и нативные ST-события
  (их приносит тонкий [Сервис событий](services/st-events.js), знающий
  только про `eventSource`/`eventTypes`), и произвольные события, которые
  публикуют сами Ядра и Модули — **динамически, в реальном времени** (пользователь
  добавил трекер-блок → тут же появилось событие "блок X обновлён", без
  правок кода). Это прямое обобщение reserve()/unreserve()-реконсиляции,
  которая в Alpha уже работала для *данных* (DataBus) — теперь то же самое
  для *событий*.
- **Шина модулей** — модуль↔модуль по контракту.
- **Шина ядер** — ядро↔ядро по контракту.
- **Шина сервисов** — единственный путь к сервису.
- **Шина сети** — единственный путь к внешнему интернету (`http.*`
  контракты, реализованные Сервисом HTTP — [services/http.js](services/http.js)).
  Реализована **как отдельная, физически независимая шина**, не как ещё один
  Гейт поверх Шины сервисов — см. "Гейт для сети" ниже, почему это не
  косметика, а единственный способ не дать эту проверку обойти.

**Директор** = роль, которую каждая шина играет для своего домена (5
независимых брокеров, не единый узел). Заказчик не знает поставщика; шина
резолвит:
- **КТО** отвечает — по заявленной поставщиком метрике загрузки (обобщение
  round-robin выбора SideCar-воркера из Alpha);
- **КОГДА** отдавать ответ — гейтится на условие/событие (обобщение
  hand-rolled `waitForPostProcess` из Alpha: подписка-до-эмита, чтобы не
  пропустить уже случившийся сигнал);
- **В КАКОМ ФОРМАТЕ** — если контракт может быть реализован по-разному.

**Контракт** — предобъявленная форма запрос/ответ, по имени которой заказчик
просит, а поставщик регистрируется (уже было в Alpha, теперь это единственный
способ адресации на любой шине).

### Заказчик API — подтверждено

Шина/Директор знает **только один примитив**: `subscribe(contract, { when
}, callback)` — постоянная подписка, событийная доставка через Директора,
без таймаута вообще (для периодических/редких/state-based условий таймаут
концептуально неверен — ничего не "висит", просто ещё не случилось).

**Весь словарь условий доставки живёт в Директоре, а не в Ядрах/Модулях**:
`{event}`, `{every:{event,count}}` / `{event, every:N}`, `{every:{ms}}`,
плюс модификаторы `debounceMs`, `throttleMs`, `dedupe`, `once` (см.
[contract-bus.js](libraries/shared/contract-bus.js) и
[delivery-filters.js](libraries/shared/delivery-filters.js)). Это прямое
следствие приоритетов №1 и №3: «раз в N ходов», «не чаще раза в секунду»,
«схлопни всплеск» — то, что в Alpha каждый модуль писал у себя счётчиками и
таймерами, здесь не пишется вообще нигде, кроме одного места. Ядро трекинга
именно так и объявляет свои триггеры — строкой имени события или готовым
условием, без единой строчки собственной обвязки.

`request()` (разовый "получить один раз и упасть в await", опционально с
таймаутом для condition-типа "завершение" — что-то уже в процессе, должно
случиться скоро, как Post-Turn) — это **не примитив шины**, а тонкий хелпер
из **Библиотеки**, собранный поверх `subscribe()`: подписаться → дождаться
первого срабатывания → сразу отписаться → завернуть в Promise (таймаут —
`Promise.race` внутри той же обёртки). Меньше примитивов у самой Шины —
меньше поверхности для багов, проще написать модуль.

Второй (и единственный сверх `subscribe()`) метод Шины — интроспекция
`contracts()`: что вообще зарегистрировано и сколько поставщиков у каждого
контракта. Это НЕ канал данных — исполнить через него ничего нельзя, только
посмотреть; нужен он затем, что иначе «показать состояние движка» пришлось
бы делать через реестр в обход Директора, а такой реестр немедленно начал бы
расходиться с реальностью. Первый потребитель — [Ядро панели
движка](cores/ui/engine-panel.js), левая колонка.

Это напрямую заменяет в Beta то, что в Alpha было руками у Tracker:
mode 2 (ждать Post-Turn) → библиотечный `request()` с таймаутом поверх
`subscribe()`; mode 3 (раз в N ходов) и mode 4 (раз в N минут) →
`subscribe()` напрямую, без таймаута, просто разный `when`.

### Поставщик

Регистрируется на шине как реализующий контракт. Может (опционально) отдать
директору метрику загрузки и/или **сам регистрировать собственные события**
на Шине событий (как обычный источник, без особого API) — директор на них
просто подписывается, как на любые другие.

## Подтверждённые сквозные решения

- Ядро↔Ядро: только через Шину ядер.
- Сервис: только через Шину сервисов, **без исключений** — даже когда
  резолвинг тривиален (структурно один поставщик, как DOM на платформу).
  Раньше здесь была попытка развести это на "резолвинг" и "проверку прав" и
  сделать для DOM прямое связывание Ядро↔Сервис в обход Гейта — неверно:
  тривиальность резолвинга (кого выбрать) не отменяет необходимость
  проверки прав (можно ли вообще). Без Гейта Ядро финального UI получило бы
  нефильтрованный доступ к DOM — ровно то, от чего Гейты должны защищать.
  Это ровно тот случай, под который уже спроектирован приоритет `immediate`
  в очереди Директора: быстро (не ждёт в общей очереди с тяжёлыми
  запросами), но всегда через реальную проверку прав, никогда в обход неё.
- UI-сплит: Ядро UI = примитивы; готовые виджеты = Библиотека поверх.
- Версии: формальный semver + compatibility gate в Раннере (детали gate —
  см. открытые вопросы).
- Граница "сервиса" = максимально широкая: ST + DOM + сеть + таймеры — всё,
  что "за движком".
- Динамическая регистрация (контракты/события/поставщики) — реконсиляция на
  уровне шины/ядра, модуль об этом не думает.

## Директора vs Гейты — важное разделение терминологии

Настоящих резолвящих Директоров — ровно 5, по одному на шину (события/
модули/ядра/сервисы/сеть). Всё, что раньше называлось "директор 4↔2",
"директор 4↔5" и т.п. — на самом деле **Гейты**: лёгкие соединители МЕЖДУ
двумя настоящими Директорами, без своей логики выбора поставщика/нагрузки/
условия. Пример полной цепочки (Ядро → SideCar):

```
Ядро → Директор своей шины (Шина ядер)
     → Гейт (не резолвит — только проверяет права)
     → Директор Шины сервисов (вот тут резолвинг — кто из сервисов исполнит)
     → HTTP-сервис (делает запрос)
```

Гейт — это в первую очередь **точка проверки прав** (см. ниже), не проводник
без логики и не второй резолвер.

## Система прав (безопасность)

**Модуль/ядро никогда не знает и не может подделать свои собственные права.**
Единственный источник правды — Директор ЕГО СОБСТВЕННОЙ шины (Шины модулей
для модуля, Шины ядер для ядра) — знает права из своего реестра с момента
регистрации заказчика, не из того, что заказчик заявляет о себе в запросе.
Гейт на переходе между шинами — точка, где эти права реально проверяются.

**Права плоские** — один набор возможностей на весь модуль/ядро, не по
контрактам отдельно.

**4 уровня доверия, определяющие набор прав при регистрации:**
1. **Официальные** — non-restricted, предустановленные с GH, в списке
   исключений — фактически без ограничений.
2. **Community submitted, проверенные на официальном GH** — несут
   зашифрованный ключ (выдан при одобрении), расшифровывается при
   инициализации модуля в конкретный набор прав. Верификация **офлайн, без
   сети** (живая онлайн-проверка отзыва — рассматривали, отклонили, не
   настолько важна). Ключ = зашифрованный { ID модуля, хэш конкретных
   фрагментов кода (название + отобранные "ключевые функции" — НЕ весь
   код), права }, подписан приватным ключом ревьюера; движок при загрузке
   пересчитывает тот же хэш по реальным файлам модуля и сверяет — так ключ
   нельзя просто скопировать на другой/изменённый модуль. Правило отбора
   фрагментов для хэша **намеренно не раскрывается** — второй, менее
   формальный барьер поверх самой подписи.
3. **Непроверенные, но похоже что безопасные** — по результату внутреннего
   сканирования не найдено ничего опасного — права выдаются по результату
   скана.
4. **Непроверенные и небезопасные** — тоже права по скану, но более
   ограниченные.

Для уровней 3 и 4 политика **default-allow**: разрешено всё, что явно не
запрещено сканом (не наоборот). *(Отметка: это осознанно более мягкая
модель, чем deny-by-default — принято как есть, не оспариваю.)*

**Эта же 4-уровневая система — общая и для Модулей, и для Ядер**, не
специфична для Модулей. На практике Ядра в подавляющем большинстве останутся
first-party (пишет сам автор движка), так что уровни доверия для них редко
активируются — но если появится community-ядро, оно проходит ту же проверку,
что и community-модуль. Механизм один и тот же для обоих слоёв.

**Нарушение прав** (модуль просит то, что ему не положено):
- Модуль **отключается насовсем** — не разовый отказ одному запросу, а
  карантин: не включится обратно (в рамках этой установки/сессии).
- Помечается **жёлтой меткой** — очень заметной, но видна **только на
  карточке самого модуля** (в списке модулей/настройках), нигде глобально.
- Текущий ответ/генерация **не прерывается** — система продолжает работать.
- **Пользователь не оповещается** проактивно — узнаёт, только если сам
  зайдёт посмотреть на карточку модуля.
- Карантин привязан к **стабильному ID/хэшу модуля**, переживает
  переустановку тех же файлов — переустановка не смывает нарушение
  гард-рейла.

## Сетевой доступ — отдельное бинарное право, не часть уровня доверия

Выход в интернет — качественно другой риск (данные буквально покидают
машину пользователя), поэтому это **отдельное, бинарное право**
(`networkAccess: true/false`), а не что-то, что подразумевается уровнем
доверия — даже **официальный** уровень по умолчанию получает
`networkAccess: false`. Выдаётся явно, при регистрации заказчика, отдельно
от `tier`/`allowedContracts`.

Проверяется **отдельным Гейтом** ([libraries/shared/network-gate.js](libraries/shared/network-gate.js)) —
композиция обычного Гейта плюс дополнительная проверка `hasNetworkAccess()`,
и на `subscribe()`, и на каждой доставке (та же дисциплина "карантин
действует немедленно", что и у обычного Гейта). Карантин отзывает
`networkAccess` так же, как и всё остальное.

**Почему Шина сети — физически отдельная шина, а не ещё один Гейт поверх
Шины сервисов**: если бы `http.*` контракты регистрировались на той же шине,
что `dom.*`, заказчик с ЛЮБЫМ посторонним `allowedContracts`-правом на эту
шину мог бы достучаться до `http.request` через обычный (не сетевой) Гейт —
`hasNetworkAccess()` при этом даже не был бы вызван, потому что запрос не
проходил бы через network-gate.js вообще. Это тот же класс ошибки, что уже
однажды случился с Ядром финального UI (см. "Подтверждённые сквозные
решения" выше — прямое связывание Ядро↔Сервис в обход Гейта) — здесь тот же
урок применён заранее, до того как ошибка успела случиться: не полагаться
на "структурно один путь", строить физическую изоляцию, которая делает
обход невозможным, а не просто маловероятным.

## Интерфейс

Правила, по которым строится всё, что видит пользователь — слои и границы,
иерархия фоном вместо рамок, цвет, кнопки, сворачиваемость, расположение,
встраивание в ST — вынесены отдельно: **[UI.md](UI.md)**. Там же записано,
какой конкретной ошибкой оплачено каждое правило.

## Блоки — организующая единица внутри любой шины

Вместо отдельного "живого реестра"/introspection-API (как `listChannels()` в
Alpha) — переиспользуем уже существующие примитивы:

- Любая шина (не только событий) группирует свои записи в **Блоки** —
  категория/группа внутри шины. Блоки разных шин **не связаны структурно**
  друг с другом — просто одноимённая концепция, у каждой шины свой набор.
- Когда содержимое Блока меняется (новое поле у трекера, новая опубликованная
  запись лорбука) — владелец триггерит на **Шине событий** сигнал "Блок X
  пополнен/изменён" — про Блок целиком, не про каждый элемент отдельно.
- Потребитель (например, пикер в Macros) подписывается не на конкретный
  модуль по имени, а на события конкретной **категории Блока** — и по
  срабатыванию перезапрашивает актуальное содержимое обычным
  `request()`/`subscribe()` к нужной шине.
- **Таксономия категорий Блоков (например, "insertable-values") — это роль
  ДВИЖКА**: публикуется и поддерживается централизованно (материалы/
  документация + формальная разметка), а не неформальная договорённость
  между авторами модулей. Автор нового модуля просто регистрирует свой Блок
  под официальным именем категории из этой таксономии — и он автоматически
  подхватывается любым потребителем этой категории, без правок в чужом коде.

**Реестр этапов пайплайна — это Блок, а не что-то рядом с ним.** Первый
реальный Блок в коде появился именно так ([Ядро пайплайнов](cores/pipeline/index.js)):
`pipeline.stages.add` = запись в Блок, `pipeline.stagesChanged` = тот самый
сигнал «Блок X изменился целиком», по которому потребитель перезапрашивает
состав. Отдельной сущности «Блок вкладов в промпт» рядом с пайплайном не
заводится: два реестра одного и того же немедленно начали бы расходиться.

## Личность вызывающего и исполнение от чужого имени

Директор передаёт поставщику ВТОРЫМ аргументом личность спрашивающего
(`handler(params, { callerId })`) — не данные, а именно личность. Нужно это
поставщику, который что-то регистрирует ОТ ИМЕНИ вызывающего: брать владельца
из `params` нельзя, их пишет сам вызывающий, и подделать чужое имя было бы
тривиально. Домашняя шина (`host.own`) личность тоже несёт, оставаясь при
этом БЕЗ Гейта — ничего не пересекает границу домена, но знать, кто пришёл,
поставщик обязан.

Обратная сторона — `engine.resolveAs(callerId, contract, params)`:
исполнить контракт ОТ ИМЕНИ другого вызывающего, тем же путём, через тот же
Гейт, с теми же правами, что были бы у него самого. Это привилегированная
возможность, выдаваемая при сборке движка ровно одному потребителю — Ядру
пайплайнов (та же форма, что `publish` у Ядра событий). Без неё пайплайн,
исполняющий ОБЪЯВЛЕННЫЕ чужими Модулями этапы, делал бы это под своей
личностью — и стал бы отмывочной для прав: объявил этап и дотянулся куда
угодно. Тот же урок, что с отдельной Шиной сети: не «структурно один путь»,
а физическая невозможность обойти проверку.

## Движок владеет генерацией целиком — и что это стоит

Осознанное решение владельца проекта, принятое после того, как альтернатива
была изложена: движок **забирает у SillyTavern саму отправку на модель**, а не
дописывает свой кусок к тому, что ST собрал сам. Реализация —
[Сервис перехвата](services/st-generation.js), детали в PIPELINE.md.

**Цена, записанная явно.** Штатный путь расширения ST — аддитивный:
`setExtensionPrompt` добавляет свой блок, ничего не отбирая у соседей. Наш
путь другой: тело исходящего запроса проходит через `generation.payload` и
уходит в том виде, какой собрал движок. Стороннее расширение, рассчитывающее
на нетронутый путь отправки ST, в этой конфигурации работать не обязано.
Обоснование — то же, что у самого проекта: расширения переезжают в движок
Модулями, и тогда конфликт исчезает не потому, что мы уступили, а потому что
конкурирующего кода больше нет.

**Что из этого следует для кода.** Раз мы ведём отправку, обязанность вести
её КОРРЕКТНО целиком тоже наша:

- Незнакомое тело запроса пропускается нетронутым, а не ломается о наше
  предположение о его форме.
- Не наш эндпоинт не трогается вообще — обёртка `fetch` смотрит только на
  пять реальных путей генерации и только на POST.
- `uninstall()` возвращает ST его собственный `fetch` и снимает глобальную
  функцию: снятый движок не оставляет следов.
- Отказ пайплайна ОТМЕНЯЕТ генерацию, а не отправляет неполный промпт молча.
## Персистентность

Настройки/состояние модуля или ядра — это ST API (extensionSettings/
chatMetadata), то есть по определению Сервис. Единый путь, чтобы не
повторить разнобой Alpha (LorebookService/ModuleEngine/Tracker хранили
настройки каждый чуть по-своему):

```
Модуль/Ядро → своя шина → Гейт → Директор Шины ядер
            → Ядро сохранения (реальная логика: неймспейсинг, кто что пишет)
            → тонкий Сервис (реальная запись в extensionSettings/chatMetadata)
```

Персистентность — не особый случай, а обычный контракт, который резолвится
так же, как любой другой. Ядро сохранения ([cores/settings/index.js](cores/settings/index.js))
— обычный поставщик; "и Модули, и Ядра шлют данные" остаётся верным, но
**не** буквальной двойной регистрацией на обеих шинах сразу (см. поправку
ниже) — оба достают его контракты, просто разными путями: Ядро — напрямую
(свой домен), Модуль — через обычный Гейт Модуль→Ядро.

**Поправка (пишу по факту реализации, не переписывая историю решения выше):**
формулировка "зарегистрирован сразу на Шине модулей и на Шине ядер" была
написана до того, как более позднее, проверенное на практике правило
("КАЖДЫЙ переход Ядро/Модуль → что угодно другое — через настоящий Гейт, без
исключений", см. историю ошибки с Ядром финального UI выше) устоялось.
Буквальная двойная регистрация означала бы, что Модуль вызывает
`storage.settings.*` через СВОЮ ЖЕ Шину модулей — то есть вообще без Гейта,
без проверки прав. И Ядро сохранения, и Ядро внутренней памяти чата (ниже)
реализованы единообразно: регистрация ТОЛЬКО на `host.own` Ядра (Шина ядер),
Модуль достаёт через обычный, проверенный Гейт.

**Ядро внутренней памяти чата** ([cores/memory/index.js](cores/memory/index.js))
— тот же общий разрез (Ядро владеет неймспейсингом, тонкий Сервис делает
реальную запись), но для произвольных чат-scoped данных, не для
settings/config — см. CORES.md за тем, почему это отдельное Ядро, не то же
самое, что Ядро сохранения.

**Неймспейсинг: заявленный, не проверенный.** Шина/Гейт доказывают только
ПРАВО вызвать контракт (`storage.chatMemory.*`), но не то, ПОД КАКИМ
namespace конкретный вызов пишет — вызывающий передаёт `namespace` строкой
в параметрах запроса, как Alpha годами передавала `moduleId` без структурной
проверки. Рассмотренная альтернатива — прокидывать через Гейт настоящий,
проверенный `callerId` вторым аргументом обработчику — была бы безопаснее
(id уже проверен на пересечении шины), но потребовала бы менять сам
примитив Шины/Гейта (`gate.js`/`contract-bus.js`) ради одного текущего
потребителя. Осознанно отклонено сейчас: official-уровень доверяется по
определению, community-уровень физически не достанет до контракта без
явного гранта в своём ключе — тот же компромисс, что уже принят для
`allowedContracts` в целом (плоские права, не по аргументам вызова).

**Обновление**: второй потребитель того же компромисса уже есть — Ядро
сохранения (`storage.settings.*`) использует ту же схему заявленного
namespace, без изменений. Решение подтверждено как рабочее на практике для
обоих Ядер, не только гипотетически; проброс проверенного `callerId` через
`gate.js`/`contract-bus.js` остаётся возможным будущим шагом, но пока не
выглядит необходимым — ничего в двух реальных потребителях его не
потребовало.

## Контракт на ошибки (единый для всей системы)

- **Директор перехватывает любое исключение на каждом шаге цепочки** — ни
  Гейт, ни другой Директор, ни сам заказчик никогда не получают сырое
  исключение напрямую.
- **Единый конверт доставки** в `subscribe()`: колбэк получает либо успешное
  значение, либо структурированный отказ (`{ ok:false, error }`) — никогда
  не падает по вине чужого кода. Это гарантия шины, не дисциплина автора
  модуля (приоритет №1 — простота).
- **Один упавший подписчик не портит рассылку остальным** — то же правило,
  что уже подтверждено для событий в Alpha, теперь общее для всех шин.
- **Логирование ошибки — та же точка, что аудит-лог** (см. бэклог ниже) —
  не отдельная система, естественное расширение того же механизма.
- **Разделение по серьёзности**: нарушение прав — тихо (карантин без
  оповещения, уже решено). Обычная рантайм-ошибка (баг, не злой умысел) —
  видна **локально, на карточке конкретного модуля/ядра** (как "last error"
  у макро-программы в Alpha), но не глобальным тостом — не спамим
  пользователя, но и не прячем совсем.

## Приоритет запросов (для латентности UI)

Приоритет — свойство **контракта**, объявленное поставщиком один раз при
регистрации (UI Core регистрирует свои контракты как `immediate`, SideCar
Core — как `queued`), не то, что каждый вызывающий код указывает вручную.

Важно: "вне очереди" влияет только на **порядок обработки** внутри очереди
Директора — Гейт и проверка прав проходятся всегда, для любого приоритета.
Иначе UI-запросы тихо обходили бы всю систему безопасности.

## Бэклог полезных расширений (оценены, не все начаты)

1. **Аудит-лог / полная трассировка запросов** — подтверждено, хотим.
   Каждый запрос обязан пройти через Директора — естественная точка
   логирования: кто кого спросил, кто ответил, что отклонено по правам.
2. **Живой граф зависимостей** — подтверждено, хотим. В Alpha
   DependencyScanner ДОГАДЫВАЛСЯ по регулярке; здесь граф реально известен
   движку из живых регистраций на шинах — точная карта без статанализа.
3. **Квоты/rate-limit на ресурсы** — опционально, записано. Гейт — уже
   единая точка проверки прав, туда же естественно ложится "сколько раз за
   минуту", не только "можно/нельзя". Обобщение того, как SideCar в Alpha
   пропускал занятых воркеров, но универсально для любого ресурса.
4. **Офлайн-SDK для разработки модуля** — упомянуто, не оценено явно.
5. **Живая замена модуля без перезапуска движка** — в долгий ящик,
   осознанно отложено. Технически становится возможным именно из-за того,
   что никто нигде не держит прямых ссылок (только через Директоров).


## Закрытые вопросы (для истории)

- Ядро↔Модуль: та же форма, что Ядро↔Сервис (Директор своей шины → Гейт →
  Директор шины-адресата) — подтверждено.
- Граница "сервиса": подтверждена widest reading — всё, что выходит за
  границы логики движка (ST, сеть, парсинг сайтов, DOM, таймеры). Просто
  логический адаптер, без собственной логики.
- Живая онлайн-проверка отзыва ключа — рассмотрена и отклонена, не
  настолько важна. Верификация ключа полностью офлайн.
- Failure mode при несовпадении semver: изолируется только несовместимый
  кусок, не весь движок (то же самое "один сломанный не должен ронять
  остальных", что уже было в Alpha).
- Живой реестр "что сейчас доступно" — закрыт через концепцию Блоков (см.
  выше), отдельный introspection-API не нужен.
- `request()`/`subscribe()` API: подтверждено — Шина знает только
  `subscribe()`; `request()` (разовый + опциональный таймаут) — библиотечная
  обёртка поверх него, не отдельный примитив шины.
